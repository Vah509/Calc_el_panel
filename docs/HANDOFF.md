## Состояние (актуально на v63)

**Единица измерения (unit) — готово.** Новый плоский справочник
`unit` (по образцу kit_group: только «Название» + «Порядок»,
`delete_mode="simple"`, БЕЗ hierarchy — физическое удаление сразу без
проверки детей, только модалка ✎, без чекбоксов). `name` хранится
СРАЗУ в сокращённом виде («шт», «м», «кг», «услуга») — используется
везде как есть: список/форма материала, в будущем — спецификация/счёт.
`material.unit_id` — новое FK-поле, nullable на уровне БД (сознательно,
чтобы не сломать существующие в проде материалы без единицы
измерения), но `required=True` в форме — при СОЗДАНИИ или РЕДАКТИРОВАНИИ
любого материала unit обязателен (`_validate_required` в api.py
проверяет на create И update одинаково). Значит любой существующий
(legacy) материал без unit_id можно спокойно читать/видеть в списке,
но при первом же сохранении через форму придётся проставить единицу
измерения — это ожидаемое поведение, не баг, полезно уточнить у
Вахтанга явно при тестировании на устройстве.

«Услуга» (сборка щита) реализована НЕ отдельной сущностью, а обычным
материалом с `unit_id`, указывающим на unit с `name="услуга"` —
решение Вахтанга (2026-08-23): проще, не создаёт третий тип позиции
для будущего `calculation_item` (там всё равно будет material_id ИЛИ
kit_id, услуга — просто material с особым unit).

## Сделано в этой сессии (2026-08-22 — v62: создание калькуляции из заявки)

**Новое в движке (универсальный паттерн, не хардкод под request/calculation):**
`TableConfig.create_child_document_url: Optional[str]` (config.py) —
если задан, ПЕРВАЯ кнопка из уже существующего списка
`child_document_actions` перестаёт быть заглушкой: активна при
выделении ровно одной строки, по клику зовёт новый JS-метод
`createChildDocument()` (page.py) — редирект на указанный URL с
`?from_request={id}` выбранной записи. Остальные кнопки списка (если
их несколько) по-прежнему disabled-заглушки — механизм рассчитан на
постепенный переход от заглушки к реальной кнопке, ровно как раньше
задумывался `child_document_actions` в v56.

На принимающей стороне — новый метод `maybeOpenFromRequest()`, вызывается
из `init()` любой страницы движка сразу после первой загрузки списка.
Проверяет `?from_request=` в адресе И что у текущей таблицы есть поле
`request_id` в форме (сейчас — только calculation, но не привязано к
имени таблицы намеренно — сработает для любого будущего документа с
таким же полем, например specification). Если оба условия выполнены:
чистит query-параметр из адресной строки (чтобы повторное открытие
формы не переиспользовало старую заявку), вызывает обычный `openCreate()`,
подставляет `request_id`, дальше зовёт `runAction('brand_slot_labels')`
— тот же путь, что уже отрабатывает при ручной смене заявки в открытой
форме (v61) или при `openEdit()` существующей записи (v58) — никакой
новой логики подтяжки брендов не потребовалось, только точка входа.

Файлы: `app/engine/config.py` (`TableConfig.create_child_document_url`),
`app/engine/page.py` (`createChildDocument()`, `maybeOpenFromRequest()`,
условный рендер первой кнопки `child_document_actions` в Jinja,
`createChildDocumentUrl` в `_serialize_level_config`), `app/engine/tables.py`
(`request_table.create_child_document_url = "/calculation-v2"`),
`app/version.py` → v62.

**Проверено (TestClient, e2e):** все 9 страниц движка рендерятся 200;
`config_json` заявок содержит `createChildDocumentUrl: "/calculation-v2"`;
HTML заявок содержит вызов `createChildDocument()` на активной кнопке;
HTML калькуляций содержит `maybeOpenFromRequest`/подхват `from_request`;
`/calculation-v2?from_request={id}` открывается без ошибок для заявки
как с заполненными брендами (обеими или частично), так и вовсе без
брендов; конфиг калькуляции подтверждённо содержит поле `request_id` и
radio-поле `brand_slot` с `radioLabelsAction: "brand_slot_labels"` —
именно то, что дёргает `maybeOpenFromRequest()` после подстановки
заявки. Регрессия: material/client/request create не сломаны, вторая

формы калькуляции сразу с выбранной заявкой и видимыми названиями

DEFAULT_NAME_TEMPLATE` (импортировано из `app/models/calculation.py`,
одна константа-источник, не задвоено) — новая калькуляция открывается
сразу с заполненным шаблоном, кнопка работает сразу.

## Сделано в этой сессии (2026-08-22 — v59: формирование названия без предварительного сохранения)

Проблема (со слов Вахтанга): раньше «Пересчитать название» ходила на
сервер по `editing.id`, поэтому для НОВОЙ калькуляции кнопка не
работала до первого сохранения — а нужно видеть готовое название ДО
сохранения. Решение: `ActionButton.client_side: bool` (новый флаг в
`config.py`) — если True, `runAction()` в page.py ищет функцию в
глобальном JS-объекте `CLIENT_ACTIONS` (по имени action) и считает
результат целиком в браузере, без fetch и без проверки id. Для
calculation `recalc_full_name` — точное зеркало серверной
`app/engine/name_template.py::render_name_template()`: те же три
плейсхолдера (`{client_name}`/`{brand_slot}`/`{request_number}`), та
же логика замены. Номер связанной заявки берётся не отдельным
запросом, а из уже загруженного `relationOptions['request_id']` (тот
же список, что в `<select>` поля «Заявка» — грузится один раз при
открытии страницы списка, до открытия любой формы).

**ДЕРЖАТЬ В СИНХРОНЕ вручную:** JS-версия (`CLIENT_ACTIONS.
recalc_full_name` в page.py) и Python-версия (`render_name_template` в
name_template.py) реализуют одну и ту же логику независимым кодом —
если в будущем добавится новый плейсхолдер или изменится правило
подстановки, поправить нужно ОБА места. Это сознательный компромисс
(нет второго рантайма JS на бэкенде, чтобы шарить код буквально) —
других calculation-подобных client_side-действий пока нет, но если
появятся — тот же риск разъезда будет для них тоже.

Серверный обработчик `_recalc_full_name_handler`/
`POST /api/calculation/{id}/actions/recalc_full_name` НЕ удалён,
остаётся зарегистрированным в `action_handlers` — просто кнопка формы
на него больше не ходит. Может пригодиться для будущего пакетного
пересчёта нескольких записей сразу.

Файлы: `app/engine/config.py` (`ActionButton.client_side`),
`app/engine/page.py` (`CLIENT_ACTIONS` JS-объект рядом с
`ENGINE_FORMULAS`, `runAction()` проверяет `CLIENT_ACTIONS` до
похода на сервер, рендер inline-кнопки/`render_action_buttons` не
делает кнопку `disabled`/`x-show="editing.id"` для `client_side`
действий), `app/engine/tables.py` (`recalc_full_name` теперь
`client_side=True`, label "Сформировать название", комментарий у
`_recalc_full_name_handler` обновлён).

**Проверено:** `/calculation-v2` рендерится без ошибок Jinja,
содержит `CLIENT_ACTIONS`/кнопку "Сформировать название"; создание
калькуляции с уже посчитанным на клиенте `full_name` в payload

## Сделано в этой сессии (2026-08-19/20, пятая часть — v53: настоящая причина 500 + формат номера R-000001)

**Настоящая причина 500 (скриншот — форма с уже подставленными R-2,
19.08.2026, все клиенты и бренды выбраны, всё равно 500):** `_ensure_
is_deleted_columns()` в `app/database.py` — единственный код, который
добавляет НОВЫЕ КОЛОНКИ в УЖЕ СУЩЕСТВУЮЩУЮ на Postgres-проде таблицу
(`SQLModel.metadata.create_all()` создаёт только целиком отсутствующие
таблицы — никогда не трогает уже развёрнутые). Таблица `request`
физически появилась на проде ещё в v49. Поля `document_number`/

подряд). На SQLite (все локальные тесты) это НИКОГДА не воспроизводится,
потому что тесты каждый раз создают таблицу с нуля через `create_all()`
— готовую сразу со всеми текущими полями модели, сценария "старая
таблица без новой колонки" просто не существует. Отсюда — три версии
подряд (v51, v52) уходили на прод с этим багом незамеченным, несмотря

**Проверено по-настоящему, не только "звучит логично":** SQLite не
даёт напрямую воспроизвести Postgres-специфичный сценарий, но сам
паттерн (существующая таблица без новой колонки → INSERT падает →

## Сделано в этой сессии (2026-08-19, третья часть — v51: баг с пустыми брендами + номер/дата заявки)

**Баг (скриншот от Вахтанга: "Сервер ответил 500: Internal Server Error"
при создании заявки без выбора бренда в слотах):** `openCreate()` во
фронте инициализировал ЛЮБОЕ незаполненное поле как `''` (пустая строка) —
для текстовых полей это нормально, но для relation-полей (select,
ссылка на другую таблицу — brand_slot_N_id, client_invoice_id) ни один
вариант `<select>` не соответствует `''`, физически нужен `null`.
На SQLite (локальные тесты) пустая строка в INTEGER-колонке молча
проходит, тип не проверяется — поэтому баг не поймался на этапе
разработки v49/v50. На проде (Postgres) это жёсткая ошибка на уровне
БД → 500 без понятного сообщения. Тот же класс проблемы задел и
`document_date` (новое date-поле, см. ниже) — конструктор модели падает
на пустой строке, только раньше на этапе валидации Pydantic, а не SQL.

**Исправлено в двух местах (защита в глубину, не только одна линия):**
1. Фронт (`openCreate()`) — relation-поля теперь инициализируются
   как `null`, не `''`. Так пустая строка вообще не возникает.
2. Бэкенд (`_normalize_relation_fields`/`_normalize_date_fields` в
   `api.py`, вызываются в create_item И update_item) — на случай, если
   `''` всё же придёт (старый кэш фронта на телефоне, прямой вызов API,
   будущие похожие поля) — relation-поля с `''` приводятся к `None`,
   date-поля с `''` удаляются из payload целиком (даёт сработать
   `default_factory` модели). Это ОБЩИЙ, переиспользуемый код движка,
   не хак под request — сработает для любой будущей таблицы с select
   или date-полем.

**Номер и дата документа (новая фича, обсуждена в этой сессии):**

  сам. При ЛЮБОМ сохранении (создание с номером от руки ИЛИ правка) —

## Сделано в предыдущей сессии (v45 — клик по всей строке kit открывает модалку, не только иконка ✎)

Вахтанг сообщил: на нижнем уровне дерева (список kit внутри раздела — например "Подключение 25а") тело строки на клик не реагировало вообще, единственный способ открыть модалку состава — точно попасть пальцем в маленькую иконку ✎. Просьба: "выбор можно было осуществить прямо непосредственно тапнув на позицию".

**Причина:** тело строки drill-list (`.drill-row-body`) было жёстко привязано к `drillOpen(item)` — методу, который умеет только углубляться в дерево на следующий уровень. Модалку по-прежнему можно было открыть, но только иконкой ✎, у которой маленькая область попадания.

**Исправление:** новый метод `rowClick(item)` — единая точка входа для клика по телу строки, сам решает, что делать: если у текущего уровня есть куда углубляться (`hasNextLevel`) — вызывает `drillOpen(item)` как раньше; если это нижний уровень без продолжения — вызывает `openEdit(item)`, открывая модалку напрямую. Иконка ✎ осталась на месте и работает как раньше (для явного визуального ориентира), но перестала быть единственным способом.

Файл: `app/engine/page.py` (новый метод `rowClick`, разметка `.drill-row-body` теперь вызывает его вместо `drillOpen` напрямую), `app/version.py` → v45.

Протестировано (TestClient): разметка `/kit_group-v2` содержит `rowClick(item)` на теле строки и правильную развилку `hasNextLevel` внутри метода; старая прямая привязка `@click="drillOpen(item)"` на теле строки отсутствует (не осталась дублирующим мёртвым кодом); иконка ✎ по-прежнему независимо вызывает `openEdit`; регресс всех остальных страниц движка — 200.

## Сделано в предыдущей сессии (v43 — MaterialPicker: фикс вёрстки, размеры, поведение поиска)

По итогам первого реального использования v42 на телефоне Вахтанг сообщил три проблемы:
1. Кнопка сохранения состава не видна вообще — "окно закрылось, нет доступа к интерфейсу".
2. Всё слишком мелкое, плохо видно.
3. Хотелось бы, чтобы интерфейс подбора материала выглядел и вёл себя как обычная плоская таблица.

**Причина проблемы 1 (найдена при разборе скриншотов):** `.picker-overlay` использовал `position: fixed; inset: 0`, что на практике равнозначно `height: 100vh`. На мобильных браузерах `100vh` больше видимой области экрана из-за адресной строки — реальная видимая высота меньше. Три flex-зоны (Отобрано/хендл/поиск) внутри занимали полные 100vh, footer с кнопками «Отмена»/«Сохранить состав» физически рендерился за пределами видимой области экрана — прокрутить к нему было нельзя, весь оверлей — не скроллящийся flex-column.

**Исправление:** `.picker-overlay` теперь `height: 100dvh` (dynamic viewport height — учитывает реальную видимую высоту, пересчитывается при появлении/скрытии адресной строки браузера). Footer сохранил `flex-shrink: 0`, стоит последним в DOM внутри flex-column — при нехватке места сжимаются зоны списка/поиска, а не футер.

**Увеличены размеры** по всему MaterialPicker: шрифт строк 14px → 16px, паддинги строк 10×16 → 16×20, кнопки +/- количества 30×30 → 40×40px, хендл-полоса 28px → 36px высотой и 48×5 → 56×6px сама полоска, кнопки футера получили увеличенный паддинг.

**Интерфейс поиска материалов приближен к обычной плоской таблице:**
- Список материалов теперь виден сразу при открытии MaterialPicker (`openMaterialPicker()` сразу вызывает `pickerSearch()` с пустым query — тот же `GET /api/material`, что и обычная таблица материалов на первой странице), а не только после того, как человек начал печатать.
- Визуальный стиль строки поиска и списка результатов приближен к `.search-input`/строкам обычной таблицы (те же паддинги, hover на строке, тот же радиус скругления инпута).

Файлы: `app/static/style.css` (переписан блок `.picker-*`), `app/engine/page.py` (`openMaterialPicker`/`pickerSearch` — список загружается сразу, пустое состояние результатов больше не завязано на наличие текста в поиске), `app/version.py` → v43.

Протестировано (TestClient): полный E2E создания kit + замены состава через `PUT /api/kit/{id}/items` по-прежнему проходит; страница `/kit_group-v2` рендерится и содержит `picker-footer`/`pickerSearch()` в разметке; CSS содержит `100dvh`-фикс и увеличенные размеры шрифта; регресс всех остальных страниц движка — 200. Визуальную вёрстку (реально ли кнопка теперь помещается на экране конкретного телефона) стоит проверить после деплоя — здесь возможности отрендерить страницу в реальном мобильном браузере нет, только через API/DOM-проверки наличия элементов и CSS-правил.

## Сделано в предыдущей сессии (v42 — MaterialPicker: полноэкранный подбор материалов для состава kit)

Контекст: v40/v41 оставляли добавление позиции состава через простую временную форму (select материала + количество) прямо внутри модалки kit — явно отложенная заглушка (см. предыдущие HANDOFF). Вахтанг прислал прототип UI подбора материала (bottom sheet с перетаскиваемой полосой между «Отобрано» и поиском) и попросил реализовать полноценный экран на его основе. Решения по UX согласованы заранее в переписке и записаны в `docs/HANDOFF_kits_and_calculation.md` (разделы 2.8–2.9) ДО начала кодирования — порядок работы был: сначала зафиксировать открытые вопросы (место открытия, поведение кнопок, дубликаты, диапазон хода полосы), потом код.

**Ключевые решения (см. HANDOFF_kits_and_calculation.md 2.8–2.9 для полного обоснования):**
- Модалка kit (список состава, только просмотр) остаётся как есть; кнопка «+ Добавить» переименована в **«Редактировать»**, старая форма select+количество внутри модалки полностью убрана.
- MaterialPicker — НЕ режим внутри той же модалки, а отдельный fullscreen-оверлей (`.picker-overlay`, `position: fixed; inset: 0`), открывается/закрывается поверх страницы без смены URL.
- При открытии — черновик (`pickerDraft`) сразу предзаполняется текущим составом kit (не начинается пустым).
- Все правки черновика — только в памяти экрана; `kit_item` на сервере не трогаются, пока не нажата финальная кнопка.
- Финальное сохранение — **полная замена**: `PUT /api/kit/{id}/items` удаляет весь прежний состав и создаёт новый из присланного списка, одной транзакцией. Осознанно не delta-сравнение — по прямому решению «можно смело переписывать всё».
- «Отмена» — черновик отбрасывается, ничего на сервере не меняется.
- Дубликаты `material_id` в черновике разрешены и сохраняются как отдельные строки (не суммируются) — у каждой строки черновика стабильный `_key`, не завязанный на `material_id`, для корректного `x-for`.
- Поиск материалов — переиспользует существующий плоский `GET /api/material?q=...`, без групп/дерева (drill-down по группам материалов на прототипе — сознательно отложенная будущая задача, категорий в справочнике материалов пока нет вообще).
- Перетаскиваемая полоса (`.picker-handle`) между зонами «Отобрано»/поиск: диапазон хода **15%–85%** высоты экрана (ни одна зона не схлопывается), хендл заметно толще обычной тонкой линии для надёжного захвата пальцем. Реализовано через pointer-события (`pointerdown`/`pointermove`/`pointerup` на `window`) — единый код для мыши и тача, `touch-action: none` на хендле, чтобы браузер не перехватывал жест как скролл страницы.

Валидирует каждую строку (`material_id` обязателен и должен существовать, `quantity` > 0) ДО удаления старого состава — чтобы при ошибке ничего не терять.    - Новый HTML-блок `.picker-overlay` вне `.modal-backdrop` — отдельный fullscreen-компонент с верхней/нижней зоной и полосой между ними, управляется тем же `enginePage()` Alpine-объектом (без отдельного `x-data`).

## Сделано в предыдущей сессии (v41 — выделение, копирование состава и пометка на удаление для kit)

Задача: групповое выделение комплектов (чекбокс, только на уровне kit) с двумя операциями — пометка/снятие пометки на удаление (уже работала generic-логика, нужно было только показать UI) и копирование ОДНОГО выделенного комплекта «один в один», включая весь состав (kit_item).

Согласованный UX копирования (обсуждалось отдельно, зафиксировано): копия создаётся на сервере СРАЗУ, целиком, с тем же названием, что и оригинал — никакого промежуточного диалога подтверждения ДО создания копии в БД нет. Сразу после копирования модалка открывается автоматически на новой записи (как обычный `openEdit`) — пользователь видит список состава (уже скопированного) и переименовывает комплект через иконку ✎ как обычную запись, когда сочтёт нужным. Это сознательно проще, чем изначально обсуждавшийся вариант «сначала подтвердить/переименовать, потом сохранить» — технически он потребовал бы отдельного промежуточного состояния модалки только ради одного шага, который пользователь и так может сделать сразу после (открыть ту же запись и переименовать).

1. **`app/engine/api.py`** — новый эндпоинт `POST /api/{key}/{item_id}/copy`, generic (не хардкод под kit): работает для любой таблицы с `edit_mode="items_modal"` (сейчас единственная такая — kit). Копирует саму запись (все поля модели, без id, `is_deleted` сброшен в `False`, если `delete_mode="soft"`) и ВСЕ дочерние записи `items_source_table_key` (для kit — kit_item), одной транзакцией (`session.flush()` для получения `new_instance.id` до коммита, чтобы проставить его копиям дочерних строк). ## Сделано в предыдущей сессии (v38.1 — hotfix: навигация проваливалась в несуществующий уровень)

Обнаружено на устройстве сразу после v38 (скриншот): открыв группу → раздел («Группы › Подключение оборудования › Модульные автоматы»), внутри показывались НАЗВАНИЯ ГРУПП («Установка оборудования», «Подключение оборудования») вместо ожидаемого пустого списка комплектов. Причина: `currentLevel()` имел фоллбэк `LEVELS[this.drillPath.length] || LEVELS[0]` — когда `drillPath.length` выходил за границы `LEVELS` (2 элемента: kit_group, kit_section — `kit` ещё не реализован), тихо откатывался на `LEVELS[0]` (группы) вместо явной защиты. А защиты от самого выхода за границы не было: стрелка `›` в строке и `drillOpen()` проверяли только `hierarchy.childKey` из конфига (у kit_section он заполнен — `"kit"`, т.к. дерево концептуально трёхуровневое), не проверяя, существует ли этот уровень РЕАЛЬНО в `LEVELS`.

1. **`currentLevel()`** — фоллбэк `|| LEVELS[0]` убран. Теперь при некорректном `drillPath` метод вернул бы `undefined` вместо того чтобы маскировать баг постановкой не относящихся к узлу данных.
2. **Новый геттер `hasNextLevel`** — единое место истины: `true` только если и `childKey` задан в конфиге текущего уровня, И `LEVELS[drillPath.length + 1]` реально существует. Используется и для стрелки `›` в строке, и в `drillOpen()` (заменил прежнюю неполную проверку) — раньше условие дублировалось в двух местах по-разному, теперь один источник.
3. **Иконка ✎** — размер увеличен (15px → 22px), зона нажатия расширена через padding+отрицательный margin (визуальный размер строки не меняется, но фактическая кликабельная область больше) — по прямому запросу с фото («слишком маленькая, нужно увеличить то поле на которое надо тыкать»).
4. Тело строки (`drill-row-body`) теперь получает `cursor: pointer` только когда `hasNextLevel` истинно — на последнем реально существующем уровне (сейчас это kit_section) курсор больше не обещает переход, которого не будет.

В v28 поле убрали из модели `Material` (ставка стала общей, живёт в `constants`), но колонку в уже существующей таблице никто не дропнул — `SQLModel.metadata.create_all()` создаёт только отсутствующие таблицы целиком, лишние колонки в существующих не трогает. Из-за этого падал ЛЮБОЙ `INSERT` в `material`, не только копирование. Диагностировано по логам Railway (Deploy Logs): `psycopg2.errors.NotNullViolation: null value in column "vat_rate" of relation "material" violates not-null constraint`.
   - Добавлена `_drop_obsolete_columns()` в `app/database.py`, вызывается в `init_db()` рядом с `_ensure_is_deleted_columns()`. Дропает `material.vat_rate` через `ALTER TABLE ... DROP COLUMN IF EXISTS` — идемпотентно. Симметричный механизм к `_ensure_is_deleted_columns()` (тот добавляет недостающие колонки, этот убирает лишние) — при появлении будущих устаревших колонок достаточно добавить строку в список `obsolete`.
4. Фронт (JS) не округляет `price_vb_incl_vat` дополнительно — бэкенд гарантированно округляет всё при `save()`.
5. **Компактная вёрстка блока цен, по дополнительной правке в этой же сессии:**
   - **`vat_rate` убран из формы через `in_form=False`** (новый флаг у `FieldConfig`, поддерживался и раньше, но не использовался). Поле остаётся `virtual=True` с `source_constant_key="vat_rate"` — по-прежнему участвует в `ComputedPair.rate_constant_key`, по-прежнему видно как колонка списка материалов. Меняется только видимость в форме.
   - **Ставка НДС показывается прямо в лейбле «Цена с НДС»** — «Цена с НДС (20%)». Механизм в `page.py` универсальный: для поля, которое является `field_b` в `computed_pair` со `rate_constant_key`, лейбл рендерится с `x-text="constants[...]"` вместо статичного текста — сработает для любой будущей таблицы движка с аналогичной парой цена/ставка, без правок `page.py`.
   - **Все три денежных поля материала — один `FormRow`, ширина каждого — `100px`** (`price_excl_vat`, `price_incl_vat`, `price_vb_incl_vat`). Отдельный `FormRow` под `price_vb_incl_vat` убран.

**Важно для следующей сессии:** при первом деплое этого архива на Railway произойдёт настоящий `DROP COLUMN vat_rate` на боевой таблице `material` — ожидаемо и безопасно (колонка не используется кодом с v28), но стоит проверить деплой success и что создание/копирование материала в проде реально работает, прежде чем считать баг закрытым.

## Сделано в предыдущей сессии (v33 — копирование строки)

Контекст: нужна была возможность быстро создать похожую позицию (как в 1С — встал на строку, скопировал). Первая идея (маленькая пиктограмма «⎘» в каждой строке списка) была отклонена в процессе обсуждения — на телефоне легко промахнуться по маленькой кнопке в узкой строке. Вместо этого выбран механизм «выделение чекбоксом + панель действий над списком» — тот же паттерн, который в будущем даст groupdelete и другие массовые операции без переделки.

1. **Чекбоксы в начале каждой строки** (первая колонка, видна только когда `TableConfig.allow_create=True` — копировать в таблицу, где создание запрещено, бессмысленно; сейчас это исключает только `constant_table`). Клик по чекбоксу не открывает форму редактирования (`@click.stop` на ячейке).
2. **Панель выделения** (`.selection-bar`) — появляется над списком только когда есть хотя бы одна выделенная строка, показывает счётчик «N выделено», кнопку «Копировать» и «Снять выделение».
3. **«Копировать» активна только при РОВНО одном выделенном элементе** — при 0 или 2+ кнопка задизейблена (`:disabled`). Сознательное решение: групповое копирование нескольких строк сразу — не то поведение, которое нужно (человек, как правило, что-то меняет перед сохранением копии, а не штампует дубликаты пачкой).
4. **`copySelected()`**: находит выделенный item в уже загруженном списке, открывает обычную модалку редактирования, предзаполненную его данными, но без `id` и с `is_deleted=false`. Дальше — обычный путь: `save()` видит отсутствие `id` → шлёт `POST` (создание), а не `PUT`. Все поля копируются как есть, включая `sku_article` — человек правит вручную перед сохранением (осознанное решение, не очищать артикул автоматически).
5. **`selectedIds` сбрасывается при каждой перезагрузке списка** (`load()`) — смена страницы/поиска/фильтра/сортировки может увести выделенные id с экрана, панель не должна показывать "выделено N" для невидимых строк.
6. Никаких изменений API — копирование целиком на фронте поверх уже существующего `POST /api/{key}`.

Протестировано (TestClient, SQLite): разметка чекбоксов/панели присутствует на материалах и брендах, отсутствует на константах (`allow_create=False`); полный сценарий копирования материала — копия получает новый `id`, независима от оригинала, все поля (включая артикул) скопированы как есть, оригинал не затронут, обе записи существуют одновременно; регресс create/list/delete-toggle/пагинации/сортировки — не сломан.

## Сделано в этой сессии (v31 — пагинация списков)

1. **`GET /api/{key}` возвращает объект вместо голого массива.** Было: `[...]`. Стало: `{"items": [...], "total": N, "page": N, "page_size": N, "total_pages": N}`. Это ломающее изменение формата ответа — обновлены ВСЕ места фронта, которые дёргают `/api/{key}` (основной список, `relationOptions`, подгрузка `constants{}` в `init()`).
2. **Новые query-параметры:** `page` (1-based, по умолчанию 1, отрицательные/за пределами общего числа страниц — зажимается до валидного диапазона) и `page_size` (если не передан — берётся `default_page_size` из справочника constants; если передан явно — приоритетнее константы). Явный `page_size` используется для служебных запросов, которым нужен весь список целиком без пагинации (например `relationOptions` для фильтров/выпадающих списков — передают `page_size=1000`).
3. **`total` считается ДО применения LIMIT/OFFSET** — по тому же statement, с учётом активного поиска/фильтра, чтобы «Стр. X из Y» не врало при активном поиске.
4. **UI:** блок пагинации под таблицей — «‹ Назад / Стр. X из Y / Далее ›», кнопки дизейблятся на первой/последней странице, блок скрыт целиком, если страниц ≤ 1.
5. **Сброс на 1-ю страницу** при изменении поискового запроса, чекбоксов полей поиска, клике по фильтру-чипу, клике по сортируемому заголовку колонки — везде, где меняется набор данных, страница явно сбрасывается в `page=1` перед `load()`. Клик «Назад»/«Далее» не сбрасывает — только двигает `page`.

Протестировано (TestClient, SQLite): 25 материалов, `page_size=10` → 3 страницы (10/10/5), `page=99` зажимается до последней валидной страницы, `page_size=1000` возвращает всё на одной странице (сценарий `relationOptions`), запрос без `page_size` берёт `default_page_size=100` из constants, `/api/constant` тоже отдаёт новый формат `{items,...}`, поиск + пагинация вместе — `total` отражает именно отфильтрованное количество, а не общее.

⚠️ Побочно обнаружено (не связано с пагинацией, существовало и раньше): на SQLite (только тестовое окружение) `LOWER()` не обрабатывает кириллицу регистронезависимо — поиск/сортировка по русским полям в TestClient-тестах может давать 0 совпадений, хотя на Postgres (Railway, продакшен) `LOWER()` с кириллицей работает корректно. При написании будущих тестов с поиском по тексту — либо проверять на латинице/цифрах, либо не полагаться на регистронезависимость кириллицы в SQLite-тестах.

**Решено в сессии v35 (зафиксировано, не поднимать заново без причины):**
- Групповая пометка/снятие пометки на удаление — БЕЗУСЛОВНАЯ установка статуса (`is_deleted = value` для всех выделенных), не toggle. Если среди выделенных уже есть позиция в нужном статусе — просто перезаписывается тем же значением, не переключается обратно. Это отличает групповую операцию от одиночной кнопки в модалке (та — toggle).
- Кнопки «Пометить на удаление» / «Снять пометку» активны при любом количестве выделенных строк (не требуют ровно одну, в отличие от «Копировать»).
- Селект в bulk-эндпоинте: `soft_delete=False` таблицы (сейчас только `constant`) получают 422; у `constant` панели выделения нет вовсе, т.к. `allow_create=False`.
- Инфраструктура выделения по-прежнему рассчитана на дальнейшие групповые операции (следующая по списку — массовое изменение поля, например бренда у нескольких материалов разом) — расширять панель когда появится конкретная следующая операция.

**Решено в сессии v34 (зафиксировано, не поднимать заново без причины):**
- Правило округления НДС по украинскому законодательству проверено: специальное «округление до целой гривны» действует только для налоговой декларации по НДС (отдельная форма, подаётся в налоговую), не для рабочих документов приложения. На уровне цен/счетов/накладных достаточно обычного округления до 2 знаков (копеек) — без спецлогики. Если в будущем понадобится модуль именно налоговой отчётности — там потребуется отдельное округление до целых гривен, закладывать заранее не стали.
- Округление до 2 знаков — универсальное правило для ЛЮБОГО `FieldConfig.is_numeric=True` поля движка (не только для полей внутри `computed_pairs`), применяется в `api.py` при `create`/`update`.

**Решено в сессии v31 (зафиксировано, не поднимать заново без причины):**
- Пагинация — классические кнопки «Назад/Далее» с номером страницы («Стр. X из Y»), не бесконечная прокрутка. Размер страницы — из `default_page_size` в constants по умолчанию, но конкретный запрос может передать свой `page_size` явно (используется для `relationOptions`/фильтров, которым нужен весь список).
- Формат ответа `GET /api/{key}` изменён с массива на объект `{items, total, page, page_size, total_pages}` — если в будущем понадобится новый потребитель этого API, учитывать новый формат.

**Решено в сессии v32 (зафиксировано, не поднимать заново без причины):**
- Курс поставщика ("ВБ") считается в калькуляции "на лету" (вариант Б), а не пересчитывается и не сохраняется в TMC заранее (вариант А был отклонён — цена протухала бы при каждом изменении курса бренда, как раньше было с НДС до v28).
- Валюта поставщика (EUR/USD/др.) НЕ хранится отдельным полем — сознательно, для расчёта неважно какая именно валюта, только цифры (курс и цена в валюте).
- Курс бренда (`rate_vb`) правится вручную в форме, без интеграции с внешним источником курсов — как и было решено для первой итерации.
- Названия полей в БД/коде: `Brand.rate_vb`, `Material.price_vb_incl_vat`. Подписи в UI: «Курс ВБ», «Цена с НДС ВБ».

**Решено в сессии v33 (зафиксировано, не поднимать заново без причины):**
- Копирование строки реализовано через выделение чекбоксом (не через маленькую пиктограмму в строке — на телефоне легко промахнуться) + кнопка «Копировать» в панели над списком. Активна только при ровно одном выделенном элементе — групповое копирование нескольких строк сразу сознательно не делали.
- Инфраструктура выделения (`selectedIds`, `.selection-bar`, чекбоксы в строках) — рассчитана на будущие групповые операции (bulk soft-delete, массовое изменение поля типа бренда у нескольких материалов разом), но сейчас реализовано только копирование. Расширять панель новыми кнопками — когда появится конкретная следующая массовая операция, не заранее.
- Копия получает новый `id`, `is_deleted` копии всегда `false`, остальные поля (включая `sku_article`) копируются как есть без очистки — человек правит вручную перед сохранением.

**Обсуждались, но НЕ реализованы (обдумать порядок отдельно, не начинать без явного решения):**
