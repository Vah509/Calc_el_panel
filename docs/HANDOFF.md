# HANDOFF

## Состояние

Работает: универсальный CRUD-движок (`app/engine/`), раздел «Обработки» (`app/processors/`). Активные страницы: `/material-v2`, `/brand-v2`, `/constant-v2`, `/processors`. Верхнее меню — «Справочники» (Материалы/Бренды/Константы) и «Обработки» (Пересчёты).

Последнее изменение: v28 — НДС у материалов теперь только из constants (живая ссылка, поле в модели удалено), + универсальный bulk-recalculate обработчик, первая функция — пересчёт НДС материалов.

## Сделано в этой сессии (v28 — НДС из constants + bulk-recalculate)

1. **`Material.vat_rate` удалено из модели.** Ставка НДС больше не хранится per-material — общая для всех, живёт только в `constants` (ключ `vat_rate`). ⚠️ Колонка `vat_rate` физически ОСТАЁТСЯ в таблице `material` на Railway (Postgres) — просто больше не используется приложением. Договорились: физическое удаление колонки (`ALTER TABLE ... DROP COLUMN`) — отдельным шагом ПОСЛЕ того, как через bulk-recalculate пересчитают реальные данные и убедятся, что всё корректно.
2. **`FieldConfig` расширен:** `virtual: bool` + `source_constant_key: Optional[str]` — поле не хранится в модели/БД вообще (исключено из `TableConfig.field_names()`), значение подтягивается на фронте отдельным запросом к `/api/constant` и показывается как readonly. Используется для `vat_rate` в форме и списке материалов.
3. **`ComputedPair` расширен:** `rate_constant_key: Optional[str]` — если задан, ставка для пересчёта берётся не из поля записи (`rate_field`), а из справочника constants. И бэкенд (`api.py _apply_computed_pairs`, теперь принимает `session`), и фронт (JS `onComputedChange`/`validateBeforeSave`, новый объект `constants{}` в Alpine state, подгружается в `init()`) читают ставку из constants одинаково.
4. **Универсальный bulk-recalculate обработчик** (`app/processors/`): реестр `Processor` (key, table_key, label, run-функция) + страница `/processors` (выбор таблицы → радио-кнопки функций → «Выполнить») + API `POST /api/processors/{key}/run`. Первая функция — `recalc_material_vat`: пересчитывает `price_incl_vat` всех материалов по актуальной ставке из constants, `price_excl_vat` — источник истины, не трогается. Идемпотентна (повторный запуск ничего не меняет, если ставка не менялась). Раздел «Обработки» в меню теперь ведёт на `/processors` (было пусто).
5. `register_engine_tables()` теперь возвращает `Jinja2Templates` наружу — `main.py` переиспользует то же окружение (с уже настроенными `APP_VERSION`/`NAV_MENU` globals) для регистрации `/processors`, вместо создания второго `Jinja2Templates`.

Протестировано: создание материала без vat_rate пересчитывает `price_incl_vat` по ставке из constants; смена ставки в constants сразу видна в карточке материала как readonly; изменение цены материала после смены ставки пересчитывает по НОВОЙ ставке; при ставке 0 — понятная 422-ошибка; bulk-обработчик находит и обновляет только реально устаревшие записи, повторный запуск идемпотентен; все старые страницы (`material-v2`, `brand-v2`, `constant-v2`) не задеты.

## Сделано в предыдущей сессии (v27 — навигация)

1. `app/version.py` — новый модуль: `APP_VERSION` и `NAV_MENU` (список разделов, у каждого `title` + `links`). Раньше версия была захардкожена прямо в `main.py` и в `base.html` по отдельности (расходились). Теперь одна точка правды.
2. `app/engine/register.py` — прокидывает `APP_VERSION`/`NAV_MENU` в `templates.env.globals`, доступны во всех шаблонах движка автоматически, без передачи вручную в каждый рендер.
3. `base.html` — меню теперь `{% for section in NAV_MENU %}` с выпадающей панелью на чистом CSS (`:hover` для десктопа, `:focus-within` + `tabindex="0"` для тапа на мобильном — без JS).
4. ⚠️ Грабли: поле раздела меню называется `links`, не `items` — `section.items` в Jinja резолвится в builtin `dict.items()` метод, а не в наш ключ словаря, ломает рендер молча (TypeError на iteration). Проверено на практике, обойдено переименованием поля.
5. Константы (`/constant-v2`) теперь доступны из меню — в прошлом шаге страница была создана, но ссылки нигде не было.

Протестировано: все три страницы движка отдают 200, содержат `v27`, оба раздела меню, пункт «Константы», плейсхолдер «Пока пусто» для Обработок. Старые API не задеты.

## Сделано в предыдущей сессии (v26 — constants)

1. Модель `Constant` (`app/models/constant.py`): `id`, `key` (unique), `value` (строка, тип приводится в коде при использовании), `description`.
2. `seed_constants()` в `app/database.py` — идемпотентный seed при старте: `vat_rate=20`, `default_page_size=100`. Вызывается в `on_startup` после `init_db()`. Проверено: повторный старт не дублирует и не перезаписывает изменённые значения.
3. Движок расширен минимально под нужды constants:
   - `FieldConfig.readonly: bool` — поле рендерится в форме как текст, не input; на бэкенде `update_item` игнорирует readonly-поля, даже если их прислать напрямую в API.
   - `TableConfig.allow_create` / `allow_delete: bool` — кнопки "+ Добавить" / "Удалить" скрываются в UI, POST/DELETE эндпоинты возвращают 422.
4. `constant_table` в `tables.py`: `key` — readonly, searchable; `value` — редактируемое; `description` — readonly, только в списке (`in_form=False`). `allow_create=False`, `allow_delete=False` (набор ключей фиксирован, задаётся только seed'ом).
5. CSS: `.field-readonly-text` для отображения readonly-полей в форме.

Протестировано локально через TestClient: seed идемпотентен, `value` редактируется, `key` защищён от изменения и на фронте, и на бэкенде, create/delete запрещены (422), старые таблицы material/brand не затронуты, HTML-страница `/constant-v2` рендерится корректно.
