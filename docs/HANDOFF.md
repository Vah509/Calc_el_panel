# HANDOFF

## Состояние

**v103 — каскадное физическое удаление для обработчиков "Обработки".**

Раздел "Обработки" уже содержал универсальные `purge_<table_key>`
обработчики (физическое удаление строк с `is_deleted=True`) для
каждой soft-delete таблицы движка. Они удаляли только строки самой
таблицы, без учёта дочерних записей (например `invoice_item` при
удалении `invoice`) — на Postgres это привело бы к ошибке нарушения
внешнего ключа. Теперь обработчики удаляют шапку документа вместе со
всей её начинкой (решение Вахтанга: "если документ удаляется, то все
записи автоматически удаляются — шапка документа и все подчинённые,
то есть начинка тоже").

## Сделано в этой сессии

1. **`app/processors/registry.py`**:
   - Добавлена `_delete_children_recursive()` — по `Hierarchy.parent_key`
     (см. `app/engine/tables.py`) рекурсивно находит все TableConfig,
     чьи записи ссылаются на удаляемую таблицу, и удаляет их строки
     ПЕРЕД удалением родителя (сначала внуки, потом дети — порядок
     важен из-за FK). Работает для любой глубины вложенности, не
     только `invoice -> invoice_item`.
   - `_make_purge_processor()` переписан: теперь вызывает
     `_delete_children_recursive()` для id всех помеченных строк
     перед их собственным удалением. Дочерние строки удаляются вне
     зависимости от их собственного `is_deleted` — они следуют за
     шапкой.
   - Отчёт (`ProcessorResult.message`) теперь показывает отдельно
     количество удалённых родительских записей и количество
     удалённых подчинённых, если такие были.
2. **`app/version.py`** — `APP_VERSION` v102 → v103.
3. Проверено локально (SQLite, `TestClient` context manager):
   - Счёт с 2 строками `InvoiceItem`, `is_deleted=True` →
     `purge_invoice` удаляет и счёт, и обе строки; сообщение
     корректно показывает "1 записей... вместе с ними 2 подчинённых".
   - Второй счёт без пометки — не тронут, его строка тоже осталась.
   - Все существующие `purge_*` (`brand`, `material`, `kit`, `client`,
     `request`, `calculation`, `product_type_rate`, `specification`,
     `firm`, `invoice`) по-прежнему строятся без ошибок.
   - `kit_group`/`kit_section` намеренно `delete_mode="simple"` (не
     soft-delete) — для них `purge_*` не создаётся, это не связано
     с этой правкой, поведение сохранено как было.

## Открыто

- Второй проход зачистки Specification (DROP таблиц/полей) — весь
  чек-лист и открытые вопросы в `docs/HANDOFF_specification_cleanup.md`.
  Ключевой вопрос: что делать с 3-4 старыми счетами, у которых
  `specification_id` заполнен, прежде чем можно будет убрать таблицы.
- Рефакторинг `enginePage()` — отдельная будущая сессия, не входит
  сюда.
- Обработчики `purge_*` пока без проверки зависимостей ВНЕ дерева
  иерархии (например, ссылается ли что-то постороннее на удаляемую
  запись, не через `Hierarchy`) — отложено до реальной потребности.
