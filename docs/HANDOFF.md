# HANDOFF

## Состояние

Работает: универсальный CRUD-движок (`app/engine/`), раздел «Обработки» (`app/processors/`), soft-delete у материалов, брендов, клиентов и заявок. Активные страницы: `/material-v2`, `/brand-v2`, `/client-v2`, `/request-v2`, `/kit_group-v2` (drill-down дерево, 3 уровня: Группы → Разделы → Комплекты), `/constant-v2`, `/processors`. Верхнее меню — «Документы» (Заявки), «Справочники» (Материалы/Бренды/Клиенты/Группы комплектов/Константы) и «Обработки» (Пересчёты + физическое удаление). `/kit_section-v2`, `/kit-v2`, `/kit_item-v2` — заглушки на случай прямого перехода по URL, отдельных пунктов меню на них нет.

`request` (заявка) — первый документ цепочки zayavka → calculation → specification → invoice. Плоская таблица (`hierarchy=None`), значит CRUD/soft-delete/copy/bulk-mark-delete/purge работают "бесплатно" через стандартный движок без единой строчки специального кода. Раскладка карточки (v50/v51): номер+дата в одном ряду сверху; клиенты — каждый на всю ширину отдельным рядом; у каждого из трёх брендовых слотов — своя строка с select + пара кнопок-заглушек «Спецификация»/«Пересчитать» рядом (`FieldConfig.row_actions`), общей кнопки «Пересчитать всё» нет. Номер документа (v51) — редактируемый вручную, автогенерируется по счётчику префикса "R" при создании (`TableConfig.document_prefix`/`document_number_field`, механика в `app/engine/document_numbering.py`, счётчики — `DocumentCounter`), номер теперь виден СРАЗУ на форме "Новая запись" (v52, `GET /api/{key}/next-document-number` — предпросмотр без резервирования) — переиспользуемо для будущих документов (calculation/specification/invoice), у каждого будет свой префикс. Поиск (v52) — по клиенту (заказчик/для счёта, переключаемые чекбоксы), через join/подзапрос на `client` (`Relation.searchable_fields`), НЕ через ряд чипов-фильтров — у request все 5 relation-полей получили `show_filter_chips=False` (5 рядов чипов на телефоне были захламлены).

Движок объединён: один `TableConfig` описывает и плоские таблицы (material, brand — `hierarchy=None`), и узлы дерева drill-down (kit_group, kit_section, kit — `hierarchy` заполнен). `delete_mode` — три режима: `"hard"` (kit_item — на неё ничего не ссылается, удаление позиции состава всегда безусловное и немедленное), `"soft"` (material/brand/kit — пометка + purge-processor), `"simple"` (kit_group/kit_section — физическое удаление, но только если нет дочерних записей).

`kit` — 3-й, нижний уровень дерева drill-down. Клик по комплекту в списке открывает МОДАЛЬНОЕ ОКНО со списком состава (`kit_item` — материал+количество, только просмотр). Кнопка «Редактировать» в этой модалке открывает **MaterialPicker** — отдельный полноэкранный экран (bottom sheet: «Отобрано» + перетаскиваемая полоса + поиск материалов), где человек правит черновик состава целиком (добавляет через поиск, меняет количество, удаляет), а по кнопке «Сохранить состав» весь прежний состав на сервере заменяется черновиком одной транзакцией (`PUT /api/kit/{id}/items`). «Отмена» — черновик отбрасывается, ничего на сервере не меняется. Дубликаты material_id в составе разрешены (не суммируются). Переименование самого комплекта — через отдельную иконку ✎ в строке drill-list.

Уровень kit поддерживает выделение чекбоксом + групповые операции (пометка/снятие пометки на удаление, копирование ОДНОГО выделенного комплекта со всем составом). kit_group/kit_section выделения не имеют.

Тема «Комплекты» (kit) ЗАВЕРШЕНА (v42-v48). Тема «Заявка» (request) —
БАЗОВАЯ ВЕРСИЯ ЗАВЕРШЕНА (v49): справочник client + документ request,
CRUD/soft-delete/copy/purge через стандартный движок, кнопки формирования
спецификации и общего пересчёта — видимые, но неактивные заглушки
(`TableConfig.extra_actions`), т.к. реальная логика зависит от calculation,

## Сделано в этой сессии (2026-08-19, четвёртая часть — v52: номер/дата не появлялись + чипы фильтров → текстовый поиск по клиенту)

**Баг 1 — номер и дата не появлялись при открытии формы "Новая запись"
(первый скриншот):** причина — в движке ДВА разных JS-массива описания
полей таблицы: `fields` (использует `openCreate()` для заполнения бланка
новой записи) и `formLayoutFields` (использует только рендер формы в
шаблоне). Ключ `"widget"` присутствовал только во втором — значит
`f.widget === 'date'` в `openCreate()` ВСЕГДА было `undefined === 'date'`
→ `false`, автоподстановка сегодняшней даты никогда не срабатывала.
Добавлен `"widget"` в первый массив тоже (`_serialize_level_config`
в page.py) — универсальный фикс, касается любого будущего date-поля
у любой таблицы, не только request.

**Дополнительно к бага 1 — номер документа теперь виден СРАЗУ на форме,
а не только после сохранения:** раньше `document_number` намеренно
оставлялся пустым на фронте и генерировался только на save — с точки
зрения Вахтанга это выглядело как несделанная фича ("номер должен быть
заполнен, если я создаю новую заявку"). Добавлен отдельный read-only
эндпоинт `GET /api/{key}/next-document-number` — ПОКАЗЫВАЕТ, каким будет
следующий номер, НЕ трогая счётчик (не резервирует, только подсказка).
`openCreate()` стал `async`, вызывает этот эндпоинт при открытии формы
для любой таблицы с `document_prefix` — заполняет поле номера сразу.
Реальный номер всё равно присваивается на save обычным путём
(`_apply_document_numbering`) — если между открытием формы и
сохранением кто-то успеет создать другой документ, возможно небольшое
расхождение с тем, что было показано (у Вахтанга единственный
пользователь, риск практически нулевой, задокументировано в коде).

**Баг/UX 2 — 5 рядов чипов-фильтров у заявки (второй скриншот, "фильтры
по брендам не нужны"):** движок рендерил ряд чипов "Все + одна кнопка
на значение" ДЛЯ КАЖДОГО relation-поля таблицы безусловно — раньше не
было заметно, потому что ни у одной существующей таблицы не было больше
одного relation-поля разом. У request их 5 (2 клиента + 3 бренда) — 5
рядов чипов выглядели захламлённо. Решение:
- Новый флаг `Relation.show_filter_chips: bool = True` — у ВСЕХ 5
  relation-полей request выставлен в `False`, ряд чипов для них больше
  не рендерится (остальные таблицы не затронуты — дефолт сохраняет
  прежнее поведение).
- Вместо чипов — обычный текстовый поиск (как у client), но НЕ по
  собственному текстовому полю (у request таких для клиента нет — это
  FK), а ПО СВЯЗАННОЙ таблице через join/подзапрос: новое поле
  `Relation.searchable_fields: list[str]` (например `client_id` →
  `["short_name", "full_name"]` клиента). Переключаемые чекбоксы —
  тот же паттерн, что и обычные текстовые searchable-поля
  (`enable_search_toggles`), но с namespaced-ключом `"rel:{field}"`,
  чтобы не столкнуться по имени с обычными полями. У request: чекбокс
  "Клиент (заказчик)" (по умолчанию включён) и "Клиент (для счёта)"
  (по умолчанию выключен) — Вахтанг подтвердил именно радиопереключатель/
  чекбоксы, не единое поле поиска без выбора.
- Backend: `list_items` в api.py строит подзапрос `SELECT id FROM client
  WHERE lower(short_name) LIKE ... OR lower(full_name) LIKE ...` и
  фильтрует `request.client_id IN (подзапрос)` — комбинируется через OR
  с обычными text-conditions и с другими активными relation-поисками.
  Резолвит `target_table` в модель через `ALL_TABLES` (тот же паттерн,
  что уже использовался для hierarchy/items_modal в этом файле).

**Новое в движке (оба пункта переиспользуемы, не хаки под request):**
`FieldConfig`/`_serialize_level_config` — "widget" теперь и в `fields`,
не только в `formLayoutFields`. `TableConfig.document_number_field`/
`document_prefix` теперь дают ещё и `GET /{key}/next-document-number`
автоматически — работает для любой будущей таблицы с этими двумя

и `Relation.searchable_fields`/`search_toggle`/`search_default`/
`search_label` — новые опциональные поля Relation, применимы к любой
будущей таблице с несколькими relation-полями (calculation, когда
дойдём — тоже, скорее всего, получит текстовый поиск по клиенту заявки
таким же способом, а не свои чипы).

## Сделано в этой сессии (2026-08-19, третья часть — v51: баг с пустыми брендами + номер/дата заявки)

**Баг (скриншот от Вахтанга: "Сервер ответил 500: Internal Server Error"
при создании заявки без выбора бренда в слотах):** `openCreate()` во
фронте инициализировал ЛЮБОЕ незаполненное поле как `''` (пустая строка) —
для текстовых полей это нормально, но для relation-полей (select,
ссылка на другую таблицу — brand_slot_N_id, client_invoice_id) ни один
вариант `<select>` не соответствует `''`, физически нужен `null`.
На SQLite (локальные тесты) пустая строка в INTEGER-колонке молча
проходит, тип не проверяется — поэтому баг не поймался на этапе
разработки v49/v50. На проде (Postgres) это жёсткая ошибка на уровне
БД → 500 без понятного сообщения. Тот же класс проблемы задел и
`document_date` (новое date-поле, см. ниже) — конструктор модели падает
на пустой строке, только раньше на этапе валидации Pydantic, а не SQL.

**Исправлено в двух местах (защита в глубину, не только одна линия):**
1. Фронт (`openCreate()`) — relation-поля теперь инициализируются
   как `null`, не `''`. Так пустая строка вообще не возникает.
2. Бэкенд (`_normalize_relation_fields`/`_normalize_date_fields` в
   `api.py`, вызываются в create_item И update_item) — на случай, если
   `''` всё же придёт (старый кэш фронта на телефоне, прямой вызов API,
   будущие похожие поля) — relation-поля с `''` приводятся к `None`,
   date-поля с `''` удаляются из payload целиком (даёт сработать
   `default_factory` модели). Это ОБЩИЙ, переиспользуемый код движка,
   не хак под request — сработает для любой будущей таблицы с select
   или date-полем.

**Номер и дата документа (новая фича, обсуждена в этой сессии):**
- `Request.document_number` (str, редактируемый) и `Request.document_date`
  (date, редактируемый, `default_factory=date.today`) — новые поля модели.
- Правила (согласованы с Вахтангом): номер редактируется вручную,
  ДУБЛИКАТЫ НЕ ПРОВЕРЯЮТСЯ (можно вписать любой, даже уже занятый).
  При создании без явного номера — сервер генерирует `"{префикс}-{n}"`
  сам. При ЛЮБОМ сохранении (создание с номером от руки ИЛИ правка) —
  если число в номере больше текущего счётчика префикса, счётчик сам
  подтягивается вверх до этого числа (только вверх, никогда не назад
  из-за правки). Дата — при создании без явной даты подставляется
  сегодняшняя, дальше свободно редактируется.
- **Новое в движке (переиспользуемо для будущих calculation/specification/
  invoice, у каждого будет свой префикс):**
  - `app/models/document_counter.py` — `DocumentCounter(prefix, last_number)`,
    отдельная таблица-счётчик, НЕ таблица движка (нет своего TableConfig/
    страницы, не в ALL_TABLES, только импортирована в tables.py ради
    `SQLModel.metadata.create_all()`).
  - `app/engine/document_numbering.py` — `next_document_number()` (продвигает
    счётчик на 1, отдаёт готовый номер) и `bump_counter_if_ahead()`
    (подтягивает счётчик вверх, если распознанное число в номере больше
    текущего last_number; не распознало число — тихо ничего не делает,
    не роняет сохранение).
  - `TableConfig.document_number_field`/`document_prefix` — опционально у
    любой таблицы; `_apply_document_numbering()` в api.py вызывает
    numbering-хелперы, только если оба заданы — для остальных таблиц
    (brand/material/client) не делает ничего.
  - `FieldConfig.widget="date"` — новый тип виджета (был только
    text/number/select), рендерится как `<input type="date">`, отдельная
    ветка в `openCreate()` подставляет сегодняшнюю дату на фронте сразу
    при открытии формы (не дожидаясь ответа сервера).
- `request_table`: добавлены поля `document_number`/`document_date` в
  начале формы, один `FormRow` их группирует в общий ряд (единственная
  оставшаяся группировка — остальные поля по-прежнему каждое в своём ряду,
  см. v50). Список заявок теперь тоже показывает номер и дату (list_width
  90px/110px).

## Сделано в предыдущей сессии (v43 — MaterialPicker: фикс вёрстки, размеры, поведение поиска)

По итогам первого реального использования v42 на телефоне Вахтанг сообщил три проблемы:
1. Кнопка сохранения состава не видна вообще — "окно закрылось, нет доступа к интерфейсу".

## Сделано в предыдущей сессии (v38.1 — hotfix: навигация проваливалась в несуществующий уровень)

Обнаружено на устройстве сразу после v38 (скриншот): открыв группу → раздел («Группы › Подключение оборудования › Модульные автоматы»), внутри показывались НАЗВАНИЯ ГРУПП («Установка оборудования», «Подключение оборудования») вместо ожидаемого пустого списка комплектов. Причина: `currentLevel()` имел фоллбэк `LEVELS[this.drillPath.length] || LEVELS[0]` — когда `drillPath.length` выходил за границы `LEVELS` (2 элемента: kit_group, kit_section — `kit` ещё не реализован), тихо откатывался на `LEVELS[0]` (группы) вместо явной защиты. А защиты от самого выхода за границы не было: стрелка `›` в строке и `drillOpen()` проверяли только `hierarchy.childKey` из конфига (у kit_section он заполнен — `"kit"`, т.к. дерево концептуально трёхуровневое), не проверяя, существует ли этот уровень РЕАЛЬНО в `LEVELS`.

1. **`currentLevel()`** — фоллбэк `|| LEVELS[0]` убран. Теперь при некорректном `drillPath` метод вернул бы `undefined` вместо того чтобы маскировать баг постановкой не относящихся к узлу данных.
2. **Новый геттер `hasNextLevel`** — единое место истины: `true` только если и `childKey` задан в конфиге текущего уровня, И `LEVELS[drillPath.length + 1]` реально существует. Используется и для стрелки `›` в строке, и в `drillOpen()` (заменил прежнюю неполную проверку) — раньше условие дублировалось в двух местах по-разному, теперь один источник.
3. **Иконка ✎** — размер увеличен (15px → 22px), зона нажатия расширена через padding+отрицательный margin (визуальный размер строки не меняется, но фактическая кликабельная область больше) — по прямому запросу с фото («слишком маленькая, нужно увеличить то поле на которое надо тыкать»).
4. Тело строки (`drill-row-body`) теперь получает `cursor: pointer` только когда `hasNextLevel` истинно — на последнем реально существующем уровне (сейчас это kit_section) курсор больше не обещает переход, которого не будет.

Протестировано (TestClient, SQLite): `config_json.levels` содержит 2 элемента; для симулированного `drillPath.length=1` (внутри группы, на разделах) `LEVELS[2]` — `undefined`, значит `hasNextLevel` вернёт `false` и стрелка/переход корректно не появятся. Рендер `/kit_group-v2` содержит новую JS-логику (`hasNextLevel`, `LEVELS[this.drillPath.length]` без `||`). Регресс: создание группы + двух разделов внутри + `parent_id`-фильтр по-прежнему работает верно на уровне API (баг был только в JS-навигации, не в данных).

## Сделано в предыдущей сессии (v32 — поля под курс поставщика)

## Сделано в этой сессии (v31 — пагинация списков)

1. **`GET /api/{key}` возвращает объект вместо голого массива.** Было: `[...]`. Стало: `{"items": [...], "total": N, "page": N, "page_size": N, "total_pages": N}`. Это ломающее изменение формата ответа — обновлены ВСЕ места фронта, которые дёргают `/api/{key}` (основной список, `relationOptions`, подгрузка `constants{}` в `init()`).
2. **Новые query-параметры:** `page` (1-based, по умолчанию 1, отрицательные/за пределами общего числа страниц — зажимается до валидного диапазона) и `page_size` (если не передан — берётся `default_page_size` из справочника constants; если передан явно — приоритетнее константы). Явный `page_size` используется для служебных запросов, которым нужен весь список целиком без пагинации (например `relationOptions` для фильтров/выпадающих списков — передают `page_size=1000`).
3. **`total` считается ДО применения LIMIT/OFFSET** — по тому же statement, с учётом активного поиска/фильтра, чтобы «Стр. X из Y» не врало при активном поиске.
4. **UI:** блок пагинации под таблицей — «‹ Назад / Стр. X из Y / Далее ›», кнопки дизейблятся на первой/последней странице, блок скрыт целиком, если страниц ≤ 1.
5. **Сброс на 1-ю страницу** при изменении поискового запроса, чекбоксов полей поиска, клике по фильтру-чипу, клике по сортируемому заголовку колонки — везде, где меняется набор данных, страница явно сбрасывается в `page=1` перед `load()`. Клик «Назад»/«Далее» не сбрасывает — только двигает `page`.

Протестировано (TestClient, SQLite): 25 материалов, `page_size=10` → 3 страницы (10/10/5), `page=99` зажимается до последней валидной страницы, `page_size=1000` возвращает всё на одной странице (сценарий `relationOptions`), запрос без `page_size` берёт `default_page_size=100` из constants, `/api/constant` тоже отдаёт новый формат `{items,...}`, поиск + пагинация вместе — `total` отражает именно отфильтрованное количество, а не общее.

⚠️ Побочно обнаружено (не связано с пагинацией, существовало и раньше): на SQLite (только тестовое окружение) `LOWER()` не обрабатывает кириллицу регистронезависимо — поиск/сортировка по русским полям в TestClient-тестах может давать 0 совпадений, хотя на Postgres (Railway, продакшен) `LOWER()` с кириллицей работает корректно. При написании будущих тестов с поиском по тексту — либо проверять на латинице/цифрах, либо не полагаться на регистронезависимость кириллицы в SQLite-тестах.

## Сделано в этой сессии (v30 — упрощение пометки + сортировка по колонкам)

1. **Пометка на удаление упрощена.** Раньше: зелёная точка = активна, серая = помечена. Теперь: активная позиция — пустая ячейка (никакой точки), помеченная — серая точка (`x-show="item.is_deleted"`). `.status-dot-active`/`.status-dot-deleted` классы убраны, остался один `.status-dot` с серым фоном.
2. **Сортировка списка по клику на заголовок колонки.** Работает для всех обычных (не-relation) полей любой таблицы движка — не только материалов. Клик по заголовку — сортирует по возрастанию, повторный клик по тому же — переключает на убывание, и так по кругу. Стрелка (▲/▼) показывает текущее направление у активной колонки.
   - Текстовые поля сортируются регистронезависимо (`func.lower()` в SQL) — то есть по-настоящему алфавитно, "Яблоко" и "яблоко" не расходятся.
   - Числовые поля (`FieldConfig.is_numeric=True`, сейчас — цены) сортируются по значению напрямую.
   - Relation-поля (например «Бренд» — `brand_id`) исключены из сортировки: список хранит и показывает `id`, а не имя связанной записи, поэтому серверная сортировка по `id` не совпадёт с видимым алфавитным порядком имён брендов — сознательно не подключаю сортировку по таким колонкам, пока нет отдельного решения (например JOIN на бэкенде или сортировка на фронте по уже подгруженным `relationOptions`).
   - Новый параметр API: `GET /api/{key}?sort_by=<field>&sort_dir=asc|desc`. Неизвестное поле в `sort_by` игнорируется молча (без 500) — защита от сортировки по произвольному атрибуту модели через query-параметр.
   - Состояние сортировки (`sortBy`/`sortDir`) держится на фронте, пока страница открыта — не сохраняется между визитами.

Протестировано (TestClient, SQLite): сортировка по `short_name`/`full_name` (алфавитная, регистронезависимая) и по `price_excl_vat` (числовая) — оба направления; артикул (`sku_article`, текстовое поле, несмотря на буквенно-цифровой вид типа «2CDS253001R0164») сортируется корректно как текст; неизвестное `sort_by` не роняет запрос; `brand_id` не получил `toggleSort` в разметке; точка статуса больше не содержит `status-dot-active`, показывается только через `x-show`; полный регресс по soft-delete/purge-обработчикам/constants — без изменений в поведении.

**Решено в сессии v29 (зафиксировано, не поднимать заново без причины):**

- Кнопка «Удалить»/«Отменить» — одна универсальная (не две разные кнопки).

**Решено в сессии v30 (зафиксировано, не поднимать заново без причины):**

- Сортировка списка — по клику на заголовок колонки, работает универсально для всех текстовых/числовых полей во всех таблицах движка. Relation-поля (бренд) сознательно НЕ сортируются на сервере — id не совпадает с видимым алфавитным порядком имени; если понадобится сортировка по бренду, нужно отдельное решение (JOIN на бэкенде либо сортировка на фронте по `relationOptions`).

**Решено в сессии v40 (зафиксировано, не поднимать заново без причины):**
- Комплект (kit) открывается МОДАЛЬНЫМ ОКНОМ поверх дерева, НЕ отдельной страницей-карточкой — прежнее решение (`edit_mode="own_page"`, см. HANDOFF_kits_and_calculation.md) пересмотрено. Причина: разница между вариантами оказалась чисто технической (свой URL vs тот же экран), не влияющей на ощущения пользователя — адрес в браузере значения не имеет (уже решено в v38), а модалка технически проще и переиспользует существующий паттерн kit_group/kit_section.
- Полноэкранный режим — но не для самой карточки kit, а для БУДУЩЕГО настоящего подбора материалов (когда внутри модалки жмут «Добавить»): сейчас это простая форма (select из общего списка + количество), полноценный подбор с поиском/фильтрами/возможным drill-down по группам материалов — сознательно отдельная большая задача, спроектируется отдельно.
- `edit_mode="items_modal"` — новый универсальный паттерн движка (не одноразовый хак под kit): модалка вместо формы редактирования показывает список дочерних записей другой таблицы + кнопку добавления, используя тот же `parent_id`-механизм, что и drill-down между уровнями дерева. Пригодится для любой будущей таблицы с похожей структурой «узел + его состав».
- Порядок работы над функционалом модалки состава — сознательно НЕ всё сразу: сначала минимальная рабочая версия (видно, открывается, можно добавить), редактирование/удаление позиций состава и переименование комплекта внутри модалки — обсуждается отдельно, следующим шагом, по прямому указанию Вахтанга.

**Решено в сессии v38 (зафиксировано, не поднимать заново без причины):**
- Движок объединён: один `TableConfig` на все случаи (плоские таблицы И деревья), не отдельный второй класс конфига — расширение полями `hierarchy`/`delete_mode`/`edit_mode`. Причина: слишком много общего между режимами (CRUD, модалка, поиск/сортировка/пагинация для плоских списков), дублирование двух похожих движков создало бы двойную поддержку одной и той же логики.
- `parent_id` в `GET /api/{key}` — универсальный параметр движка для ЛЮБОЙ hierarchy-таблицы (работает уже для kit_section по kit_group, будет работать для kit по kit_section, в будущем для subgroup материалов по group), не отдельный код на каждую конкретную пару таблиц.
- Счётчик количества детей в строке group/section («3 раздела») — сознательно убран из плана целиком, ни в API, ни в UI. Строка показывает только название.
- Drill-down работает БЕЗ перезагрузки страницы браузера — одна HTML-страница знает про всю цепочку уровней дерева сразу (`config_json.levels[]`). Обоснование: объём небольшой (по оценке Вахтанга максимальная будущая вложенность — материалы, ~10-15 разделов по ~50 подразделов), это нормально загрузить целиком сразу, а плавность UX внутри интерфейса важнее, чем экономия на первом запросе.
- Адрес в браузере НЕ синхронизируется с положением в дереве (кнопка «Назад» браузера не работает для навигации вглубь/наружу дерева) — сознательно, по прямому указанию Вахтанга, не заложено даже как задел на будущее.
- Финальный вид UI для kit_group/kit_section/kit — см. HANDOFF_kits_and_calculation.md, уточнения по итогам разбора скриншотов прототипа (см. также пункт выше «Финальный согласованный UI» в этой сессии).

**Отложено осознанно (не поднимать без явного запроса):** редактирование/удаление отдельных позиций состава внутри модалки kit, переименование kit в той же модалке, полноэкранный подбор материалов с поиском/фильтрами (см. «Решено в сессии v40» выше); RBAC/роли (второго пользователя нет); валидация уникальности вне движка; экспорт CSV.

**Решено в сессии v35 (зафиксировано, не поднимать заново без причины):**
- Групповая пометка/снятие пометки на удаление — БЕЗУСЛОВНАЯ установка статуса (`is_deleted = value` для всех выделенных), не toggle. Если среди выделенных уже есть позиция в нужном статусе — просто перезаписывается тем же значением, не переключается обратно. Это отличает групповую операцию от одиночной кнопки в модалке (та — toggle).
- Кнопки «Пометить на удаление» / «Снять пометку» активны при любом количестве выделенных строк (не требуют ровно одну, в отличие от «Копировать»).
- Селект в bulk-эндпоинте: `soft_delete=False` таблицы (сейчас только `constant`) получают 422; у `constant` панели выделения нет вовсе, т.к. `allow_create=False`.
- Инфраструктура выделения по-прежнему рассчитана на дальнейшие групповые операции (следующая по списку — массовое изменение поля, например бренда у нескольких материалов разом) — расширять панель когда появится конкретная следующая операция.

**Решено в сессии v34 (зафиксировано, не поднимать заново без причины):**
- Правило округления НДС по украинскому законодательству проверено: специальное «округление до целой гривны» действует только для налоговой декларации по НДС (отдельная форма, подаётся в налоговую), не для рабочих документов приложения. На уровне цен/счетов/накладных достаточно обычного округления до 2 знаков (копеек) — без спецлогики. Если в будущем понадобится модуль именно налоговой отчётности — там потребуется отдельное округление до целых гривен, закладывать заранее не стали.
- Округление до 2 знаков — универсальное правило для ЛЮБОГО `FieldConfig.is_numeric=True` поля движка (не только для полей внутри `computed_pairs`), применяется в `api.py` при `create`/`update`.

**Решено в сессии v31 (зафиксировано, не поднимать заново без причины):**
- Пагинация — классические кнопки «Назад/Далее» с номером страницы («Стр. X из Y»), не бесконечная прокрутка. Размер страницы — из `default_page_size` в constants по умолчанию, но конкретный запрос может передать свой `page_size` явно (используется для `relationOptions`/фильтров, которым нужен весь список).
- Формат ответа `GET /api/{key}` изменён с массива на объект `{items, total, page, page_size, total_pages}` — если в будущем понадобится новый потребитель этого API, учитывать новый формат.

**Решено в сессии v32 (зафиксировано, не поднимать заново без причины):**
- Курс поставщика ("ВБ") считается в калькуляции "на лету" (вариант Б), а не пересчитывается и не сохраняется в TMC заранее (вариант А был отклонён — цена протухала бы при каждом изменении курса бренда, как раньше было с НДС до v28).
- Валюта поставщика (EUR/USD/др.) НЕ хранится отдельным полем — сознательно, для расчёта неважно какая именно валюта, только цифры (курс и цена в валюте).
- Курс бренда (`rate_vb`) правится вручную в форме, без интеграции с внешним источником курсов — как и было решено для первой итерации.
- Названия полей в БД/коде: `Brand.rate_vb`, `Material.price_vb_incl_vat`. Подписи в UI: «Курс ВБ», «Цена с НДС ВБ».

**Решено в сессии v33 (зафиксировано, не поднимать заново без причины):**
- Копирование строки реализовано через выделение чекбоксом (не через маленькую пиктограмму в строке — на телефоне легко промахнуться) + кнопка «Копировать» в панели над списком. Активна только при ровно одном выделенном элементе — групповое копирование нескольких строк сразу сознательно не делали.
- Инфраструктура выделения (`selectedIds`, `.selection-bar`, чекбоксы в строках) — рассчитана на будущие групповые операции (bulk soft-delete, массовое изменение поля типа бренда у нескольких материалов разом), но сейчас реализовано только копирование. Расширять панель новыми кнопками — когда появится конкретная следующая массовая операция, не заранее.
- Копия получает новый `id`, `is_deleted` копии всегда `false`, остальные поля (включая `sku_article`) копируются как есть без очистки — человек правит вручную перед сохранением.
