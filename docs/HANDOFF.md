# HANDOFF

## Состояние

Работает: универсальный CRUD-движок (`app/engine/`), раздел «Обработки» (`app/processors/`), soft-delete у материалов и брендов. Активные страницы: `/material-v2`, `/brand-v2`, `/constant-v2`, `/processors`. Верхнее меню — «Справочники» (Материалы/Бренды/Константы) и «Обработки» (Пересчёты + физическое удаление).

Последнее изменение: v31 — пагинация списков (LIMIT/OFFSET, кнопки «Назад/Далее», размер страницы из `default_page_size` в constants).

## Сделано в этой сессии (v31 — пагинация списков)

1. **`GET /api/{key}` возвращает объект вместо голого массива.** Было: `[...]`. Стало: `{"items": [...], "total": N, "page": N, "page_size": N, "total_pages": N}`. Это ломающее изменение формата ответа — обновлены ВСЕ места фронта, которые дёргают `/api/{key}` (основной список, `relationOptions`, подгрузка `constants{}` в `init()`).
2. **Новые query-параметры:** `page` (1-based, по умолчанию 1, отрицательные/за пределами общего числа страниц — зажимается до валидного диапазона) и `page_size` (если не передан — берётся `default_page_size` из справочника constants; если передан явно — приоритетнее константы). Явный `page_size` используется для служебных запросов, которым нужен весь список целиком без пагинации (например `relationOptions` для фильтров/выпадающих списков — передают `page_size=1000`).
3. **`total` считается ДО применения LIMIT/OFFSET** — по тому же statement, с учётом активного поиска/фильтра, чтобы «Стр. X из Y» не врало при активном поиске.
4. **UI:** блок пагинации под таблицей — «‹ Назад / Стр. X из Y / Далее ›», кнопки дизейблятся на первой/последней странице, блок скрыт целиком, если страниц ≤ 1.
5. **Сброс на 1-ю страницу** при изменении поискового запроса, чекбоксов полей поиска, клике по фильтру-чипу, клике по сортируемому заголовку колонки — везде, где меняется набор данных, страница явно сбрасывается в `page=1` перед `load()`. Клик «Назад»/«Далее» не сбрасывает — только двигает `page`.

Протестировано (TestClient, SQLite): 25 материалов, `page_size=10` → 3 страницы (10/10/5), `page=99` зажимается до последней валидной страницы, `page_size=1000` возвращает всё на одной странице (сценарий `relationOptions`), запрос без `page_size` берёт `default_page_size=100` из constants, `/api/constant` тоже отдаёт новый формат `{items,...}`, поиск + пагинация вместе — `total` отражает именно отфильтрованное количество, а не общее.

⚠️ Побочно обнаружено (не связано с пагинацией, существовало и раньше): на SQLite (только тестовое окружение) `LOWER()` не обрабатывает кириллицу регистронезависимо — поиск/сортировка по русским полям в TestClient-тестах может давать 0 совпадений, хотя на Postgres (Railway, продакшен) `LOWER()` с кириллицей работает корректно. При написании будущих тестов с поиском по тексту — либо проверять на латинице/цифрах, либо не полагаться на регистронезависимость кириллицы в SQLite-тестах.

## Сделано в этой сессии (v30 — упрощение пометки + сортировка по колонкам)

1. **Пометка на удаление упрощена.** Раньше: зелёная точка = активна, серая = помечена. Теперь: активная позиция — пустая ячейка (никакой точки), помеченная — серая точка (`x-show="item.is_deleted"`). `.status-dot-active`/`.status-dot-deleted` классы убраны, остался один `.status-dot` с серым фоном.
2. **Сортировка списка по клику на заголовок колонки.** Работает для всех обычных (не-relation) полей любой таблицы движка — не только материалов. Клик по заголовку — сортирует по возрастанию, повторный клик по тому же — переключает на убывание, и так по кругу. Стрелка (▲/▼) показывает текущее направление у активной колонки.
   - Текстовые поля сортируются регистронезависимо (`func.lower()` в SQL) — то есть по-настоящему алфавитно, "Яблоко" и "яблоко" не расходятся.
   - Числовые поля (`FieldConfig.is_numeric=True`, сейчас — цены) сортируются по значению напрямую.
   - Relation-поля (например «Бренд» — `brand_id`) исключены из сортировки: список хранит и показывает `id`, а не имя связанной записи, поэтому серверная сортировка по `id` не совпадёт с видимым алфавитным порядком имён брендов — сознательно не подключаю сортировку по таким колонкам, пока нет отдельного решения (например JOIN на бэкенде или сортировка на фронте по уже подгруженным `relationOptions`).
   - Новый параметр API: `GET /api/{key}?sort_by=<field>&sort_dir=asc|desc`. Неизвестное поле в `sort_by` игнорируется молча (без 500) — защита от сортировки по произвольному атрибуту модели через query-параметр.
   - Состояние сортировки (`sortBy`/`sortDir`) держится на фронте, пока страница открыта — не сохраняется между визитами.

Протестировано (TestClient, SQLite): сортировка по `short_name`/`full_name` (алфавитная, регистронезависимая) и по `price_excl_vat` (числовая) — оба направления; артикул (`sku_article`, текстовое поле, несмотря на буквенно-цифровой вид типа «2CDS253001R0164») сортируется корректно как текст; неизвестное `sort_by` не роняет запрос; `brand_id` не получил `toggleSort` в разметке; точка статуса больше не содержит `status-dot-active`, показывается только через `x-show`; полный регресс по soft-delete/purge-обработчикам/constants — без изменений в поведении.

## Сделано в предыдущей сессии (v29 — soft-delete + физическое удаление)

1. **`is_deleted: bool` добавлено в модели `Material` и `Brand`** (default `False`). Не объявляется как обычный `FieldConfig` в `tables.py` — служебное поле движка, сериализуется отдельно в `engine/api.py _serialize()`, только если `config.soft_delete=True`.
2. **`TableConfig.soft_delete: bool`** (новое поле, default `False`) — включено для `brand_table` и `material_table`. `constant_table` не тронута (там `allow_delete=False` — как было).
3. **`DELETE /api/{key}/{id}` — переключатель, не удаление**, если `soft_delete=True`: `instance.is_deleted = not instance.is_deleted`. Повторный вызов на уже помеченной записи снимает пометку. Возвращает `{"deleted": False, "is_deleted": <bool>, "id": ...}` вместо прежнего `{"deleted": True, ...}`.
4. **UI списка:** первая колонка — точка-индикатор статуса (`.status-dot`, зелёная = активна / серая = помечена), без текста, только `title`-подсказка при наведении. Появляется только у `soft_delete`-таблиц (`{% if config.soft_delete %}` в `engine/page.py`).
5. **UI модалки:** кнопка внизу теперь одна универсальная — подпись переключается `x-text="editing.is_deleted ? 'Отменить' : 'Удалить'"`. Клик всегда шлёт `DELETE`; для `soft_delete`-таблиц модалка НЕ закрывается после клика (запись осталась, просто обновился статус) — человек может сразу передумать и нажать ещё раз.
6. **Ключевой принцип соблюдён и проверен тестом:** обработчик `recalc_material_vat` обрабатывает помеченные на удаление материалы наравне с обычными — никакой фильтрации по `is_deleted` нигде в движке или в существующих обработчиках нет.
7. **Обработчик физического удаления** (`app/processors/registry.py`): `_build_purge_processors()` автоматически генерирует по одному `Processor` (`purge_<table_key>`) для КАЖДОЙ таблицы движка с `soft_delete=True` — не нужно руками добавлять новый процессор при появлении следующей soft-delete таблицы. Сейчас: `purge_brand`, `purge_material`. Логика простая: `DELETE` всех строк `is_deleted=True` в этой таблице, без проверки зависимостей (сознательно — следующий шаг). Страница `/processors` уже поддерживала выбор одной таблицы через `<select>` — код `processors/page.py` не менялся, новые процессоры подхватились автоматически.
8. **Миграция колонки на Railway (Postgres):** `app/database.py` — `_ensure_is_deleted_columns()`, вызывается из `init_db()` при каждом старте. Для Postgres проверяет через `information_schema.columns`, есть ли `is_deleted` у `material`/`brand`, и добавляет через `ALTER TABLE ... ADD COLUMN ... DEFAULT false`, если нет. Идемпотентно. Для SQLite — не нужна, пропускается (там таблица создаётся сразу с полем). В отличие от истории с `vat_rate` (там удаление колонки — ручное, разово) добавление новой колонки с default безопасно автоматизировать.

Протестировано (TestClient, SQLite): создание материала/бренда → `is_deleted=False`; `DELETE` ставит пометку, повторный `DELETE` снимает; помеченная запись остаётся в обычном списке (`GET /api/...`) без фильтрации; `recalc_material_vat` обрабатывает помеченный материал как обычный; `purge_brand`/`purge_material` физически удаляют только помеченные записи, найдены автоматически в `PROCESSORS` без ручного перечисления; `constant-v2` (без soft_delete) не показывает точку статуса и не задета; `DELETE` константы по-прежнему 422 (allow_delete=False); страницы `/material-v2`, `/brand-v2`, `/processors` рендерятся, содержат ожидаемую разметку.

## Сделано в предыдущей сессии (v28 — НДС из constants + bulk-recalculate)

1. **`Material.vat_rate` удалено из модели.** Ставка НДС больше не хранится per-material — общая для всех, живёт только в `constants` (ключ `vat_rate`). ⚠️ Колонка `vat_rate` физически ОСТАЁТСЯ в таблице `material` на Railway (Postgres) — просто больше не используется приложением. Договорились: физическое удаление колонки (`ALTER TABLE ... DROP COLUMN`) — отдельным шагом ПОСЛЕ того, как через bulk-recalculate пересчитают реальные данные и убедятся, что всё корректно.
2. **`FieldConfig` расширен:** `virtual: bool` + `source_constant_key: Optional[str]` — поле не хранится в модели/БД вообще (исключено из `TableConfig.field_names()`), значение подтягивается на фронте отдельным запросом к `/api/constant` и показывается как readonly. Используется для `vat_rate` в форме и списке материалов.
3. **`ComputedPair` расширен:** `rate_constant_key: Optional[str]` — если задан, ставка для пересчёта берётся не из поля записи (`rate_field`), а из справочника constants. И бэкенд (`api.py _apply_computed_pairs`, теперь принимает `session`), и фронт (JS `onComputedChange`/`validateBeforeSave`, новый объект `constants{}` в Alpine state, подгружается в `init()`) читают ставку из constants одинаково.
4. **Универсальный bulk-recalculate обработчик** (`app/processors/`): реестр `Processor` (key, table_key, label, run-функция) + страница `/processors` (выбор таблицы → радио-кнопки функций → «Выполнить») + API `POST /api/processors/{key}/run`. Первая функция — `recalc_material_vat`: пересчитывает `price_incl_vat` всех материалов по актуальной ставке из constants, `price_excl_vat` — источник истины, не трогается. Идемпотентна (повторный запуск ничего не меняет, если ставка не менялась). Раздел «Обработки» в меню теперь ведёт на `/processors` (было пусто).
5. `register_engine_tables()` теперь возвращает `Jinja2Templates` наружу — `main.py` переиспользует то же окружение (с уже настроенными `APP_VERSION`/`NAV_MENU` globals) для регистрации `/processors`, вместо создания второго `Jinja2Templates`.

Протестировано: создание материала без vat_rate пересчитывает `price_incl_vat` по ставке из constants; смена ставки в constants сразу видна в карточке материала как readonly; изменение цены материала после смены ставки пересчитывает по НОВОЙ ставке; при ставке 0 — понятная 422-ошибка; bulk-обработчик находит и обновляет только реально устаревшие записи, повторный запуск идемпотентен; все старые страницы (`material-v2`, `brand-v2`, `constant-v2`) не задеты.
