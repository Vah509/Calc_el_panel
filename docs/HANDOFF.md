# HANDOFF

## Состояние

**v89 — механика формирования подчинённых документов изменена:
Спецификация и Счёт теперь ОБНОВЛЯЮТСЯ НА МЕСТЕ при повторном
формировании (id и номер документа сохраняются), а не пересоздаются
заново. Готово к очередной заливке в `ai-updates/`.**

zayavka -> calculation -> specification -> **invoice** (счёт-фактура,
образец печатной формы — СФ-0000040, обсуждение 2026-08-29). Кнопка
«Создать счёт» — на карточке спецификации (внешне похожа на текстовую
ссылку, а не на классическую кнопку — это нормально, так же
оформлены «Обновить»/«Отвязать от спецификации»/«Дать скидку» на
самом счёте). Печатная форма (сам бланк по образцу) — ЕЩЁ НЕ СДЕЛАНА,
это только редактируемая карточка документа.

**v89 — новое правило «обновление на месте + каскад» (прямое указание
Вахтанга, 2026-08-30):** при повторном нажатии «Спецификация N» на
заявке — если для этого (request_id, brand_slot) спецификация уже
существует, она НЕ удаляется и не пересоздаётся с новым id/номером:
document_number остаётся прежним, обновляются только document_date/
document_time (на текущий момент — оба, так проще и единообразнее) и
позиции (SpecificationItem — полная перезапись состава, т.к. набор
калькуляций мог измениться). Если у этой спецификации уже есть
привязанный (`specification_id` заполнен) счёт — он тоже
пересчитывается автоматически, тем же кодом, что и ручная кнопка
«Обновить» на счёте, без отдельного захода человека на карточку
счёта («следующий документ тоже нужно обновить» — прямые слова
Вахтанга). Механика счёта (`_build_invoice_handler`) не менялась —
она уже работала по этому принципу с самого начала (v86).

Побочный эффект: ForeignKeyViolation-баги, которые раньше чинились
временным обнулением `Invoice.specification_id`/`InvoiceItem.
specification_item_id` при удалении родителя (см. историю ниже),
теперь возникают РЕЖЕ — сама Specification больше не удаляется
вообще, счёт остаётся привязан к ней постоянно. Но SpecificationItem
всё равно пересобираются (delete+create) при каждом формировании, так
что обнуление `InvoiceItem.specification_item_id` (трассировочная
ссылка на конкретную строку, не то же самое что сама привязка счёта
к спецификации) по-прежнему нужно и осталось в коде.

**Три прод-бага после первого деплоя v86 (2026-08-30) — история,
все исправлены к текущей версии:**

1. **500 при создании фирмы** (`POST /api/firm` → `TypeError: Not a
   boolean value: ''`). `is_default` было обычным `FieldConfig`,
   пустая форма присылала `is_default: ""` — Python это молча принял,
   Postgres на INSERT потребовал настоящий boolean и упал (SQLite
   тест не поймал — не строгий с типами колонок). **Исправление**:
   `is_default` полностью убран из `fields=[]` у `firm_table`,
   переключается только кнопкой «Сделать по умолчанию».

2. **Двойная вертикальная полоса прокрутки** на полноэкранных
   карточках-формах (`/invoice-v2/{id}` и т.д.). `.modal-body` в
   общем CSS всегда имел `max-height: 60vh; overflow-y: auto` — для
   обычной модалки это нужно, но полноэкранный режим формы уже
   растягивает `.modal`/`.modal-backdrop` на весь экран отдельным
   инлайн-стилем, а `.modal-body` этот override не получал.
   **Исправление**: тот же инлайн-стиль `max-height:none;
   overflow-y:visible;` добавлен и для `.modal-body`, но ТОЛЬКО когда
   `render_mode == 'form' and not config.hierarchy`.

3. **500 (`ForeignKeyViolation`) при повторном нажатии
   «Спецификация N»/«Пересчитать», если из этой спецификации уже был
   создан хотя бы один счёт.** Изначально (v88) исправлено обнулением
   `Invoice.specification_id`/`InvoiceItem.specification_item_id`
   перед удалением старой Specification/SpecificationItem — работало,
   но означало, что счёт при каждой пересборке спецификации
   автоматически "отвязывался" (нежелательный побочный эффект, не
   отдельно обсуждённый с Вахтангом). **v89 заменяет это правильным
   решением** — раз Specification больше не удаляется (см. «Состояние»
   выше), Invoice.specification_id вообще не рвётся; обнуление
   осталось только для InvoiceItem.specification_item_id (трассировка
   до конкретной СТРОКИ спецификации, которая всё ещё пересоздаётся).

## Сделано в этой сессии

- **Новые модели**: `app/models/firm.py` (справочник СВОИХ юрлиц-
  продавцов — полное название, ЄДРПОУ, ІПН, № свідоцтва ПДВ, банковские
  реквизиты, телефон, адрес, `is_default`), `app/models/invoice.py`
  (шапка счёта), `app/models/invoice_item.py` (строки счёта, снэпшот +
  редактируемая `discount_percent`). Подробная механика — в docstring-
  комментариях каждого файла, там же зафиксированы решения Вахтанга
  из обсуждения.
- **Новый универсальный примитив движка** `invoice_items_tab` (по
  аналогии с `readonly_items_tab` из v85, но с ОДНИМ редактируемым
  полем на строку — скидка) — `app/engine/config.py`:
  `invoice_items_tab` / `invoice_items_table_key` /
  `invoice_items_columns` / `invoice_items_discount_field` /
  `invoice_items_price_field` / `invoice_items_price_after_discount_
  field` / `invoice_items_line_total_field` / `invoice_items_sum_field`
  / `invoice_items_bulk_discount_action`.
- **`app/engine/api.py`**: `POST /{item_id}/actions/{action}` теперь
  ПРИНИМАЕТ необязательный JSON-body (`payload`) — нужен для «Дать
  скидку» (единственное действие в движке, которому нужны данные от
  человека, не только id записи). Обратная совместимость: payload
  передаётся обработчику, только если тот объявлен с 3-м позиционным
  параметром (проверка через `handler.__code__.co_argcount`) —
  существующие `action_handlers` (recalc_full_name и т.д.) не тронуты.
- **`app/engine/tables.py`**:
  - `_sync_invoice_items_from_specification` — полная перезапись
    InvoiceItem по текущим SpecificationItem (delete-all+create-all,
    как и у `_build_specification_handler`)
  - `_recalculate_invoice_totals` — Σ InvoiceItem.line_total +
    constants['vat_rate']
  - `_build_invoice_handler` (кнопка «Создать счёт» на спецификации):
    ищет НЕ отвязанный Invoice по `specification_id`, если нет —
    создаёт новый (firm = is_default, client_invoice_id = Request.
    client_invoice_id ИЛИ Request.client_id), в обоих случаях
    синхронизирует строки и пересчитывает итоги
  - `_unlink_invoice_handler` (кнопка «Отвязать от спецификации») —
    сбрасывает ТОЛЬКО specification_id, request_id и все данные счёта
    остаются
  - `_refresh_invoice_items_handler` (кнопка «Обновить») — пока
    привязан, перечитывает строки заново
  - `_apply_bulk_discount_handler` (кнопка «Дать скидку», payload=
    {"discount_percent": число}) — перезаписывает ВСЕ строки
    одинаковым значением, включая уже изменённые вручную (решение
    Вахтанга: без исключений)
  - `_recalc_invoice_item_before_update` (`before_update_hook` у
    `invoice_item_table`) — при обычном PUT одной строки (правка
    скидки прямо в таблице) пересчитывает unit_price_after_discount/
    line_total строки И итоги шапки счёта
  - `_set_default_firm_handler` — кнопка «Сделать по умолчанию» на
    firm. **`is_default` полностью исключён из `fields=[]`** (см.
    прод-баг №1 выше) — не входит в `field_names()`, не
    сериализуется, не приходит и не уходит через обычный
    create/update, переключается только через эту кнопку.
  - `firm_table`, `invoice_table`, `invoice_item_table` — новые
    TableConfig, добавлены в `ALL_TABLES`
  - `_build_specification_handler` (пересборка спецификации при
    повторном нажатии «Спецификация N»/«Пересчитать») — **v89,
    переписан полностью**: спецификация теперь ОБНОВЛЯЕТСЯ НА МЕСТЕ
    (id/document_number сохраняются, document_date/document_time
    обновляются на текущие), а не удаляется и создаётся заново.
    Позиции (SpecificationItem) по-прежнему полностью пересобираются
    (delete+create) — их id меняются, поэтому `InvoiceItem.
    specification_item_id` (трассировочная ссылка) обнуляется у уже
    существующих строк счёта перед удалением старых
    SpecificationItem — но САМА Specification/Invoice.
    specification_id теперь не рвётся вообще, т.к. родитель больше
    не удаляется. Сразу после пересборки — если у спецификации есть
    привязанный Invoice, вызывается `_sync_invoice_items_from_
    specification` + `_recalculate_invoice_totals` для него
    (каскадное обновление «следующего документа», прямое указание
    Вахтанга)
  - `specification_table` — добавлена `ActionButton(action=
    "build_invoice", label="Создать счёт")`
- **`app/engine/document_chain.py`** — `ChainLink(child_key="invoice",
  parent_key="request", fk_field="request_id")`. specification_id у
  Invoice сознательно НЕ зарегистрирован отдельным ChainLink (nullable,

- **`app/engine/page.py`**:
  - HTML-блок `invoice_items_tab` (параллельно `readonly_items_tab`) —
    таблица строк с редактируемым `<input>` скидки на каждой строке +
    кнопка «Дать скидку» сверху
  - JS: `invoiceItemDiscountChanged(row)` (PUT одной строки),
    `invoiceItemsRefreshTotals()` (перечитывает шапку после правки),
    `invoiceItemsApplyBulkDiscount()` (`window.prompt()` + POST на

  - Новые ключи в CONFIG: `invoiceItemsTab`, `invoiceItemsTableKey`,

    `invoiceItemsPriceAfterDiscountField`, `invoiceItemsLineTotalField`,

  - **v87**: `.modal-body` получает `style="max-height:none;
    overflow-y:visible;"` при `render_mode == 'form' and not

  → калькуляция → спецификация → счёт, включая арифметику скидок,
  правку одной строки vs «Дать скидку» на все, отвязку + повторное

## Открыто

- **Печатная форма счёта** (реальный бланк по образцу СФ-0000040 —
  Постачальник/Одержувач/Платник в шапке, таблица, пропись суммы) —
  ЕЩЁ НЕ СДЕЛАНА. Сейчас есть только карточка редактирования (форма
  движка), не документ для печати/PDF. Обсудить формат вывода (HTML
  для печати из браузера? PDF-экспорт? когда переходить к
  Excel/PDF-экспорту по общему пункту дорожной карты) отдельно.
- **`is_default` у Firm нигде не виден в UI** — только через кнопку
  «Сделать по умолчанию» (переключить) и напрямую в БД (посмотреть).
  В списке/форме сейчас никак не отображается, какая фирма сейчас
  дефолтная — сознательный компромисс после прод-бага №1: безопаснее
  полностью убрать поле с формы, чем городить показ read-only bool
  без нормальной движковой поддержки. Можно доделать позже отдельным
  движковым примитивом для boolean-полей (сейчас в движке в принципе
  нет универсального способа безопасно показать/редактировать
  `bool`-поле модели через обычный FieldConfig — то же ограничение
  обошли и здесь, и раньше у is_deleted через спецкейс).
- **Существующие счета (созданные до фикса фирм), например I-000001**
  — у них `firm_id = null` (фирмы ещё не было в момент создания).
  Нужно вручную выбрать «Постачальник» в уже существующих счетах —
  это не баг, это ожидаемое поведение для документов, созданных до
  того, как появилась хоть одна фирма.
- **Пересборка спецификации после создания счёта (v89)** — теперь
  корректно НЕ отвязывает и не пересоздаёт связанный счёт, а
  каскадно обновляет его на месте. Человек не увидит явного
  уведомления в момент клика «Спецификация N» о том, что связанный
  счёт был пересчитан заодно — стоит решить, нужно ли такое
  уведомление в UI (сейчас просто редирект на страницу спецификации,
  без явного упоминания счёта).
- **Deploy pipeline пропустил ДВА Postgres-специфичных бага подряд**
  (is_default — прод-баг №1; specification_item_id — прод-баг №3) —
  SQLite CI по умолчанию не ловит ни строгую типизацию колонок, ни
  нарушения внешних ключей (нужна явная `PRAGMA foreign_keys=ON`,
  которой до сих пор нет в `app/database.py`, см. давно открытый
  пункт «SQLite vs Postgres trap»). Стоит серьёзно рассмотреть
  включение этой PRAGMA в тестовом окружении по умолчанию — иначе
  продолжим находить такие баги только на живом проде.
- **v89 (обновление на месте + каскад) не проверено визуально/вживую
  на Railway** — только в контейнере через TestClient. Нужно
  подтверждение от Вахтанга после деплоя v89: (1) номер спецификации
  действительно не меняется при повторном нажатии «Спецификация N»,
  (2) привязанный счёт обновляется без захода на его карточку, (3)
  двойной скролл (фикс v87) не вернулся.
- Пункты 2–4 дорожной карты (ценообразование/актуализация цен,
  «перепроведение» остальных документов, Excel/PDF-экспорт) — не
  начаты.
- Рефакторинг `enginePage()` — по-прежнему сознательно отложен.
