# План "Перепроведение" — сквозной план сессий

Этот файл был физически утерян из репозитория до сессии 4 (см.
предупреждение в `HANDOFF.md` сессии 3). Восстановлен по контексту
чата задним числом в сессии 4, начиная с решений сессии 4 —
детали сессий 2–3 восстановлены кратко из `HANDOFF.md`.

## Идея плана

Новая цепочка документов, параллельная существующей (заявка →
калькуляция → спецификация → счёт): на каждой из трёх вкладок
бренда заявки — работа с активными калькуляциями слота напрямую,
без спецификации как отдельного документа.

Целевая цепочка: **заявка → калькуляция → счёт** (напрямую).

Старый путь через спецификацию **не удаляется сейчас** — он
продолжает работать как есть. Спецификацию удалим только когда
новая цепочка будет полностью реализована и обкатана (решено в
сессии 4, см. ниже).

## Сессия 2 (кратко, по памяти из HANDOFF.md сессии 3)

- На каждой из трёх вкладок бренда заявки — read-only список
  АКТИВНЫХ калькуляций этого слота с чекбоксом в каждой строке.
- Чекбоксы чисто клиентские (`brandCalcSelected` в page.py), в БД
  ничего не пишут, сбрасываются при каждом открытии формы.
- Кнопка «Обновить список» — `refresh_brand_calculations`.
- Подтверждено: путь через спецификацию не убирается на данном
  этапе (см. также решение сессии 4 ниже).

## Сессия 3 (v98)

- Кнопка «Обновить цены» — `recalc_brand_calculations`, пересчитывает
  цены+суммы всех активных калькуляций всех трёх слотов разом (не
  только текущего слота, не только отмеченных).
- `_recalc_calculation_prices(instance, session) -> dict` выделена
  из `_recalc_material_prices_handler` как переиспользуемое ядро

- `_active_brand_slot_calculations(request_instance, slot, session)`
  выделена как общий запрос активных калькуляций слота.

## Сессия 4 — «Создать счёт» из калькуляций слота

### Решено (Вахтанг, 2026-09-04)

1. **Кнопка «Створити рахунок» — своя на каждом слоте.** По клику
   создаёт счёт из калькуляций, отмеченных чекбоксом на этой
   вкладке/слоте. Калькуляция принадлежит только своему слоту —
   в счёт от кнопки слота 1 калькуляции слота 2/3 попасть не могут.

2. **Спецификация как промежуточный шаг убирается для этой цепочки.**
   Новая цепочка строит `invoice` + `InvoiceItem` напрямую из
   отмеченных калькуляций, минуя создание `specification` /
   `SpecificationItem`.
   - Старый путь (заявка → калькуляция → спецификация → счёт)
     **остаётся рабочим как есть** — не трогаем, пока новая цепочка
     не будет полностью реализована и обкатана.
   - **Когда новая цепочка будет полностью готова — спецификацию
     удалим** (модель, обработчики, интерфейс). Это следующий
     большой шаг ПОСЛЕ сессии 4, не часть неё.

3. **Одна калькуляция = одна строка счёта** (по `final_total`) — не
   разворачивается в отдельные материалы/комплекты калькуляции.

4. **Пустой выбор → кнопка неактивна** (disabled, не ошибка).
   - Список калькуляций слота пуст (калькуляций ещё нет) → кнопка
     неактивна.
   - Список не пуст, но ничего не отмечено → кнопка тоже неактивна.
   - Оба случая — одинаковое поведение, без отдельных сообщений.
   - Дополнительно нужна кнопка **«Відмітити всі»** рядом со списком
     калькуляций слота (клиентское действие, отмечает все чекбоксы
     текущего слота разом).

5. **Клиент/фирма счёта** — берутся из `request.client_id` /
   `client_invoice_id` как есть (по аналогии с текущим путём через
   спецификацию), без отдельного шага подтверждения.

6. **Поведение при повторном клике** — зависит от количества
   активных счетов, уже созданных с этого слота:
   - **0 активных счетов по слоту** → создаётся новый счёт (обычный
     первый путь).
   - **Ровно 1 активный счёт по слоту** → счёт **пересоздаётся**:
     - шапка счёта (`invoice`: номер, дата, клиент, фирма и т. д.)
       **не меняется**;
     - **все существующие `InvoiceItem` этого счёта удаляются и
       создаются заново** из текущего отмеченного набора
       калькуляций слота.
   - **2+ активных счетов по слоту** → действие блокируется,
     показывается сообщение: «по цьому слоту є декілька активних
     рахунків — заморозьте або видаліть один з них».
   - «Активный» здесь = не замороженный (конкретный признак
     заморозки — смотреть существующее поле статуса `invoice` в
     коде перед реализацией, не заводить новое понятие без сверки).

7. **Label и размещение кнопки** — «**Створити рахунок**» (интерфейс
   системы украиноязычный), в том же ряду, что «Обновити список» /
   «Обновити ціни» на каждой из трёх вкладок бренда.

### Открытые вопросы — все закрыты по состоянию на конец сессии 4

Три технических уточнения обнаружены при чтении кода перед
реализацией (расхождение между уже существующими комментариями в
коде и текстом плана выше) и решены с Вахтангом 2026-09-04:

- **Merge vs delete-all+create-all при повторном формировании счёта
  (пункт 6 выше).** `app/models/invoice_item.py` уже содержал (до
  сессии 4) комментарий, что повторное формирование должно идти
  MERGE-логикой по `calculation_id`, сохраняя `discount_percent` на
  совпавших строках — это ПРОТИВОРЕЧИТ формулировке "все InvoiceItem
  удаляются и создаются заново" выше в этом же пункте. **Решено:
  MERGE по `calculation_id`** — существующие строки (калькуляция
  осталась отмеченной) обновляются на месте с сохранением
  `discount_percent`; строки калькуляций, которые сняли с отметки —
  удаляются; новые отмеченные калькуляции — создаются как новые
  строки с `discount_percent=0`. Формулировка в пункте 6 выше
  ("все... удаляются и создаются заново") считать УСТАРЕВШЕЙ,
  замещена этим уточнением.
- **`Invoice.brand_slot` — новое snapshot-поле**, тот же принцип, что
  `Specification.brand_slot` (см. образец в `app/models/
  specification.py`). Нужно для запроса "активные счета этого
  слота" из пункта 6. Подтверждено Вахтангом. **Не забыть
  `_ensure_is_deleted_columns()` в `app/database.py`** — таблица
  `invoice` уже на проде.
- **Побочно обнаружено и исправлено при реализации:** `Invoice.
  is_frozen` (v96) и `InvoiceItem.calculation_id` (v96) были добавлены
  в МОДЕЛИ ещё в сессии до текущей, но не были добавлены в
  `FieldConfig` соответствующих `TableConfig` (`invoice_table`/
  `invoice_item_table` в `app/engine/tables.py`) — без этого поле
  отсутствует в `field_names()` движка и не сериализуется /не
  принимается через API, хотя физически есть в БД. Обнаружено при
  тестировании сессии 4 (`build_invoice_slot_N` читает `is_frozen`
  для правила "активных счетов слота"). Добавлены оба `FieldConfig`
  в этой же сессии 4, а не отложено — та же логика, что и правило
  "не откладывать явные баги в отдельную сессию".
- **Контракт payload с фронта.** `runAction()` в `page.py` шлёт голый
  POST без тела — универсальный механизм НЕ трогаем. Для кнопки
  "Створити рахунок" — отдельная JS-функция с собственным `fetch()`
  и JSON body (тот же паттерн, что `invoiceItemsApplyBulkDiscount()`
  для кнопки "Дать скидку"), передаёт `{calculation_ids: [...]}`
  напрямую на `/api/request/{id}/actions/build_invoice_slot_N`.
  Серверный роут `run_action` в `app/engine/api.py` уже поддерживает
  необязательный `payload` (введено для "Дать скидку" — обработчик с
  3 позиционными параметрами получает его, остальные — по-старому).

## Сессия 5 (v100) — кнопка «Заморозити» на форме счёта

### Решено (Вахтанг, 2026-09-05)

1. **Отдельная кнопка**, не переиспользование чекбокса `is_frozen`
   как обычного поля формы — `ActionButton(action="toggle_frozen")`
   рядом с «Обновить»/«Отвязать» (`action_buttons`, `tab=None`).
2. **Toggle с динамической подписью**: «Заморозити», когда
   `is_frozen=False`; «Розморозити», когда `is_frozen=True`. Одна
   кнопка на оба направления, не две разные.
3. **Без confirm** — переключение сразу по клику в обе стороны,
   несмотря на влияние на `_build_invoice_from_slot_handler`.
4. **Кнопка «Відв'язати від специфікації» (`unlink_invoice`) —
   помечена на удаление, но НЕ удаляется в сессии 5.** Для счетов
   новой цепочки `specification_id` и так `NULL`, кнопка не имеет
   смысла. Полное удаление (кнопка + `_unlink_invoice_handler`) —
   задача **сессии 6** вместе с остальной зачисткой старого пути.

### Реализация (v100)

- `_toggle_invoice_frozen_handler(instance, session)` в
  `app/engine/tables.py` — простой toggle `instance.is_frozen`,
  возвращает `{"is_frozen": ...}` (мержится в `editing` через
  стандартный `runAction()`, отдельный JS не понадобился).
- `ActionButton(action="toggle_frozen", label="Заморозити", tab=None)`
  в `invoice_table.action_buttons` + регистрация в
  `action_handlers["toggle_frozen"]`.
- `app/engine/page.py`, макрос `render_action_buttons` — точечная
  ветка по `btn.action == 'toggle_frozen'`: рендерит кнопку с
  `x-text="editing.is_frozen ? 'Розморозити' : 'Заморозити'"` вместо
  статичного `{{ btn.label }}`. Единственная кнопка с динамической
  подписью в проекте — `ActionButton.label` для остальных кнопок
  остаётся статичным, схема намеренно не обобщена под один случай.
- Никаких изменений в модели/БД — `Invoice.is_frozen` и колонка в
  БД существуют с v96, `FieldConfig` — с v99 (сессия 4).
- Протестировано локально (SQLite, `TestClient`): toggle
  false→true→false через `POST /api/invoice/{id}/actions/
  toggle_frozen`, значение сохраняется в БД; рендер `/invoice-v2/
  {id}` содержит кнопку и обе возможные подписи; регрессия —
  `/request-v2/new` и `/invoice-v2/new` рендерятся без ошибок,
  `unlink_invoice` не тронут и присутствует как раньше.

## Сессия 6 (v101) — частичная зачистка старого пути

### Решено (Вахтанг, 2026-09-05)

По плану сессия 6 предполагала полную зачистку старого пути через
спецификацию (4 пункта, см. `SESSION_6_CONTEXT.md`). По факту решено
**не выполнять план целиком** — только код-уровневая часть,
без изменений в БД:

1. **Specification/SpecificationItem в БД — НЕ трогаются.** Таблицы,
   модели, `specification_table`, страницы `/specification-v2/*`,
   пункт «Спецификации» в `NAV_MENU` (`app/version.py`) и в
   `/documents-chain` — **всё остаётся как есть без изменений**.
   Причина: документы в базе ещё не исправлены, DROP TABLE
   откладывается до отдельного явного решения в будущем.
2. **Старые счета с заполненным `specification_id`** — остаются как
   архивные записи как есть, ничего не мигрируется.
   `Invoice.specification_id` в модели тоже остаётся (не убирается
   физически) — по той же причине, что и пункт 1.
3. **Пункт «Спецификация» в `/documents-chain`** — остаётся как есть,
   без изменений (то же решение, что пункты 1–2).
4. **Рефакторинг `enginePage()`** — отложен отдельной сессией после,
   НЕ входит в сессию 6.

**Что реально удалено в сессии 6** — только два элемента старого
пути, которые уже фактически не используются для новых счетов
(подтверждено Вахтангом: «уже не используется»), и удаление которых
не требует ни одной миграции БД:

- **Кнопка «Отвязать от спецификации» (`unlink_invoice`)** на форме
  счёта + обработчик `_unlink_invoice_handler`.
- **Кнопка «Создать счёт» (`build_invoice`)** на форме спецификации
  + обработчик `_build_invoice_handler`.

### Реализация (v101)

- `app/engine/tables.py`:
  - Удалены функции `_build_invoice_handler` и
    `_unlink_invoice_handler` целиком.
  - `specification_table.action_buttons`/`action_handlers` —
    запись `build_invoice` убрана (весь блок опустел, атрибуты
    удалены из `TableConfig`, так как других кнопок на спецификации
    не было).
  - `invoice_table.action_buttons`/`action_handlers` — запись
    `unlink_invoice` убрана, `refresh_invoice_items` и
    `toggle_frozen` остались нетронутыми.
  - Комментарии, ссылавшиеся на удалённые обработчики (в
    `_build_invoice_from_slot_handler`, `_refresh_invoice_items_handler`,
    `firm_table`, `invoice_item_table`) — поправлены на актуальные
    ссылки (`_build_invoice_from_slot_handler` и т.д.), чтобы не
    вводить в заблуждение в будущих сессиях.
- `_refresh_invoice_items_handler` — НЕ тронут, продолжает читать
  `Specification` для старых счетов старой цепочки (specification_id
  ещё заполнен) — это единственный оставшийся код-путь, кроме модели,
  который трогает `Specification` со стороны `invoice_table`.
- `app/version.py` — `APP_VERSION` v100 → v101. `NAV_MENU` не менялся.
- Протестировано локально (SQLite, `TestClient` context manager):
  - `/invoice-v2/new`, `/specification-v2/new`, `/request-v2/new`,
    `/calculation-v2/new`, `/documents-chain` — рендерятся без
    ошибок (200, без Jinja-исключений);
  - HTML `/invoice-v2/new` не содержит `unlink_invoice` и старой
    подписи «Отвязать от спецификации»; кнопки `toggle_frozen` и
    `refresh_invoice_items` присутствуют как раньше;
  - HTML `/specification-v2/new` не содержит вызова action
    `build_invoice` и кнопки «Создать счёт» (ложное совпадение
    отфильтровано — `build_invoice_slot_N`, не связанная строка
    новой цепочки, по-прежнему на месте).

## Технический ориентир для реализации сессии 4 (для Claude, не для Вахтанга)

- Смотреть `_build_specification_handler` и
  `_recalc_brand_calculations_handler` в `app/engine/tables.py` как
  два образца:
  - первый — как строится дочерний документ из заявки по слоту с
    `redirect_url` (аналог для создания `invoice` напрямую);
  - второй — как обрабатывается набор калькуляций слота разом.
- `_active_brand_slot_calculations(request_instance, slot, session)`
  уже даёт список активных калькуляций слота — но новому обработчику
  нужны только ОТМЕЧЕННЫЕ (id калькуляций нужно передавать с фронта в
  теле запроса, не голым POST без параметров, как остальные action —
  проверить текущий контракт `runAction()`/`action_handlers`,
  возможно потребуется новый вид вызова с payload).
- «Відмітити всі» — чисто клиентское (`CLIENT_ACTIONS` в page.py), по
  аналогии с другими client-side action, добавляет все id текущего
  слота в `brandCalcSelected[slot]`.
- Перед реализацией пункта 6 (пересоздание/блокировка по количеству
  активных счетов) — нужен запрос "активные счета, созданные с этого
  слота этой заявки". Слот, вероятно, придётся связывать с
  `invoice` через новое поле (аналогично тому, как калькуляция несёт
  `brand_slot`) — как именно счёт узнаёт "я создан со слота N",
  нужно решить технически (например `Invoice.brand_slot` snapshot-
  поле) и, если это новое поле на уже задеплоенной таблице —
  не забыть `_ensure_is_deleted_columns()` в `app/database.py`
  (см. критический паттерн в общих принципах проекта).
