## 0. Комплекты (kit) — ЗАВЕРШЕНО, код в проде

`kit_group → kit_section → kit → kit_item`, drill-down дерево через
универсальный движок (`Hierarchy` в `app/engine/config.py`), включая
модалку состава (`edit_mode="items_modal"`). Полностью реализовано и
задеплоено — детали см. `app/engine/ENGINE.md`, не дублируется здесь.

Единственный принцип, важный для калькуляции: калькуляция хранит
ССЫЛКУ на kit (`kit_id`), не снимок состава — при пересчёте состав
разворачивается заново на текущий момент ("live", не snapshot).
Комплекты — только soft-delete (не физически) из-за возможных ссылок
на них из калькуляций; физическое удаление — отдельным purge-
обработчиком с проверкой использования.

## 2. Документооборот: что уже в коде, что спроектировано, что открыто

Цепочка: **request → calculation → specification → invoice**

### 2.1 Порядок реализации
1. `client` + `request` — ГОТОВО (v49-v55). Простой CRUD-документ.
2. `calculation` (шапка, без строк) — ГОТОВО. Реальный FK
   `request_id` → request.
3. `calculation_item` — СЛЕДУЮЩИЙ ШАГ. Строки калькуляции (материал
   или комплект × количество).
4. `specification` + `specification_item` — не начато. Кнопки
   "Спецификация"/"Пересчитать" в request — пока неактивные заглушки
   (`FieldConfig.row_actions`, по паре на каждый брендовый слот).
5. `invoice` — не начато, не спроектировано.

### 2.2 Таблица `client` — ЗАКОДИРОВАНО
Поля (`app/models/client.py`): `short_name` (внутреннее, для поиска),
`full_name` (полное, для документов), `egrpou_code`, `phone`,
`contact_person_name`/`contact_person_phone` (контактное лицо,
отдельный телефон от общего), `is_deleted` (стандартный soft-delete).

### 2.3 Таблица `request` (заявка) — ЗАКОДИРОВАНО
Поля (`app/models/request.py`):
- `document_number`, `document_date` — своя нумерация, префикс "R"
  (см. `app/engine/document_numbering.py`), оба редактируются вручную,
  дубликаты номеров не проверяются.
- `client_id` (FK → client, оформитель) и `client_invoice_id` (FK →
  client, nullable — получатель счёта, если отличается от
  оформителя; "по умолчанию = client_id" — правило будущего UI, НЕ
  constraint модели).
- `brand_slot_1_id`/`brand_slot_2_id`/`brand_slot_3_id` (FK → brand,
  каждый nullable) — все три слота всегда видны в форме.
- `note` — свободная текстовая заметка, только в форме (не в
  списке/поиске).
- `is_deleted` — стандартный soft-delete.
- **Статуса у request НЕТ.** Управление состоянием — через три
  независимые операции: копирование (штатный client-side copy
  движка), пометка на удаление + физическое удаление обработчиком,
  архивация (планируется, механика не спроектирована — см. раздел 3).
- Кнопки "Спецификация"/"Пересчитать" — по паре на каждый брендовый
  слот, в одном ряду с select бренда (`row_actions`). Пока disabled-
  заглушки — получат логику вместе со specification.
- "Создать документ на основании" / "Показать подчинённые документы"
  (`child_document_actions`) — рабочие кнопки, ведут на создание
  calculation и на страницу "Цепочка документов" соответственно.

### 2.4 Таблица `calculation` (калькуляция, шапка) — ЗАКОДИРОВАНО
Поля (`app/models/calculation.py`):
- `document_number`, `document_date`, `document_time` — своя
  нумерация, префикс "K". `document_time` — отдельное от даты поле
  (важно для хронологии в журнале подчинённых документов).
- `request_id` (FK → request, **nullable**) — по умолчанию
  калькуляция всегда создаётся на основании заявки, но nullable
  оставлен на случай калькуляции без заявки.
- `client_name` — рабочее название, вводится человеком вручную
  (свободный текст, НЕ ссылка на справочник client — концептуально
  другое поле, чем `client_id` у request).
- `name_template` — шаблон полного названия, СВОЙ у каждой
  калькуляции (не общая константа). Плейсхолдеры `{client_name}`,
  `{brand_slot}`, `{request_number}` — см.
  `app/engine/name_template.py::render_name_template()`. Дефолт:
  `"Сборка {client_name}"`.
- `full_name` — результат подстановки `name_template`, пересчитывается
  НЕ автоматически при сохранении, а вручную по кнопке "Пересчитать
  название" (чтобы не перезаписывать ручную правку при каждом save).
- `brand_slot` (1/2/3, nullable) — номер варианта, группирующий
  признак. `brand_id` как отдельное FK-поле на calculation НЕ
  заведено — бренд самого варианта смотрится через `request` по
  номеру слота (`request.brand_slot_N_id`), не хранится повторно на
  calculation.
- `status` — draft / active / archived_pending / delete_pending, БЕЗ
  принудительного порядка переходов. Пересчёт разрешён в любом
  статусе. Единственное различие между статусами — участвует ли
  документ в дальнейших цепочках (специфика конкретного будущего
  обработчика, не самого поля).
- `is_deleted` — стандартный soft-delete, отдельно от `status`.

**Логика "перепровести" (пересчитать), пока не реализована для
строк — верхнеуровневый принцип согласован:** 1) актуализируются цены
материалов, 2) live-разворачивается состав комплектов на текущий
момент, 3) собирается итоговая спецификация материалов и цена изделия.
Если состав kit изменился с прошлого пересчёта — лог/предупреждение,
не молчаливая потеря/добавление строки.

#### 2.4.1 `calculation_item` (строки калькуляции) — СЛЕДУЮЩИЙ ШАГ, не закодировано
Модель верхнего уровня согласована: одна таблица, два nullable FK
(`material_id` / `kit_id`) — тип строки определяется тем, какое поле
заполнено (ровно одно из двух). Повтор одного и того же kit в разных
строках одной калькуляции — норма, не ошибка-дубликат. На фронте — две
вкладки "Материалы"/"Комплекты" (чисто UI-фильтр над одним списком,
не влияет на структуру таблицы). Точные остальные поля (quantity,
цена на момент добавления и т.п.) — решить при кодировании этого шага.

### 2.5 Таблица `specification` + `specification_item` — НЕ НАЧАТО
Промежуточный документ между calculation и invoice. Назначение:
перечень изделий одного варианта не всегда переносится в счета 1-в-1
— из одной спецификации может быть создано НЕСКОЛЬКО счетов (например,
из 5 изделий сначала счёт на 3, потом на 2).

Из-за этого — ЭТО СНИМОК, не live-ссылка (в отличие от kit_item).
Обоснование: если бы цена была live и калькуляцию пересчитали после
того как часть спецификации уже нарезали на выставленный счёт — счёт
задним числом "поехал" бы в цене, недопустимо для финансового
документа.

Черновая структура (не финализирована, требует отдельного
проектирования при начале работы):
- `specification`: `request_id` (FK), `brand_slot` (1/2/3)
- `specification_item`: `specification_id` (FK), `calculation_id` (FK
  — не для live-подтяжки цены, а чтобы при повторном формировании
  пройти по ссылкам и перечитать актуальные значения), плюс
  скопированные на момент формирования `client_name`/`full_name`
  (уточнить, какое из двух названий использовать), `price`,
  `quantity`.

Механика формирования (кнопка "Спецификация" у брендового слота N в
request): пересчитать все calculation этого `(request_id, brand_slot)`
→ для каждой взять актуальные название/цену → полностью переписать
`specification_item` (delete-all+create-all, как `kit_item`). Между
нажатиями кнопки данные сами не меняются — чистый статичный снимок.

2026-08-26):** от чего именно наследуется specification — от request
или от calculation — и как в этот момент участвует выбор бренда,
Вахтанг ещё не определил. Не начинать кодирование раздела 2.5, пока
это не обсуждено отдельно.

### 2.6 Таблица `invoice` (счёт) — НЕ СПРОЕКТИРОВАНО
Появится после specification. Открытый вопрос: копирует ли invoice
себе данные (снимок снимка) или может сослаться на
`specification_item` напрямую — вероятно тоже снимок по той же
логике, что и specification, но не подтверждено.

### 2.7 Журнал изделий для сквозного поиска — идея, НЕ решено заводить
В более раннем черновике этого документа обсуждалась отдельная
таблица `product`, куда calculation "толкала" бы копию названия/цены
при каждом сохранении — чтобы искать изделие по названию спустя долгое
время независимо от стадии документооборота. **Эта идея НЕ
реализована и не подтверждена как нужная** — в текущем коде
(`app/models/`) такой таблицы нет. Если понадобится сквозной поиск по
изделиям — обсуждать отдельно, не считать уже решённым.
