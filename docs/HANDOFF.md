# HANDOFF

## Состояние

**v99 — Сессия 4 плана "Перепроведение" (кнопка "Створити рахунок" на
вкладке бренда заявки).**
На каждой из трёх вкладок бренда заявки, рядом с "Обновить список"/
"Обновить цены", появились две новые кнопки:
- **"Відмітити всі"** — клиентское действие, отмечает чекбоксом все
  калькуляции текущего списка слота разом.
- **"Створити рахунок"** — по клику на калькуляциях, отмеченных
  чекбоксом на ЭТОЙ вкладке/слоте, создаёт (или обновляет) счёт
  напрямую, МИНУЯ спецификацию. Disabled, если список калькуляций
  слота пуст или ничего не отмечено.

Правила поведения (полностью, см. `docs/HANDOFF_reprovodenie.md`,
сессия 4):
- 0 активных (не замороженных) счетов этого слота заявки → создаётся
  новый `Invoice` (напрямую, `specification_id=NULL`).
- Ровно 1 активный счёт слота → счёт обновляется НА МЕСТЕ: шапка не
  трогается, позиции (`InvoiceItem`) обновляются MERGE-логикой по
  `calculation_id` — совпавшие калькуляции обновляют строку на месте
  (`discount_percent` СОХРАНЯЕТСЯ), снятые с отметки калькуляции
  удаляются, новые отмеченные — создаются заново.
- 2+ активных счёта слота → действие блокируется (422 с понятным
  текстом на украинском).
- Старый путь через спецификацию (`build_specification_N` + кнопка
  "Создать счёт" на самой спецификации) остаётся полностью рабочим,
  не тронут.

Спецификация как документ пока НЕ удаляется — это отдельный будущий
шаг ПОСЛЕ полной обкатки новой цепочки (см. план).

## Сделано в этой сессии

1. **`app/models/invoice.py`** — новое поле `brand_slot: Optional[int]`
   (снэпшот номера слота заявки, тот же принцип, что
   `Specification.brand_slot`) — нужно, чтобы находить "активные
   счета этого слота", т.к. счета новой цепочки не проходят через
   `Specification` и иначе были бы неотличимы друг от друга по слоту.
2. **`app/database.py`** — `("invoice", "brand_slot", "INTEGER NULL")`
   добавлено в `_ensure_is_deleted_columns()` (таблица `invoice` уже
   на проде).
3. **`app/engine/tables.py`**:
   - Новая фабрика `_build_invoice_from_slot_handler(brand_slot)` —
     обработчик с сигнатурой `(instance, session, payload)` (третий
     параметр — уже существующий с 2026-08-29 контракт payload в
     `run_action`, `app/engine/api.py`, введён тогда для "Дать
     скидку"). Реализует все правила из "Состояние" выше. Возвращает
     `{"redirect_url": "/invoice-v2/{id}"}`.
   - Зарегистрированы `build_invoice_slot_1/2/3` в `action_handlers`
     `request_table` (номер слота зашит в имени action, тот же приём,
     что `build_specification_N`).
   - **Попутно обнаружены и исправлены два упущения из более ранних
     версий**: `Invoice.is_frozen` (v96) и `InvoiceItem.calculation_id`
     (v96) существовали в моделях, но НЕ были добавлены в
     `FieldConfig` соответствующих `TableConfig` — без этого поля не
     сериализуются и не принимаются через API движка, хотя физически
     есть в БД. Добавлены `FieldConfig` для обоих в `invoice_table` /
     `invoice_item_table`.
4. **`app/engine/page.py`**:
   - Новая JS-функция `buildInvoiceFromSlot(slot)` — свой `fetch()` с
     JSON body `{calculation_ids: [...]}` (тот же паттерн, что
     `invoiceItemsApplyBulkDiscount()` для "Дать скидку"), НЕ через
     универсальный `runAction()` (тот не передаёт payload). Обрабатывает
     `redirect_url` в ответе так же, как `runAction()`.
   - `brandCalcSelectedCount(slot)` — для `:disabled`-биндинга кнопки.
   - `CLIENT_ACTIONS.mark_all_brand_calc_1/2/3` — "Відмітити всі",
     чисто клиентское, отмечает все id текущего списка слота в
     `brandCalcSelected[slot]`.
   - HTML: две новые кнопки в `materials-toolbar` на вкладках брендов.
5. **`app/version.py`** — `APP_VERSION` v98 → v99.
6. **`docs/HANDOFF_reprovodenie.md`** — восстановленный в этой сессии
   файл дополнен: три открытых технических вопроса закрыты решениями
   Вахтанга (см. файл, раздел "Открытые вопросы" сессии 4), включая
   явную фиксацию противоречия план/код по merge-логике (решено в
   пользу merge, не delete-all+create-all).
7. Проверено локально (SQLite, `TestClient` context manager, тестовые
   скрипты удалены перед архивацией):
   - `build_invoice_slot_1` с 2 отмеченными калькуляциями → новый
     счёт, верные суммы (`total_excl_vat`/`vat_amount`/`total_incl_vat`);
   - повторный вызов с одной калькуляцией снятой — тот же `invoice.id`
     (не новый счёт), снятая строка удалена, `discount_percent`,
     выставленный вручную на оставшейся строке, СОХРАНИЛСЯ (merge);
   - пустой `calculation_ids` → 422 с понятным текстом;
   - после установки `is_frozen=True` — повторный вызов создаёт НОВЫЙ
     `Invoice` (не трогает замороженный);
   - 2 активных счёта одного слота → 422, блокировка;
   - регрессия: `build_specification_N` → старый `build_invoice`
     (со спецификации) → `refresh_brand_calculations` →
     `recalc_brand_calculations` — все работают как раньше;
   - рендер `/request-v2/new` и `/invoice-v2/{id}` — без ошибок Jinja,
     новые кнопки/функции присутствуют в HTML.
