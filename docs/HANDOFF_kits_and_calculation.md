## 2. К чему пришли по обсуждению (ЗАФИКСИРОВАНО, не переоткрывать без причины)

### 2.1 Порядок работы над темой
Выбран путь: спроектировать верхнеуровневую цепочку документов
(заявка → калькуляция → спецификация → счёт) на уровне общей формы связей
СЕЙЧАС, до кода, а кодировать — снизу вверх, начиная с того, что не имеет
зависимостей. Первый практический шаг в коде — kit_section.

Причина: калькуляция изделия как документ ещё не существует вообще, и без
понимания её формы есть риск спроектировать kit/kit_items неудобно для
будущей калькуляции и потом переделывать.

### 2.2 Комплекты (kit) — архитектура отображения и структуры
- `kit_section` — справочник разделов комплектов. Обычная таблица через
  universal CRUD engine. Нужен sort_order для управляемого порядка обхода
  (у Вахтанга в 1С была практика: открыл раздел → выбрал нужные комплекты →
  закрыл → следующий раздел, порядок важен для удобства работы).
  Примеры разделов (не финальные, для ориентира): подключение силовых
  автоматов, подключение модульных автоматов, установка силовых автоматов,
  установка модульных автоматов, расширительные шины и т.д. Точный список
  разделов ещё нужно проговорить отдельно.
- `kit` — карточка комплекта. НЕ обычная списковая таблица движка, а
  отдельная страница-карточка. Поля: название, ссылка на раздел (kit_section).
  Soft-delete как везде в проекте.
- `kit_items` — состав комплекта: вложенный редактируемый список внутри
  карточки kit. Каждая позиция — материал + количество. Позиции можно
  удалять физически сразу, БЕЗ soft-delete (обоснование см. 2.3).
  Операции: изменить количество, скопировать позицию, добавить позицию.
- Отображение — трёхуровневая раскрывающаяся структура:
  раздел (свёрнут по умолчанию) → комплекты внутри раздела (клик разворачивает)
  → состав комплекта (клик разворачивает, редактирование внутри).
  Это кастомный UI-компонент, не стандартная таблица движка.
- Для самого kit (не kit_items) нужны те же операции, что и у обычных
  строк движка: копирование, создание нового. Удаление — только soft-delete
  (пометка), т.к. в комплектации могут быть ссылки на него из калькуляций.
  Нужен отдельный processor (по аналогии с существующим purge processor),
  который перед физическим удалением комплекта проверяет, не используется
  ли он где-то (в калькуляциях).

### 2.3 Принцип "live-разворачивание" комплекта в калькуляции
Решено: калькуляция хранит ССЫЛКУ на kit (kit_id), а НЕ снимок его состава.
При действии "перепровести" система заново идёt в текущий состав kit_items
и разворачивает его на момент пересчёта. Это следует общему принципу проекта
"live references vs snapshots" (снимки — только для фактов расчёта типа
price_snapshot).
Следствие: позиции материала внутри комплекта можно удалять сразу, без
soft-delete — потому что калькуляции не хранят копию состава, только ссылку
на kit. Если состав комплекта изменился, а комплект уже использовался в
старой калькуляции — при "перепровести" нужно показать предупреждение/лог,
что состав изменился, а не молча потерять/добавить строку.

### 2.4 Черновая модель калькуляции (верхний уровень, спроектировано СЕЙЧАС, код ещё не писался)

Цепочка документов: **заявка → калькуляция → спецификация → счёт**

**request (заявка)** — журнал заявок. Пока НЕ реализована в коде.
На время разработки калькуляции без готовой таблицы request: либо временно
nullable FK, либо одна техническая заявка-заглушка, к которой всё привязано,
пока настоящих заявок нет. Архитектурно связь request→calculation
ОБЯЗАТЕЛЬНА (в проде это ошибка, если её нет), это временный обход только
для этапа разработки.

**calculation (калькуляция)** — одно изделие (один вариант, один бренд).
Поля (черновые, английские названия НЕ согласованы, только для ориентира):
- `request_id` (FK на заявку; временно nullable/заглушка — см. выше)
- `brand_id` (FK на бренд) — это РЕАЛЬНЫЙ группирующий признак вариантов
  одного изделия внутри заявки. НЕ название — важно, см. 2.5.
- `client_name` — название изделия как ввёл человек, свободный текст,
  БЕЗ технической роли, ненадёжно для любых связей (может быть опечатка).
- `work_name` — рабочее/внутреннее название для отображения в базе.
  Генерируется по правилу (какому именно — ОТКРЫТЫЙ ВОПРОС, см. раздел 3).
  Пример прикидки от Вахтанга: перед клиентским названием добавляется
  префикс "Сборка" (например клиент написал "ШМУ" → в базе "Сборка ШМУ").
  Возможно также нужен номер заявки и номер/код бренда в составе рабочего
  названия — это тоже не решено окончательно.
- `quantity` — количество этого изделия в рамках заявки (например, в заявке
  нужно 20 шт этого щита — это не 20 строк, а одна calculation с quantity=20).
- статус — НЕ до конца спроектирован, см. раздел 3.
- строки калькуляции (calculation_item, ещё не спроектированы детально) —
  либо материал напрямую, либо комплект (kit_id) × количество. Повтор одного
  и того же комплекта в одной калькуляции несколькими строками — это НОРМА,
  не дублирование-ошибка (Вахтанг специально подтвердил: может быть комплект
  №1 три раза, потом комплект №2 два раза, потом снова комплект №1 один раз —
  всё это потом схлопывается в единую спецификацию материалов позже).

**Логика "перепровести" (пересчитать калькуляцию):**
Пересчёт идёт по дереву: 1) актуализируются цены материалов по текущим
правилам, 2) разворачивается состав комплектов live (на текущий момент),
3) собирается итоговая спецификация материалов и итоговая цена изделия.
Если что-то в составе комплекта изменилось с прошлого пересчёта — лог/
предупреждение, не молчаливое исчезновение.

### 2.5 Почему группировка вариантов — через бренд, а не через название
Изначально Claude предположил, что три варианта одного изделия на разных
брендах связаны одинаковым client_name. Вахтанг поправил: НЕТ, названия
могут и должны отличаться, привязываться к названию нельзя (хрупко,
опечатка ломает связь). Реальная группировка вариантов одного изделия
внутри заявки — через `brand_id`. "Показать все изделия этого варианта
заявки" = "все calculation с этим request_id и этим brand_id". Отдельной
сущности "вариант/позиция изделия" не создаём — это просто срез по
(request_id, brand_id).

### 2.6 Операции над калькуляцией (начато, не закончено)
Кроме "перепровести", калькуляцию можно:
- копировать в ДРУГУЮ заявку — при копировании бренд НЕ переносится
  автоматически, его нужно вручную выбрать заново из списка брендов,
  доступных в целевой заявке (см. открытый вопрос 3.4 — есть ли у заявки
  свой ограниченный список допустимых брендов, или выбор из общего списка
  брендов системы).
