# Универсальный CRUD-движок

Генерирует страницу(и) + JSON API по одному декларативному описанию
таблицы (`TableConfig`). Одна и та же система обслуживает и плоские
справочники (material, brand), и документы с собственной нумерацией
(request, calculation), и drill-down деревья (kit_group → kit_section
→ kit). Все детали конкретного поведения — в комментариях `config.py`
рядом с самим полем; этот файл — карта "что где искать", не дубликат.

Актуальное состояние: **v75**. Полную историю решений и почему именно
так — смотреть `docs/HANDOFF.md` (текущий шаг) и git-историю этого
файла (прошлые своды).

## Файлы

| Файл                 | Отвечает за |
|----------------------|-------------|
| `config.py`          | Датаклассы: `TableConfig`, `FieldConfig`, `ComputedPair`, `Relation`, `FormRow`, `Hierarchy`, `ActionButton` |
| `formulas.py`        | Формулы пересчёта (без `eval`); продублированы в JS (`ENGINE_FORMULAS` в `page.py`) — должны совпадать |
| `name_template.py`   | `render_name_template()` — подстановка плейсхолдеров в шаблон полного названия документа (Python); JS-дубликат — `recalc_full_name` в `CLIENT_ACTIONS` внутри `page.py`, тоже должны совпадать |
| `document_numbering.py` | Автогенерация номера документа при создании + подтяжка счётчика (`DocumentCounter`, один на префикс) |
| `document_chain.py`  | Реестр связей parent→child между ТИПАМИ документов (`CHAIN_LINKS`, `ROOT_KEY`) — используется страницей "Цепочка документов", не связан с `Hierarchy` (та про drill-down внутри одной таблицы) |
| `api.py`             | Фабрика JSON-роутера: `GET/POST/PUT/DELETE /api/{key}`, `GET /api/{key}/{id}` (единичная запись), bulk-операции, actions |
| `page.py`            | Рендер HTML (список / форма / оба) через Jinja + Alpine.js; самый большой файл — вся клиентская логика движка живёт здесь одним `<script>`-блоком |
| `page_router.py`     | Подключает `/{key}-v2` (и, если есть `own_page_url`, ещё `/{key}-v2/new` и `/{key}-v2/{id}`) к FastAPI |
| `register.py`        | Регистрирует все таблицы из `tables.py` разом; защитная проверка `own_page_url == url_path` при старте |
| `tables.py`          | Реальные `TableConfig(...)` — material, brand, client, unit, constant, request, calculation, kit_group/kit_section/kit, calculation_item, kit_item |

## Как добавить новую таблицу

1. Модель SQLModel уже должна существовать в `app/models/`.
2. В `tables.py` создать `TableConfig(...)`. Смотреть ближайший по
   смыслу существующий конфиг как пример, а не писать с нуля:
   `material_table` — плоский справочник с вычисляемой парой полей;
   `request_table`/`calculation_table` — документ со своей нумерацией
   и вкладками; `kit_group_table`/`kit_section_table`/`kit_table` —
   drill-down дерево.
3. Добавить конфиг в список, который читает `register.py` (один
   вызов) — если добавляется тип документа в цепочку (после
   calculation), не забыть строку в `CHAIN_LINKS`
   (`document_chain.py`).
4. Страница(ы) и API появляются автоматически — руками ничего больше
   не пишется. Если таблице нужны полноэкранные формы (документ, а не
   справочник) — задать `own_page_url`, см. раздел ниже.

Названия таблиц/полей/функций согласуются с Вахтангом ДО фиксации в
коде — английский термин может быть неочевиден человеку, для которого
английский не родной.

## Три способа хранения таблицы

Каждая `TableConfig` попадает ровно в одну из трёх категорий — они не
смешиваются:

**Плоский справочник** (`hierarchy=None`, `edit_mode="modal"`,
`own_page_url=None`) — material, brand, client, unit, constant. Список
+ модалка редактирования на одном URL `/{key}-v2`, как было с самого
начала движка.

**Drill-down дерево** (`hierarchy` заполнен) — kit_group → kit_section
→ kit. Один URL на весь путь дерева, переходы между уровнями БЕЗ
перезагрузки страницы (`config_json` несёт всю цепочку `child_key`
разом). `delete_mode="simple"` на промежуточных узлах (kit_group,
kit_section) — физическое удаление разрешено, только если нет детей
(синхронный `count()`, без processor). Последний уровень (kit) —
`edit_mode="items_modal"`: клик открывает не форму переименования, а
модалку состава (`items_source_table_key` — отдельная плоская таблица
kit_item, не встроенная в дерево).

**Плоский документ со своей страницей** (`own_page_url` задан) —
request, calculation. См. следующий раздел — это добавилось позже
(v75) и меняет то, как рендерится форма.

## `own_page_url` и `render_mode` (v75) — полноэкранные формы документов

До v75 форма редактирования ЛЮБОЙ таблицы была модалкой поверх списка
на одном URL. Для request/calculation это неудобно на телефоне —
теперь для таблиц с заданным `own_page_url` действует отдельная схема:

- `/{key}-v2` — только список (`render_mode="list"`), в разметке
  модалки вообще нет
- `/{key}-v2/new` — форма создания на весь экран (`render_mode="form"`)
- `/{key}-v2/{id}` — форма редактирования на весь экран
  (`render_mode="form"`)

Клик по строке списка / кнопка "+ Запись" переходят на форму (полная
перезагрузка), а не открывают модалку на месте. "Закрыть"/после
"Сохранить"/после "Удалить" делают `history.back()` — человек
возвращается туда, откуда реально пришёл (свой журнал, чужой журнал
через "Создать документ на основании", или "Цепочка документов").

Таблицы БЕЗ `own_page_url` (все справочники + drill-down дерево)
продолжают работать по-старому — список+модалка на одном URL,
`render_mode` для них игнорируется, всегда форсируется `"both"`.

`own_page_url` строкой **обязан совпадать** с фактическим URL, на
который таблицу регистрирует `page_router.py` (`/{key}-v2`) —
`register.py` бросает `ValueError` при старте, если это разошлось.

Ключевые JS-функции (`page.py`): `openDocumentRow()`,
`openCreateRow()` — переход на форму вместо открытия модалки;
`maybeOpenOwnPage()` — на form-странице читает id из ПУТИ (не query) и
подгружает запись; `closeToList()` — вызывается из `close()`/`save()`/
`remove()` вместо `modalOpen=false`, когда `CONFIG.renderMode ===
"form"`.

## Цепочка документов (`app/documents_chain/`, отдельно от движка)

Не часть `app/engine/`, но зависит от него: страница `/documents-chain`
показывает документ (request) и всех его потомков по реестру
`document_chain.py::CHAIN_LINKS`, обходя граф BFS вниз от
`ROOT_KEY`. Добавление нового уровня цепочки (specification →
calculation) — одна строка `ChainLink` в реестре, без правок кода
страницы/API.

Кнопка "Создать документ на основании" в панели выделения этой
страницы (v76) видна, только когда выделен ровно один документ из
`groups[0]` (корневой уровень) — использует
`group.create_child_document_url`, тот же URL-паттерн, что и
одноимённая кнопка обычного журнала (`.../new?from_request={id}`).
Для некорневых уровней кнопка сознательно не показывается — механизм
calculation → specification ещё не спроектирован.

## `FieldConfig` — что стоит помнить

Полный список опций и их смысл — комментарии прямо над каждым полем
в `config.py` (актуальнее, чем любой пересказ здесь). Тонкости, которые
проще один раз явно назвать:

- `searchable` + `search_toggle` + `search_default` — на таблице
  сначала должно быть `enable_search_toggles=True`, иначе чекбоксы
  поиска не показываются вообще, поиск идёт по всем `searchable`
  полям без возможности отключить отдельное.
- `virtual=True` — поле не хранится в модели/БД, используется для
  вычисляемых/сервисных полей формы.
- `tab` — работает только если на `TableConfig` задан непустой
  `form_tabs`; без него все поля рендерятся одной колонкой.
- `inline_action` — кнопка встраивается в строку конкретного поля
  (например "Пересчитать название" рядом с `full_name` у calculation),
  в отличие от `TableConfig.action_buttons`, которые рендерятся общим
  блоком.

## `ComputedPair` — пересчитываемые пары полей

Формула обязана быть реализована ДВАЖДЫ и совпадать: в `formulas.py`
(Python, серверная проверка при сохранении — 422 при недопустимом
состоянии) и в `ENGINE_FORMULAS` внутри `page.py` (JS, мгновенный
пересчёт на фронте без похода на сервер). `eval` нигде не используется.
Пример — цена без/с НДС у material (`formula="vat"`).

## `FormRow` — группировка полей в один визуальный ряд

Без `form_rows` каждое поле — своя строка формы, по порядку
объявления в `fields`. `FormRow(field_names=[...])` собирает несколько
полей в один ряд; раскладка строится в `_build_form_layout()`
(`page.py`) строго по порядку `fields` — если поле входит в ещё не
отрисованный `FormRow`, выводится весь ряд целиком. Поля с
`in_form=False` пропускаются. Ряд с полем из `computed_pairs`
получает класс `.price-pair` (визуально выделен).

## Нумерация документов (`document_numbering.py`)

Таблица с `document_number_field` + `document_prefix` получает
автогенерацию номера при создании (счётчик по префиксу в
`DocumentCounter`, одна строка на префикс — "R" у request, "K" у
calculation). Номер и дата редактируются вручную человеком в форме;
дубликаты номеров НЕ проверяются (осознанное решение — можно вписать
уже занятый номер вручную). Ручная правка номера на большее значение
подтягивает счётчик вверх.

## Тестирование изменений движка

Постоянных `pytest`-файлов в репозитории нет — тесты пишутся заново в
каждой сессии как одноразовый скрипт и удаляются перед сборкой архива
(см. чек-лист упаковки в `docs/HANDOFF.md`). Через
`fastapi.testclient.TestClient(app)` **в режиме контекстного
менеджера** (`with TestClient(app) as client:`) — иначе не сработают
startup-события (`init_db()`). Фоновый `uvicorn` через `&` в
`bash_tool` ненадёжен, не использовать. Требует пакет `httpx2`
(`pip install httpx2 --break-system-packages`), не `httpx`.

## Известные ограничения / на будущее

- Фильтр по связи (chips в filterbar) поддерживает пока только один
  явный relation-параметр в query (`brand_id` у material) — при
  появлении второго нужно обобщить до произвольного `?field=value` по
  всем `config.relations`.
- Список опций для чипов-фильтров и для `relationOptions` цепочки
  документов подгружается целиком без пагинации — годится, пока
  связанные таблицы небольшие (десятки записей).
- `specification`/`invoice` не реализованы. Когда появятся —
  потребуется задать им `own_page_url` для полноэкранных форм и
  строку в `CHAIN_LINKS`; является ли specification дочерним для
  calculation или для request, и как в этот момент участвует выбор
  бренда — не решено, не начинать без обсуждения.
- MkDocs (Material theme) как возможная будущая "витрина" для `.md` —
  не решено, не внедрять без прямого запроса.
