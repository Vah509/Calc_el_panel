# ЭлектроЩит — автоматизация ценообразования и документооборота для сборки электрощитов

Замена 1С: расчёт стоимости изделий, цепочка документов (заявка →
калькуляция → спецификация → счёт-фактура), печатные формы. Деплой
полностью через Railway (автодеплой по пушу в `main`).

## Стек

- **FastAPI** + **SQLModel** — бэкенд и модели данных
- **Alpine.js** + **Jinja2** — фронтенд без сборки/бандлера
- **PostgreSQL** (Railway, прод) / **SQLite** (локально, CI)
- **reportlab** — печатная форма счёта в PDF (чистый Python, без
  системных библиотек)
- **openpyxl** — та же печатная форма в Excel (тоже чистый Python)

Обе PDF- и Excel-библиотеки выбраны намеренно как pure-Python — без
зависимости от системных пакетов (Pango/Cairo/Tesseract и т.п.),
чтобы сборка Docker-образа была быстрой и одинаково стабильной
локально и на Railway.

## Структура

```
app/
├── main.py               ← точка входа (объект app, app.main:app)
├── database.py            ← подключение к БД, init_db(), seed_constants(),
│                            _ensure_is_deleted_columns() — миграции для
│                            полей, добавленных в модель ПОСЛЕ первого
│                            деплоя таблицы на Postgres (см. app/engine/ENGINE.md)
├── version.py              ← APP_VERSION, верхнее меню
├── models/                  ← модели SQLModel, 1 класс-таблица = 1 файл
├── engine/                   ← универсальный CRUD/drill-down движок —
│   │                         вся логика списков/форм/API генерируется
│   │                         декларативно из TableConfig, НЕ через
│   │                         отдельные роутеры на каждую таблицу
│   └── ENGINE.md                ← как устроен движок, все примитивы
├── documents_chain/            ← страница "Цепочка документов"
├── invoice_print/               ← печатные формы счёта (PDF, Excel)
├── processors/                   ← разовые серверные обработчики (/processors)
├── static/, templates/
docs/
└── HANDOFF.md              ← передача контекста между рабочими сессиями
entity_registry.md           ← полный реестр таблиц/полей по факту кода
```

Подробное описание всех таблиц, их полей и связей — в
`entity_registry.md`. Как устроен и расширяется CRUD-движок — в
`app/engine/ENGINE.md`. Оба обновляются по факту изменений кода, не
задним числом.

## Обновление проекта

Разработка ведётся с мобильного телефона. Обновления заливаются
архивом (`.zip`) в папку `ai-updates/`. GitHub Actions автоматически:
1. Разворачивает архив в staging
2. Тестово поднимает приложение и проверяет `/health`
3. При успехе — переносит изменения в репозиторий и коммитит
4. Присылает уведомление в Telegram о результате

Railway запускает независимый автобилд по тому же пушу — это второй,
не связанный с Actions процесс; при первом появлении нового файла в
репозитории они иногда стартуют не синхронно (см. `docs/HANDOFF.md`
при диагностике "build failed: file not found" на новых файлах —
чаще всего это гонка, а не баг).

## Проверка после деплоя

Открыть `/` — должна показаться страница с подтверждением, что
приложение живо и видит (или не видит) переменную `DATABASE_URL`.

Открыть `/health` — должен вернуться `{"status": "ok"}`.
