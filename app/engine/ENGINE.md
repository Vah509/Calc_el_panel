# Универсальный CRUD-движок

Генерирует страницу списка + модалку редактирования (Alpine.js) и
JSON API по одному декларативному описанию таблицы (`TableConfig`).
Заменяет ручное написание `*_api.py` + `*_alpine.html` на каждую
новую сущность справочника.

Текущее состояние: v21. Активные страницы движка — `/material-v2`,
`/brand-v2`. Старые ручные страницы (`/materials`, `/brands`,
`/materials-alpine`, `/brands-alpine`) оставлены нетронутыми рядом,
на живой БД, ничего не удалялось.

## Файлы

| Файл          | Отвечает за |
|---------------|-------------|
| `config.py`   | Датаклассы конфигурации: `TableConfig`, `FieldConfig`, `ComputedPair`, `Relation`, `FormRow` |
| `formulas.py` | Формулы пересчёта (без `eval`), продублированы в Python и в JS (`ENGINE_FORMULAS` внутри `page.py`) — должны совпадать |
| `api.py`      | Фабрика JSON-роутера: `GET/POST/PUT/DELETE /api/{key}` по `TableConfig` |
| `page.py`     | Рендер HTML-страницы (список + модалка) через Jinja + Alpine.js |
| `tables.py`   | Реальные описания таблиц (`material_table`, `brand_table`, …) |
| `register.py` | Регистрация всех таблиц движка в приложении (роутеры + страницы) |
| `page_router.py` | Подключение `/{key}-v2` страниц к FastAPI |

## Как добавить новую таблицу

1. Модель SQLModel уже должна существовать в `app/models/`.
2. В `tables.py` создать `TableConfig(...)` — см. `material_table`
   как самый полный пример (relation, computed pair, form_rows,
   search toggles).
3. Зарегистрировать конфиг в `register.py` (один вызов).
4. Страница и API появляются автоматически на `/{key}-v2` и
   `/api/{key}` — руками ничего больше не пишется.

Наименование полей/функций/таблиц согласуется с Вахтангом до того,
как попадает в код — особенно если есть неоднозначность в русском/
английском переводе.

## `FieldConfig` — все опции

```python
FieldConfig(
    name="short_name",        # имя атрибута модели
    label="Short name",       # подпись в форме/списке (рус.)
    widget="text",            # "text" | "number" | "select"
    required=True,             # обязательное — проверяется на бэке (422) и на фронте (до отправки)
    placeholder="ABB S203 C16",
    in_list=True,               # показывать колонкой в таблице списка
    list_width="22%",           # ширина колонки списка
    searchable=True,            # участвует в q=... поиске
    is_numeric=False,           # выравнивание по правому краю + .toFixed(2) в списке
    in_form=True,                # показывать в форме модалки
    form_width="140px",          # фиксированная ширина поля в форме;
                                   # без этого поле растягивается на всю ширину ряда
    default=20.0,                 # значение по умолчанию при создании новой записи
    search_toggle=True,           # см. раздел "Галочки поиска" ниже
)
```

## `ComputedPair` — пересчитываемые пары полей

Пример — цена без/с НДС в `material_table`:

```python
ComputedPair(
    field_a="price_excl_vat",
    field_b="price_incl_vat",
    rate_field="vat_rate",
    formula="vat",              # ключ в formulas.py и в ENGINE_FORMULAS (JS)
    label_a="Цена без НДС",
    label_b="Цена с НДС",
    label_rate="Ставка НДС",
)
```

Логика:
- Изменение `field_a` пересчитывает `field_b` (и наоборот) через
  формулу `forward`/`backward`.
- Если `rate_field` пуст или равен 0 — пересчитать нельзя. Это
  проверяется **и на фронте** (`validateBeforeSave()`, до отправки —
  человек сразу видит причину в баннере модалки), **и на бэке**
  (`_apply_computed_pairs` в `api.py`, второй источник истины,
  возвращает `422` с тем же текстом ошибки).
- Формула обязана быть реализована явно в обоих местах — в
  `formulas.py` (Python) и в `ENGINE_FORMULAS` внутри `page.py`
  (JS-блок страницы). `eval` нигде не используется.

## `FormRow` — порядок и группировка полей формы

По умолчанию (без `form_rows`) каждое поле — отдельная строка формы,
в порядке объявления в `config.fields`.

`form_rows` группирует несколько полей в один визуальный ряд:

```python
form_rows=[
    FormRow(field_names=["brand_id", "sku_article"]),
    FormRow(field_names=["price_excl_vat", "price_incl_vat", "vat_rate"]),
]
```

Раскладка строится в Python (`_build_form_layout()` в `page.py`) до
рендера — идёт по `config.fields` строго по порядку, и если поле
входит в ещё не отрисованный `FormRow`, выводит весь ряд целиком
(в порядке `field_names` этого ряда), иначе — как одиночную строку.
Поля с `in_form=False` пропускаются полностью. Ряд, где хотя бы одно
поле участвует в `computed_pairs`, получает класс `.price-pair`
(визуально выделен фоном) — остальные многополосные ряды получают
`.field-row`.

Ширина конкретного поля внутри ряда задаётся через `form_width` на
`FieldConfig` (inline `style="flex: 0 0 <width>"`, побеждает CSS-класс
по каскаду). Без `form_width` поле растягивается наравне с соседями
по ряду (`flex: 1 1 140px`).

## Галочки поиска (`enable_search_toggles`)

Общая возможность движка, включается на уровне таблицы:

```python
TableConfig(
    ...,
    enable_search_toggles=True,
)
```

Когда включено — под строкой поиска показываются чекбоксы "искать по
<label>" для каждого поля с `searchable=True` **и** `search_toggle=True`
(значение по умолчанию). Поле с `searchable=True, search_toggle=False`
(например артикул у материалов) ищется всегда, без отдельного
чекбокса — управлять им нельзя, но из общего поиска не выпадает.

По умолчанию, при открытии страницы, все чекбоксы включены — то есть
поведение идентично обычному поиску по всем `searchable` полям, пока
пользователь явно что-то не отключит.

Механизм на бэкенде: `GET /api/{key}?q=...&search_fields=short_name&search_fields=full_name`.
- `search_fields` не передан → ищет по всем `searchable` полям (старое
  поведение, обратная совместимость).
- `search_fields` передан → берётся пересечение с `searchable_fields()`
  таблицы (защита от поиска по произвольному полю модели через
  query-параметр) и ищет только по нему.

## Тестирование изменений движка

Из-за мобильной разработки (см. README) все правки движка
прогоняются локально через `TestClient` до сборки архива —
`bash_tool` + `fastapi.testclient.TestClient(app)` в режиме
контекст-менеджера (см. корневой `context_handoff_*.md` за пояснением
почему именно так, а не через background uvicorn).

## Известные ограничения / на будущее

- `brand_id` в `list_items()` — единственный явный relation-фильтр
  в query. При появлении второго relation-поля в какой-либо таблице
  нужно обобщить до произвольного набора `?field=value` по всем
  `config.relations`, а не хардкодить имя параметра.
- Документация по чекбокс-поиску только для материалов — если
  понадобится второй-третий toggleable relation-фильтр (не поиск, а
  именно чекбоксы над списком), это отдельная, ещё не спроектированная
  фича.
- MkDocs с Material theme — возможный будущий вариант оформления этой
  папки в сайт, не реализовано, текущая структура `.md` уже с ним
  совместима при необходимости.
