# Как работает деплой (process-update.js) + sitemap.xml

Актуально станом на: 2026-09-26 (повна ревізія — звірено з реальним кодом
усіх модулів `scripts/`, а не лише з описом одного файлу)

---

## Коротко, суть

Раніше `sitemap.xml.ts` сам рахував `git log` під час білду на Cloudflare
Pages — для кожної сторінки окремо, прямо в момент генерації XML. Зараз це
прибрано. Дати рахуються один раз — у GitHub Actions, під час обробки
чергового ZIP-архіву — і зберігаються у звичайний JSON-файл
`src/data/lastmod-map.json`. `sitemap.xml.ts` більше не звертається до git
взагалі — він просто читає цей готовий файл.

---

## Структура скрипта деплою (модулі `scripts/`)

Оркестратор — `scripts/process-update.js`. Він імпортує та викликає окремі
модулі з `scripts/lib/`, кожен відповідає за один крок:

| Модуль | Відповідальність |
|---|---|
| `lib/read-archive.js` | Читає список файлів усередині щойно завантаженого ZIP |
| `lib/lastmod.js` | Рахує карту дат оновлення (`computeLastmodMap`, `applyArchiveDatesOverride`, `writeLastmodMap`) |
| `lib/staging.js` | Керує тимчасовою «пісочницею»: `createStaging`, `applyArchiveToStaging`, `promoteToRepo`, `cleanupStaging` |
| `lib/optimize-photos.js` | Перевіряє/стискає фото з архіву (Node.js + бібліотека `sharp`) |
| `lib/test-build.js` | Запускає тестову збірку Astro (`npm run build`) усередині staging |
| `lib/send-telegram.js` | Формує і надсилає обидва Telegram-повідомлення |

## Що робить process-update.js, крок за кроком (звірено з кодом)

Спрацьовує автоматично, коли в `ai-updates/` з'являється новий `.zip`
(запускається з `.github/workflows/unzip-and-update.yml` одним рядком
`node scripts/process-update.js`).

1. **Знаходить ZIP** у `ai-updates/`. Якщо архіву немає — завершується без дій.
2. **Читає список файлів усередині архіву** (`readArchiveFileList`) — для
   звіту в Telegram і для подальшого розрахунку дат.
3. **Рахує карту дат (`computeLastmodMap`)** — за реальною git-історією
   репозиторію, **ДО** того, як архів щось змінить. Скануються рекурсивно:
   `src/pages`, `src/pages/posluhy-ta-produktsiia`, `src/pages/ru` (усі
   RU-сторінки), та `src/content/vykonani-roboty` (карточки `.md`).
   Динамічні роути (файли, що починаються з `[`) пропускаються — для них
   lastmod не рахується. Якщо в файлу взагалі немає git-історії —
   підставляється сьогоднішня дата як фолбек, а лічильник `gitFailures`
   зростає (для звіту в консоль).
4. **Примусово підставляє сьогоднішню дату (`applyArchiveDatesOverride`)**
   для файлів `.astro`/`.md`, які Є у списку архіву — незалежно від того,
   що показав git log. Причина: якщо рахувати дати вже ПІСЛЯ того, як файли
   з архіву потрапили в репозиторій, але ДО коміту — git ще не бачить
   сьогоднішній коміт (його ще не було), тож видав би СТАРУ дату замість
   сьогоднішньої.
5. **Створює staging-копію проекту** (`createStaging`) — `cp -a` всього
   репозиторію в `/tmp/em-staging`, окремо видаляючи `.git` (staging не
   потребує git-історії, тестова збірка Astro нею не користується).
6. **Розпаковує архів поверх staging** (`applyArchiveToStaging`) — `unzip -o`.
   Реальний репозиторій на цьому кроці ще не чіпається.
7. **Перевіряє/оптимізує фото** (`optimizePhotos`) — тільки `.jpg`/`.jpeg`
   зі списку архіву:
   - ширина ≤ 1200px → вважається вже оптимізованим, залишається як є (звіт: «ОК»)
   - ширина > 1200px → стискається до 1200px (`withoutEnlargement: true`),
     якість JPEG **85**, звіт по кожному файлу: розмір до → після, статус «ОПТ»
   - помилка аналізу файлу → окремий рядок з текстом помилки, обробка інших
     файлів продовжується
8. **Надсилає ПЕРШЕ повідомлення в Telegram** — що змінилось (список файлів
   з архіву) + звіт по фото.
9. **Пробує зібрати сайт** (`npm run build`, `testBuild`) усередині staging.
10. **Якщо збірка ОК:**
    - записує вже готову карту дат у `staging/src/data/lastmod-map.json`
      (`writeLastmodMap`) — щоб вона поїхала в реальний репозиторій разом з
      рештою файлів архіву, одним набором змін, без окремого коміту
    - переносить staging → реальний репозиторій (`promoteToRepo`): `cp -a`,
      з тимчасовим винесенням `dist/` і `node_modules/` за межі копіювання
      (бо `cp -a` не має `--exclude`) і поверненням їх назад після
    - надсилає друге Telegram-повідомлення: 🟢 успішно

    **Якщо збірка НЕ ОК:**
    - реальний репозиторій НЕ змінюється взагалі — ні файли, ні дати
    - надсилає друге Telegram-повідомлення: 🔴 помилка збірки, з текстом помилки
11. **Видаляє оригінальний ZIP з `ai-updates/`** — це відбувається ЗАВЖДИ,
    незалежно від результату збірки чи навіть несподіваної помилки на
    будь-якому з попередніх кроків. Гарантується структурою `try/finally`
    навколо всієї логіки в `main()`, а не просто порядком рядків коду.
12. **Прибирає staging-директорію** (`cleanupStaging`) — так само гарантовано,
    у `finally`.

Скрипт завершується з кодом виходу `0` при успіху, `1` при провалі білду
АБО при будь-якій несподіваній помилці — щоб workflow міг через
`if: success()` коректно розгалужити подальші кроки (коміт) без потреби
парсити вивід.

Далі (поза цим скриптом, окремим кроком у workflow, лише якщо білд був
успішним) — одразу йде `git add`/`commit`/`push`. Окремого кроку
«Generate lastmod map» у workflow немає — карта дат рахується всередині
`process-update.js` і їде разом з іншими файлами одним комітом.

## Формат lastmod-map.json

```json
{ "src/pages/kontakty.astro": "2026-07-23", "...": "..." }
```

Ключ — repo-relative шлях до файлу (той самий формат, що читає
`sitemap.xml.ts`), значення — дата `YYYY-MM-DD`.

## Що робить sitemap.xml.ts зараз (звірено з кодом файлу)

Під час білду на Cloudflare Pages:

1. Збирає список усіх сторінок сайту через `import.meta.glob`:
   верхній рівень (`src/pages/*.astro`), продукція
   (`posluhy-ta-produktsiia/*.astro`), індекс портфоліо
   (`vykonani-roboty/index.astro`), усі RU-сторінки (`ru/**/*.astro`)
2. Картки портфоліо додаються окремо через `getCollection('vykonani-roboty')`
3. Виключає за іменем файлу: `admin_509`; за повним `urlPath`:
   `ru/vykonani-roboty` (заглушка без карток — свідомо не в sitemap, хоч і
   доступна за URL)
4. Виключає динамічні роути (імена файлів, що починаються з `[`)
5. Дедублікація за `urlPath` — лишається перше входження
6. Для кожної сторінки бере `lastmod` не з git, а напряму з готового файлу
   `src/data/lastmod-map.json`
7. Якщо для якогось файлу запису в мапі раптом немає — підставляє дату
   білду як запасний варіант, щоб sitemap ніколи не зламався

Переваги такого підходу:
- Cloudflare більше не залежить від git під час білду
- Дати для щойно оновлених сторінок завжди коректні — сьогоднішні, а не з
  попереднього коміту
- Один файл-джерело правди для дат, який видно і можна перевірити окремо
  від самого sitemap
