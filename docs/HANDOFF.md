# HANDOFF

## Состояние

Работает: универсальный CRUD-движок (`app/engine/`) — `config.py`, `formulas.py`, `api.py`, `page.py`, `tables.py`, `register.py`. Активные страницы: `/material-v2`, `/brand-v2`. Старые страницы работают параллельно, не тронуты.

Последнее изменение: v19–v20 — форма модалки (`_build_form_layout`), валидация обязательных полей, равная ширина полей формы, баннер ошибки внутри модалки.

Этот разговор был обсуждением архитектуры без написания кода — зафиксирован план на следующий блок.

## Сделано в этой сессии

Ничего не кодировали — только договорились о плане. Ключевые решения:

1. **Справочник `constants`** — новая таблица, key-value. Первые константы: `vat_rate` (сейчас 20%), `default_page_size` (лимит строк по умолчанию в списках). НДС хранится ТОЛЬКО здесь, не per-material — материал ссылается на константу, показывает её read-only в карточке, не хранит своё значение.

2. **Пагинация / лимит строк** — не полноценная постраничная навигация, а параметр `default_page_size` из справочника constants, ограничивающий число строк в списке. Регулируемость (кнопки вперёд/назад) — возможно потом, не сейчас.

3. **Soft-delete** — флаг `is_deleted` вместо физического удаления. ВАЖНО: это только визуальный маркер, НЕ фильтр видимости — записи, помеченные на удаление, продолжают отображаться во всех обычных списках/выборках (перечитываются всегда), пока не будут физически удалены отдельным скриптом очистки. Никакого `WHERE is_deleted = False` в `list_items` не ставим. Совпадает с уже действующим принципом статуса `deleted` у материалов/брендов/китов — просто распространяется на движок как общий флаг. Нужно:
   - `TableConfig.soft_delete: bool`
   - API `delete_item` — ставить флаг, не удалять физически
   - API `list_items` — без изменений в фильтрации, помеченные записи остаются в выдаче
   - Модели (material, brand) — добавить поле `is_deleted`
   - UI — иконка/маркер статуса в первой колонке списка (активна / помечена на удаление), чтобы визуально отличать
   - Отдельно (не в этом блоке) — скрипт физической очистки: проходится по помеченным записям и удаляет насовсем. Без этого скрипта данные не должны удаляться из базы вообще.

4. **Bulk-recalculate обработчик** — универсальный механизм: пользователь выбирает таблицу + одну или несколько функций пересчёта из списка, жмёт выполнить — обработчик прогоняет выбранные функции по всем строкам таблицы. Функции — простые, отдельные, добавляются по мере необходимости (по аналогии с `formulas.py`). Первая функция: пересчёт `price_incl_vat` по текущей `vat_rate` из constants. Второй пример на будущее (не делать сейчас): `increase_price_pct` — поднять цены на X%.
   - Важно: пересчёт живых данных (материалы) не обновляет автоматически уже созданные документы (калькуляции/спецификации/счета) — они остаются со старой ценой до следующего обращения/пересчёта документа. Это ожидаемое поведение, соответствует принципу "live reference vs snapshot".

## Открыто

**Порядок реализации на следующий блок (зафиксирован, идём по порядку, НЕ делать всё разом):**
1. `constants` — новая таблица через движок (TableConfig + register). Простой шаг, от него зависят 3 и 4.
2. (пропущено намеренно — см. ниже, лимит строк объединён с шагом 1 по факту малого объёма, либо сразу за ним)
3. Soft-delete — трогает TableConfig, API, обе существующие модели (material, brand). Тестировать изолированно. Помнить: без фильтрации видимости, см. выше.
4. Bulk-recalculate — зависит от constants (vat_rate) и от soft-delete. Решено: пересчитывать ВСЕ позиции наравне, включая помеченные на удаление — они всё ещё используются в текущих документах, и при обновлении документа нужны актуальные данные. Пометка на удаление не исключает из расчётов, только сигнализирует "не создавать новых ссылок". Физическое удаление — отдельная задача, с проверкой зависимостей (на что позиция ссылается), чтобы не порвать документы; не часть этого блока.

Каждый пункт — свой архив, свой APP_VERSION, тест на устройстве между шагами.

**Отложено осознанно (не поднимать без явного запроса):**
- Зависимые таблицы (kits/kit_items) — решено, что это будет ОТДЕЛЬНАЯ полноценная страница-карточка (не голый список пар, не мелкий инлайн-виджет): открываешь конкретный кит, видишь его название и редактируемый состав внутри. Актуально, когда дойдём до комплектов, не сейчас.
- Роли / RBAC — второго пользователя пока нет физически, таблицы `users` не существует. Когда появится: нужна модель `users` с полем `role`, `RoleChecker`-dependency на эндпоинтах `create_item`/`update_item`/`delete_item`, поля `min_role_to_edit`/`min_role_to_delete` в `TableConfig`, скрытие кнопок в UI по роли. Права разграничиваются на уровне ОПЕРАЦИЙ (создать/удалить), не на уровне видимости данных — справочники (материалы, бренды, константы) остаются общими для всех пользователей. Видимость по владельцу (`owner_id`) может понадобиться только для документов (заказы/счета) — это отдельный, более поздний шаг, не часть базового RBAC.
- Валидация уникальности (например SKU) — отдельный скрипт вне движка, не сейчас, ID и так делает записи различимыми технически.
- Массовые операции (bulk delete/update через чекбоксы в UI) и экспорт CSV — low priority, не поднимать без запроса.
