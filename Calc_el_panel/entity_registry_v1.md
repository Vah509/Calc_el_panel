# Реестр сущностей — ЭлектроЩит

Единый источник правды по факту реального кода (не по плану из спеки).
Обновляется тем же шагом, где менялся код. Расхождения код/спека
фиксируются явно, не молча — см. раздел внизу.

Формат: один файл на предметную область, внутри — три слоя вместе
(данные / функции / представление) — тот же разрез, что и в коде.

---

## Материалы (Шаг 1)

### Фактическая структура файлов

```
app/
├── __init__.py
├── database.py         ← подключение к БД, get_session(), init_db()
├── main.py               ← точка входа, подключение роутеров, /health
├── models/
│   ├── __init__.py
│   ├── brand.py           ← класс Brand
│   └── material.py         ← класс Material
├── routers/
│   ├── __init__.py
│   └── materials.py         ← CRUD-эндпоинты + recalc_prices()
├── static/
│   └── style.css
└── templates/
    ├── base.html
    └── materials/
        ├── list.html         ← список + поиск
        ├── _form.html         ← фрагмент формы (create/edit)
        └── _row.html           ← фрагмент строки таблицы (для HTMX)
```

Паттерн: 1 класс-таблица = 1 файл в `models/`. Логика живёт в роутере
(`routers/materials.py`), отдельного слоя "функции без HTTP" пока нет —
на текущем масштабе это оправдано.

### Таблицы и поля

#### `brand`
| Поле | Тип | Назначение |
|---|---|---|
| id | int, PK | |
| name | str, unique, indexed | Уникальное название бренда |

⚠️ В спеке есть ещё `is_universal` (флаг спецбренда "Universal") — в коде
пока нет, добавляется при работе над комплектами (шаг 5).

#### `material`
| Поле | Тип | Назначение |
|---|---|---|
| id | int, PK | |
| short_name | str, indexed | Укороченное имя, для поиска |
| full_name | str | Полное имя (для документов) |
| brand_id | int, FK → brand.id, nullable | |
| sku_article | str, indexed, nullable | Артикул производителя |
| price_excl_vat | float | Цена без НДС |
| price_incl_vat | float | Цена с НДС |
| vat_rate | float, default 20.0 | Ставка НДС |
| owner_id | int, indexed, nullable | Задел под многопользовательскую модель |

Валютные поля (`price_excl_vat_supplier`, `currency_quote_id` и т.д.),
`category_id`, `tree_node_id` — ещё нет, появляются на шагах 3a/3b.

### Функции

| Функция | Файл | Что делает |
|---|---|---|
| `recalc_prices()` | routers/materials.py | Взаимный пересчёт цены по changed_field, без сессии БД — чистая функция |
| `list_materials()` | routers/materials.py | GET /materials — список + фильтр по q/brand_id |
| `new_material_form()` | routers/materials.py | GET /materials/new — пустая форма |
| `edit_material_form()` | routers/materials.py | GET /materials/{id}/edit — форма с данными |
| `create_material()` | routers/materials.py | POST /materials — создать + вернуть обновлённый список |
| `update_material()` | routers/materials.py | PUT /materials/{id} — изменить + вернуть список |
| `delete_material()` | routers/materials.py | DELETE /materials/{id} — удалить (физически! статусная модель из 4.3 ещё не применена) |
| `init_db()` | database.py | Создаёт таблицы при старте, если их нет |
| `get_session()` | database.py | FastAPI Depends — сессия БД на запрос |

⚠️ Текущее удаление — физическое (`session.delete`). Спека (4.3) требует
статусную модель (`status = deleted` как пометка, не физическое
удаление). Не противоречит текущему коду (шаг 1 был простым
CRUD-скелетом), но нужно будет заменить на soft-delete, когда дойдёт
очередь до статусной модели.

## Известные расхождения код ↔ спека

| Что | В коде | В спеке | Решение |
|---|---|---|---|
| Имя поля артикула | `sku_article` | `sku` | **Правим спеку** — `sku_article` читабельнее, оставляем как в коде |
| Структура моделей | `models/` — папка, файл на класс | единый `database/models.py` | **Правим спеку** — папка читабельнее на масштабе 14 таблиц |

Критерий принятия решения при расхождении код/спека (согласовано с
пользователем): приоритет — чистый, читаемый, функциональный код,
универсальность и лёгкость/быстрота доработки. Спецификация может не
всё учитывать и подлежит правке, если код лучше. Каждый случай
обсуждается отдельно, не подгоняется автоматически.
