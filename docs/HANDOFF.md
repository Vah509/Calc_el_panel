**Прод-баг №4 (2026-08-31, найден по Deploy Logs сразу после первого
использования кнопки «Скачать PDF» на реальном счёте):**
`amount_in_words.py::_int_to_words` делил число только на ДВЕ тройки
(тисячі + одиниці) — `thousands = n // 1000` без ограничения сверху.
На сумме ≥ 1 000 000 `thousands` само оказывалось ≥1000, и
`_three_digit_words(thousands, ...)` получало `h = thousands // 100`
≥ 10 → `IndexError: list index out of range` на `_HUNDREDS[h]` (у
`_HUNDREDS` всего 10 элементов, индексы 0-9). Тестовые случаи при
разработке v91 не превышали 105 532 — диапазон ошибки просто не был
перекрыт тестами.

**Исправление**: разбивка на тройки теперь рекурсивная — мільйони /
тисячі / одиниці, каждая тройка независимо 0-999 перед передачей в
`_three_digit_words`. Добавлено склонение «мільйон/мільйони/
мільйонів» (`_million_form`, та же грамматика 1/2-4/5+, что у
`_thousand_form`). Диапазон ДЕСЯТКОВ миллионов и выше (`_HUNDREDS`
покрывает только 0-999 в самой верхней тройке тоже) — уже проверен
тестами до 100 000 000, этого достаточно для реалистичных сумм
счёта; если когда-то понадобятся миллиарды — тот же рекурсивный
паттерн масштабируется тривиально (добавить ещё один уровень
`billions, rem = divmod(rem, 1_000_000_000)` перед millions).

Урок на будущее (общий с остальными прод-багами проекта, см. общий
принцип «SQLite vs Postgres trap» — здесь тот же КЛАСС проблемы,
просто не БД, а диапазон входных данных): числовые/грамматические
хелперы с ручным разбором по диапазонам нужно тестировать на
ГРАНИЧНЫХ значениях (999, 1000, 999999, 1000000, 999999999,
1000000000...), а не только на одном примере из образца — один
удачный тест-кейс (105532.44 из СФ-0000040) не гарантирует
корректность на порядок величины больше.

## Сделано в этой сессии

1. Диагностика по Deploy Logs Railway (Postgres) — traceback указал
   точную строку (`app/invoice_print/amount_in_words.py:38,
   words.append(_HUNDREDS[h])`), без логов пришлось бы гадать между
   несколькими гипотезами (Postgres-типы, оборванные FK-цепочки,
   отсутствие Firm и т.д.) — все они технически валидны, но
   реальная причина оказалась третьей, не связанной с БД вообще.
2. `_int_to_words` переписан на рекурсивную разбивку по тройкам
   (мільйони/тисячі/одиниці), добавлен `_million_form`.
3. Тест на воспроизведение точного прод-сценария (сумма 1234567.89,
   полный цикл request→calculation→specification→invoice→PDF через
   `TestClient`) — ДО фикса падал так же, как на проде, ПОСЛЕ фикса
   зелёный, PDF визуально проверен (корректная грамматика: «Один
   мільйон чотириста вісімдесят одна тисяча чотириста вісімдесят
   одна гривня 47 копійок»).
4. Расширенный набор ручных проверок `amount_in_words_uk` — весь
   диапазон от 0 до 100 000 000, включая точные границы тройок
   (999999.99, 1000000.00, 2000000.00 для проверки формы
   «мільйони»).
