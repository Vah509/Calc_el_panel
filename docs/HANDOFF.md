# HANDOFF

## Состояние

**v83 — автопересчёт вкладки "Стоимость" калькуляции на клиенте.**

Разбирали баг: у заявки R-000009 спецификации вариантов 2/3 показывали
сумму 0, хотя на этих слотах есть активные калькуляции. Проверка по
скриншотам показала — это НЕ баг спецификации (обработчик сборки
работал верно), а забытое нажатие кнопки "Пересчитать" у калькуляций
К-000004/К-000003: их `final_total` был честно 0, спецификация просто
взяла то, что было. Решение Вахтанга: раз кнопку легко забыть — сделать
пересчёт стоимости автоматическим при изменении состава, а кнопку
"Пересчитать" оставить (она ещё и подтягивает свежие цены из
справочника материалов — то, что клиент без сетевого запроса не может).

## Сделано в этой сессии

- `app/engine/page.py`:
  - `round2()` — новый общий JS-хелпер округления до 2 знаков (рядом с
    `applyFormula`), выделен из уже существующих разрозненных
    `Math.round(x * 100) / 100`
  - Новые computed-геттеры на форме calculation (рядом с
    `materialsTotal`/`kitsTotal`): `liveBaseTotal`, `liveInsuredTotal`,
    `liveMarkupTotal`, `liveHourlyRate`, `liveHoursTotal`,
    `liveFinalTotal` — ЗЕРКАЛО формулы `_recalc_cost_totals`
    (app/engine/tables.py) на клиенте, работают ЦЕЛИКОМ реактивно от
    `materialsTotal`/`kitsTotal`/`editing.insurance_markup`/
    `editing.markup_percent`/`editing.assembly_hours`/
    `editing.product_type_rate_id`/`editing.cost_method`.
    `liveHourlyRate` берёт ставку из уже загруженного
    `relationOptions.product_type_rate_id` (тот же приём, что
    `brand_slot_labels` берёт бренд из `relationOptions.request_id`) —
    без похода на сервер
  - `applyLiveCostTotals()` — пишет посчитанные `live*` значения в
    `editing.materials_total/kits_total/base_total/insured_total/
    markup_total/hours_total/final_total`, чтобы они отражались в
    полях формы и уходили в БД при "Сохранить" тем же путём, что и
    после ручного "Пересчитать"
  - Вкладка "Стоимость" формы calculation — добавлен скрытый
    `<div x-effect="applyLiveCostTotals()">`: Alpine сам отслеживает
    все реактивные зависимости внутри метода и перезапускает его при
    любом изменении состава материалов/комплектов или полей
    стоимости — без кнопки, без запроса к серверу
  - Кнопка "Пересчитать" (materials/kits/cost вкладки) — НЕ убрана,
    осталась ручным дублирующим действием ради подтяжки актуальных
    цен из справочника материалов (то, чего клиентский автопересчёт
    сознательно не делает — см. комментарий у
    `_recalc_material_prices_handler`)
  - `pick_final_total` (CLIENT_ACTIONS, переключатель cost_method) —
    оставлен как есть, не мешает: пишет то же самое значение, что
    теперь параллельно пишет `applyLiveCostTotals()`
- `app/version.py` — `APP_VERSION = "v83"`
- Тестирование: `TestClient` регрессия — `/calculation-v2`,
  `/request-v2`, `/specification-v2` — 200. Логика клиентского JS не
  покрыта TestClient (это браузерный Alpine-код) — нужна проверка
  вживую на телефоне: открыть калькуляцию с материалами, поменять
  количество/добавить позицию, убедиться что "Итоговая стоимость" на
  вкладке "Стоимость" меняется СРАЗУ без нажатия "Пересчитать"
