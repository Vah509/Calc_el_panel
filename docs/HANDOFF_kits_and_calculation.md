## 0. Комплекты (kit) — ЗАВЕРШЕНО, код в проде

`kit_group → kit_section → kit → kit_items`, включая полноэкранный
MaterialPicker для редактирования состава. Полностью реализовано и
задеплоено, актуальная версия — см. docs/HANDOFF.md. Здесь не описывается
детально — это уже не проектирование, а готовый код.

Единственный принцип оттуда, который важен для калькуляции: калькуляция
хранит ССЫЛКУ на kit (`kit_id`), не снимок состава — при пересчёте состав
комплекта разворачивается заново на текущий момент ("live", не snapshot).
Комплекты можно только soft-delete (не физически) из-за возможных ссылок
на них из калькуляций.

## 2. Модель документооборота (спроектировано, код НЕ писался)

Цепочка: **zayavka → calculation → specification → invoice → (product)**

### 2.1 Порядок реализации (решено, не менять без причины)
1. `zayavka` — базовая таблица, простой CRUD-документ (без кнопок
   формирования спецификации на этом шаге)
2. `calculation` — с реальным FK `request_id` → zayavka (не заглушка);
   попутно, при сохранении calculation — создание/обновление записи в
   `product` (см. 2.5)
3. `calculation_item` — материалы/комплекты внутри калькуляции, движок
   пересчёта
4. `specification` + `specification_item` — снимок по варианту, три кнопки
   формирования в zayavka

### 2.2 Таблица `zayavka` (заявка)
Поля (английские имена черновые, финально согласовать при кодировании):
- `client_id` (FK на клиента) — кто оформляет заявку
- `client_invoice_id` (FK на клиента, nullable, по умолчанию = client_id) —
  на кого выставляется счёт, если отличается от оформителя
- `brand_slot_1`, `brand_slot_2`, `brand_slot_3` — три поля, "на каком
  бренде считать вариант N" (ОТКРЫТО: FK на Brand или текст — не уточнили,
  спросить в начале кодирования)
- `is_deleted` — стандартный soft-delete проекта
- Копирование — server-side copy, как у kit
- Физическое удаление — только отдельным обходчиком/чистильщиком
- Три кнопки "Сформировать спецификацию по варианту N" (N=1,2,3),
  независимые, без общей "пересчитать всё". По нажатию: актуализация цен
  calculation этого brand_slot + полная перезапись specification этого
  варианта (delete-all+create-all, как kit_items)
- Дата/признак "когда обновлялись цены" — РЕШЕНО НЕ хранить (излишнее
  усложнение по прямому решению Вахтанга)

**ОТКРЫТО, уточнить в начале кодирования:** уже существует ли таблица
Client в проекте, или создавать с нуля вместе с zayavka.

### 2.3 Таблица `calculation` (калькуляция)
Одно изделие — один вариант (один brand_slot) в рамках одной заявки.
- `request_id` — реальный FK на zayavka
- `brand_slot` (1/2/3) — группирующий признак вариантов внутри заявки
  (совпадает по смыслу с `brand_slot_N` в zayavka)
- `brand_id` (FK на бренд) — справочное поле, НЕ группирующий признак
  (группировка именно через номер слота)
- `product_name` — название изделия, вводит человек, свободный текст
- `work_name` — рабочее название, генерируется по шаблону (см. 2.4)
- `quantity` — количество этого изделия в заявке
- `status` — draft/active/archived_pending/delete_pending, точная механика
  переходов НЕ проговорена (открытый вопрос)
- `product_id` — FK на `product` (см. 2.5), один-к-одному
- строки калькуляции — `calculation_item` (материал ИЛИ kit × количество,
  см. 2.3.1). Повтор одного и того же kit в разных строках — норма, не
  дублирование-ошибка

**Логика "перепровести" (пересчитать калькуляцию):**
1) актуализируются цены материалов, 2) live-разворачивается состав
комплектов на текущий момент, 3) собирается итоговая спецификация
материалов и итоговая цена изделия. Если состав kit изменился с прошлого
пересчёта — лог/предупреждение, не молчаливая потеря/добавление строки.

#### 2.3.1 `calculation_item` (строки калькуляции) — ОТКРЫТО, детали не расписаны
Модель верхнего уровня подтверждена: одна таблица, два nullable FK
(`material_id` / `kit_id`), тип строки — по тому, какое поле заполнено.
На фронте — две вкладки "Материалы"/"Комплекты" (чисто UI-разделение, не
влияет на структуру таблицы). Точные остальные поля — решить при
кодировании этого шага.

### 2.4 Правило генерации `work_name`
- Текущее правило: `"Сборка " + product_name`
- Хранится НЕ жёстко в коде, а как настраиваемый текстовый шаблон в
  constants-таблице — чтобы в будущем добавить номер заявки/код бренда без
  правки кода
- Автоген с возможностью РУЧНОГО переопределения: если человек вручную
  поправил work_name — флаг "переопределено", авторасчёт больше не
  перезаписывает поле, пока флаг не сброшен

### 2.5 Таблица `product` (журнал изделий для поиска)
Назначение: чтобы через долгое время можно было найти изделие по названию
+ примерному клиенту, не разбираясь, на какой стадии документооборота оно
находится. Плоский справочник по тому же принципу, что `material` —
обычная таблица движка с текстовым поиском по полям.

**Механика связи с calculation (один-к-одному, calculation → product):**
- При каждом сохранении `calculation` — создаётся (если нет) или
  обновляется (если есть) соответствующая запись `product`. Направление:
  calculation ТОЛКАЕТ обновления в product — не наоборот, product не тянет
  live-данные при обращении (в отличие от specification/kit)
- `calculation.product_id` — FK хранится на стороне calculation
- Запись product живёт, пока жива сама calculation
- **ОТКРЫТО:** что происходит с product при удалении calculation — прямо
  отложено Вахтангом ("отдельная процедура, подумаем отдельно"). Не
  реализовывать удаление calculation, пока это не обсуждено
- Запись может никогда не понадобиться для поиска — это ок, создаётся как
  задел на будущее, не по требованию

**Примерные поля (не финализированы):**
`name`/`work_name`, `client_name`, `calculation_id` (обратная ссылка для
провала в историю расчёта), `price` (на момент последнего сохранения
calculation), возможно `status`.

**Важно:** это заменяет собой более раннее представление о `finished_products`
как отдельной таблице только для физически готовых/отгруженных изделий.
Вместо этого — единая таблица `product`, живущая с первого сохранения
calculation. Открыт вопрос: нужно ли отдельное поле-статус "физически
готово/отгружено" внутри той же product, или это будет отдельная сущность
поверх product — решить ближе к работе над invoice.

Реализация `product` — НЕ отдельный шаг, подключается как побочный эффект
при кодировании calculation (шаг 2 в разделе 2.1).

### 2.6 Таблица `specification` + `specification_item`
Промежуточный документ между calculation и invoice. Назначение: перечень
изделий одного варианта не всегда переносится в счета 1-в-1 — из одной
спецификации может быть создано НЕСКОЛЬКО счетов-фактур (например, из 5
изделий сначала счёт на 3, потом на 2). Спецификация даёт стабильную базу
для такой гибкой нарезки.

Из-за этого — ЭТО СНИМОК, не live-ссылка (в отличие от kit_items).
Обоснование: если бы цена была live и калькуляцию пересчитали после того
как часть спецификации уже нарезали на выставленный счёт — счёт задним
числом "поехал" бы в цене, что недопустимо для финансового документа.

**`specification`:** `zayavka_id` (FK), `brand_slot` (1/2/3)

**`specification_item`:**
- `specification_id` (FK)
- `calculation_id` (FK) — НЕ для live-подтяжки цены, а чтобы при повторном
  формировании пройти по ссылкам и перечитать актуальные значения
- `product_name`, `price`, `quantity` — скопированы на момент формирования

Механика формирования (кнопка "Сформировать спецификацию по варианту N" в
zayavka): пересчитать все calculation этого (zayavka_id, brand_slot) → для
каждой взять актуальные name/price → полностью переписать
specification_item (delete-all+create-all). Между нажатиями кнопки данные
не меняются сами — чистый статичный снимок.

**ОТКРЫТО:** счёт-фактура при создании из спецификации — тоже копирует
себе данные (снимок снимка), или может сослаться на specification_item
напрямую? Вероятно тоже снимок по той же логике, но не подтверждено —
уточнить в начале работы над invoice.
