# HANDOFF

## Состояние

Работает: универсальный CRUD-движок (`app/engine/`), раздел «Обработки» (`app/processors/`), soft-delete у материалов и брендов. Активные страницы: `/material-v2`, `/brand-v2`, `/kit_group-v2` (drill-down дерево, 3 уровня: Группы → Разделы → Комплекты), `/constant-v2`, `/processors`. Верхнее меню — «Справочники» (Материалы/Бренды/Группы комплектов/Константы) и «Обработки» (Пересчёты + физическое удаление). `/kit_section-v2`, `/kit-v2`, `/kit_item-v2` — заглушки на случай прямого перехода по URL, отдельных пунктов меню на них нет.

Движок объединён: один `TableConfig` описывает и плоские таблицы (material, brand — `hierarchy=None`), и узлы дерева drill-down (kit_group, kit_section, kit — `hierarchy` заполнен). `delete_mode` — три режима: `"hard"` (kit_item — на неё ничего не ссылается, удаление позиции состава всегда безусловное и немедленное), `"soft"` (material/brand/kit — пометка + purge-processor), `"simple"` (kit_group/kit_section — физическое удаление, но только если нет дочерних записей — теперь включая проверку на «есть ли kit внутри», это подтянулось автоматически вместе с подключением kit к дереву).

`kit` — теперь настоящий 3-й, нижний уровень дерева drill-down (было временной плоской таблицей в v39/v39.1). Клик по комплекту в списке открывает МОДАЛЬНОЕ ОКНО (не отдельную страницу-карточку, как планировалось изначально в HANDOFF_kits_and_calculation.md — решение сознательно пересмотрено Вахтангом) со списком состава (`kit_item` — материал+количество). Новый `edit_mode="items_modal"` в движке: вместо обычной формы редактирования модалка показывает список дочерних записей + кнопку «Добавить» с простой формой создания. На этом шаге — ТОЛЬКО просмотр состава + добавление новых позиций; редактирование/удаление существующих позиций состава, переименование самого комплекта, полноценный подбор материалов (поиск/фильтры вместо простого select) — сознательно отложены, по прямому указанию Вахтанга («сначала всё подтянем и увидим что открывается, потом подробно обсудим функционал»).

Тема «Комплекты» (kit) продолжается — согласованная архитектура и открытые вопросы в `docs/HANDOFF_kits_and_calculation.md` (ведётся вручную, но раздел про own_page-карточку там теперь неактуален — см. решение сессии ниже).

Последнее изменение: v40 — kit подключён к drill-down дереву как 3-й уровень, модалка состава (edit_mode="items_modal").

## Сделано в этой сессии (v40 — kit как 3-й уровень дерева, модалка состава)

Контекст: после v39/v39.1 (kit/kit_item как временные плоские таблицы для ручного ввода пробных данных) Вахтанг занёс тестовые записи (2 комплекта: «Панель 150» с 2 позициями состава, «Подключение 25а» с 1 позицией) и попросил подтянуть их в дерево. По ходу обсуждения решение по способу открытия комплекта изменилось — раньше планировалась отдельная страница-карточка (`edit_mode="own_page"`, см. HANDOFF_kits_and_calculation.md), теперь — модальное окно поверх дерева (проще технически, тот же паттерн, что уже есть у kit_group/kit_section, разница между вариантами оказалась чисто технической, не про ощущения пользователя — адрес в браузере ему не важен). Полноэкранный режим настоящего подбора материалов (кнопка «Добавить» внутри модалки на будущем шаге) явно отложен как отдельная большая задача.

1. **`app/engine/config.py`** — новый `edit_mode="items_modal"` (третье значение Literal, было только `"modal"`/`"own_page"`) и новое поле `TableConfig.items_source_table_key: Optional[str]` — ключ дочерней таблицы в `ALL_TABLES`, чьи записи показывает модалка (для kit — `"kit_item"`). Дочерняя таблица должна иметь свой `hierarchy.parent_field`, указывающий на FK к текущей записи — так модалка переиспользует тот же универсальный механизм `parent_id`, что и drill-down между уровнями дерева, без нового API.
2. **`app/engine/tables.py`**: `kit_table` — `hierarchy=Hierarchy(parent_field="kit_section_id", parent_key="kit_section")` (БЕЗ `child_key` — последний уровень дерева), `edit_mode="items_modal"`, `items_source_table_key="kit_item"`. `kit_section_table.hierarchy.child_key` возвращён на `"kit"` (был временно пуст в v39). `kit_item_table` получил `hierarchy=Hierarchy(parent_field="kit_id", parent_key="kit")` — НЕ ради появления в цепочке дерева (ничей `child_key` на него не указывает), а чисто ради бесплатной `parent_id`-фильтрации через уже существующий механизм движка; `kit_id`-поле теперь `in_list=False, in_form=False` (проставляется автоматически при сохранении из модалки, не показывается пользователю). Оба (`kit`, `kit_item`) теперь имеют `hierarchy.parent_key` заполненным (не root) — это автоматически даёт им заглушку вместо полноценной страницы при прямом переходе по `/kit-v2`/`/kit_item-v2` (используется уже существующая в движке с v38 логика `is_root()`, без нового кода).
3. **`app/engine/page.py`** — главная часть работы:
   - `_serialize_level_config` — новое поле `itemsSource` в JSON: для `edit_mode="items_modal"` рекурсивно сериализует дочернюю таблицу (`_serialize_items_source`) тем же форматом, что и любой уровень дерева (fields/relations/formLayoutFields) — модалке нужно ровно то же самое, чем и грузить список, и рисовать форму добавления.
   - Модалка переписана на четыре взаимоисключающих режима вместо двух: (1) `items_modal`+есть `id`+не в режиме добавления — список состава (материал+количество, только просмотр) с кнопкой «Добавить»; (2) `items_modal`+`addingItem=true` — простая форма создания новой позиции (select материала + количество), переиспользует `itemsSource.formLayoutFields`; (3) обычная hierarchy-форма (kit_group/kit_section) — как было; (4) `items_modal`+создание нового kit (`editing.id` ещё нет) — тоже обычная форма (название+раздел), т.к. у новой записи не может быть состава. Заголовок модалки для существующего kit показывает название комплекта вместо «Редактирование».
   - Новые JS-методы: `isItemsModal()` (единая проверка режима текущего уровня), `loadKitItems()` (загружает состав через `?parent_id={editing.id}`, плюс опции материалов для отображения названий), `openAddItem()`/`saveNewItem()` (форма добавления — `kit_id` проставляется автоматически из `hierarchy.parentField` источника, не вводится вручную), `itemsSourceRelationName()`/`itemsSourceRelationFor()` (аналоги `relationName()` верхнего уровня, но для полей дочерней таблицы состава).
   - **Hotfix во время работы:** случайно возникший рассинхрон `{% if %}`/`{% endif %}` — JS-комментарий содержал текст `{% if not config.hierarchy %}` (ссылку на Jinja-условие снаружи), который Jinja распарсила как настоящий тег и попыталась его закрыть, что сломало весь рендер страницы (`TemplateSyntaxError`). Исправлено переформулировкой комментария без буквального `{% %}`-текста внутри.
4. **`app/static/style.css`** — новые классы `.items-modal-list`/`.items-modal-row`/`.items-modal-qty`/`.items-modal-empty`/`.items-modal-add-btn` для списка состава внутри модалки.
5. **`app/version.py`** — `APP_VERSION = "v40"`, пункты меню «Комплекты (временный список)» и «Состав комплектов (временный список)» убраны — комплекты теперь доступны только через дерево «Группы комплектов», состав — только через модалку конкретного комплекта.

Протестировано (TestClient, SQLite): все страницы движка — 200; `/kit-v2` и `/kit_item-v2` корректно отдают текстовую заглушку («открывается изнутри дерева») вместо падения. `CONFIG.levels` на `/kit_group-v2` теперь содержит 3 уровня (`kit_group` → `kit_section` → `kit`), у `kit` `editMode: "items_modal"`, `itemsSource.key: "kit_item"`, `childKey: null` (стрелка `›` для перехода вглубь не появляется — верно, дальше только модалка, не следующий уровень дерева). Полный E2E: группа → раздел → комплект → `GET /api/kit?parent_id={section_id}` возвращает только комплекты этого раздела → создание позиции состава с `kit_id`, проставленным как в реальном `saveNewItem()` → `GET /api/kit_item?parent_id={kit_id}` возвращает только позиции этого комплекта. **Побочный положительный эффект от подключения дерева:** удаление раздела с непустым комплектом внутри теперь тоже блокируется (422, «внутри есть N записей «Комплекты»») — раньше, пока kit был отдельной плоской таблицей, этой защиты не было. Регресс: material/brand create, soft-delete toggle на kit, `_build_purge_processors()` (только `purge_brand`/`purge_material`/`purge_kit`, `kit_item` с дефолтным `hard` корректно отсутствует) — не сломаны.

**Следующий шаг темы:** по прямому плану Вахтанга — обсудить и определиться с функционалом редактирования/удаления позиций состава, переименования комплекта внутри модалки, копирования, пометки на удаление; полноэкранный режим настоящего подбора материалов (поиск/фильтры, возможно drill-down по группам материалов) — отдельная большая задача, будет спроектирована отдельно, когда до неё дойдёт очередь.

## Сделано в предыдущей сессии (v39.1 — hotfix: relation-select показывал пустые опции для display_field != "name")

Обнаружено на устройстве сразу после v39 (скриншот): в форме «Состав комплектов» выпадающий список «Материал» показывал только «—», хотя в справочнике материалов было 5 записей. Причина: движок (`page.py`) в трёх местах — `<option x-text="opt.name">` в форме, `<span x-text="opt.name">` в фильтр-чипах списка, `relationName()` в JS — жёстко использовал поле `opt.name`, ИГНОРИРУЯ `Relation.display_field` из конфига. Для `material_table.brand_id` (`display_field="name"`) и `kit_table.kit_section_id` (`display_field="name"`) это случайно совпадало и работало; для `kit_item_table.material_id` (`display_field="short_name"`, т.к. у Material нет поля `name`) — опции реально загружались с сервера (`relationOptions` не пуст), но подпись у каждой была пустой строкой, что выглядело как «список пуст».

1. **`app/engine/page.py`** — три места исправлены на использование `display_field` вместо жёстко зашитого `.name`: Jinja-шаблон формы (`opt['{{ rel.display_field }}']`, ключ известен на этапе рендера сервером), Jinja-шаблон фильтр-чипов списка (та же замена), JS-функция `relationName()` (`found[rel.display_field]`, `rel.display_field` уже приходит в сериализованном JSON `relations`).
2. **`app/engine/tables.py`** — `kit_item_table.form_rows` изменён по прямому запросу Вахтанга (материал в узком поле рядом с «Комплект» нечитаем на телефоне): «Материал» теперь отдельной широкой строкой, «Комплект»+«Количество» — в одной строке, «Количество» узкое (`FieldConfig(..., form_width="110px")`).

Протестировано (TestClient, SQLite): рендер `/kit_item-v2` содержит `opt['short_name']` (материал) и `opt['name']` (комплект) — фикс применён. Регресс: `/material-v2` (brand select) и `/kit-v2` (kit_section select) по-прежнему используют `opt['name']` — не сломаны, они и раньше случайно работали через захардкоженное поле. Полный E2E по сценарию со скриншота (группа → раздел → комплект «Панель 150» → материал → позиция состава через API) — создаётся и возвращается корректно. Все страницы движка — 200.

## Сделано в предыдущей сессии (v39 — kit/kit_item как временные плоские таблицы)

Контекст: после v38.1 (движок объединён, kit_group/kit_section работают как drill-down дерево) следующий шаг по плану — карточка kit с подбором материалов (`edit_mode="own_page"`). Вахтанг решил разбить этот шаг на два: сначала (v39) — просто завести таблицы kit/kit_item как ОБЫЧНЫЕ ПЛОСКИЕ таблицы старого движка (без drill-down, без карточки), чтобы вручную занести пробные записи и увидеть данные в системе уже сейчас; полноценный подбор материалов внутри карточки — отдельным шагом позже, когда будет спроектирован (по словам Вахтанга — "очень много работы по подбору").

1. **`app/models/kit.py`** — новая модель `Kit` (`id`, `name`, `sort_order`, `kit_section_id` — FK на `kitsection.id`, nullable как у прочих relation-полей проекта; `is_deleted` — soft-delete, т.к. на kit в будущем будут ссылаться `calculation_item`, см. HANDOFF_kits_and_calculation.md).
2. **`app/models/kit_item.py`** — новая модель `KitItem` (`id`, `kit_id` — FK на `kit.id`, `material_id` — FK на `material.id`, `quantity: float`). БЕЗ `is_deleted` — согласно принципу "живая ссылка vs снапшот", ничто не ссылается на конкретный `KitItem` напрямую (калькуляция хранит только `kit_id` и разворачивает состав live), значит удаление позиции состава — осознанно всегда безусловное физическое удаление сразу (`delete_mode` не указан → дефолт `"hard"`), без пометки и без purge-processor.
3. **`app/engine/tables.py`** — `kit_table` (`delete_mode="soft"`, `Relation(kit_section_id → kit_section)`, простой select без поиска — по образцу `material_table.brand_id`) и `kit_item_table` (`delete_mode` дефолтный `"hard"`, два `Relation`: `kit_id → kit`, `material_id → material`). Оба — `hierarchy=None`, обычные плоские таблицы. **Важная деталь:** `kit_section_table.hierarchy.child_key` НЕ проставлен в `"kit"` (хотя концептуально kit_section — родитель kit в дереве) — если бы был проставлен, `_build_hierarchy_levels` (page.py, см. v38) молча включил бы `kit` в цепочку уровней drill-down дерева как узел БЕЗ `hierarchy`, что сломало бы сериализацию/клиентскую логику (`hasNextLevel` и т.д. рассчитаны на то, что у любого элемента `LEVELS` есть `hierarchy`). `child_key` вернётся, когда `kit` станет настоящим drill-down уровнем.
4. **`app/version.py`** — `APP_VERSION = "v39"`, добавлены пункты меню «Комплекты (временный список)» → `/kit-v2` и «Состав комплектов (временный список)» → `/kit_item-v2» (с пометкой «временный» прямо в названии пункта, чтобы не создавать впечатление финального UI).

Протестировано (TestClient, SQLite): все страницы движка (`/material-v2`, `/brand-v2`, `/constant-v2`, `/kit_group-v2`, `/kit_section-v2`, `/kit-v2`, `/kit_item-v2`, `/processors`, `/health`) — 200. Полный E2E: группа → раздел → 2 тестовых комплекта («Подключение ВА47 3P 63А», «Подключение ВА47 3P 100А») в одном разделе → материал → позиция состава (кабель, кол-во 5) — все создаются и корректно связаны через `Relation` (выпадающие списки в форме отдают правильные варианты). Soft-delete toggle на `kit` работает (`purge_kit` появился в `_build_purge_processors()` автоматически). Hard-delete на `kit_item` — физическое удаление сразу, без пометки, `purge_kit_item` в реестре корректно отсутствует. Дерево `/kit_group-v2` по-прежнему обрывается на `kit_section` (`childKey: null`, `levels` длины 2) — стрелка `›` и переход вглубь на разделах не появляются, регресс из v38.1 не воспроизведён. Регресс `material`/`brand`/защита удаления непустой группы (422 с понятным текстом) — не сломаны.

**Следующий шаг темы:** карточка `kit` (`edit_mode="own_page"`, `hierarchy` без `child_key`, drill-down-подключение к дереву вместо текущего плоского списка) с полноценным подбором материалов внутри — большая отдельная задача, будет спроектирована отдельно перед реализацией.

## Сделано в предыдущей сессии (v38.1 — hotfix: навигация проваливалась в несуществующий уровень)

Обнаружено на устройстве сразу после v38 (скриншот): открыв группу → раздел («Группы › Подключение оборудования › Модульные автоматы»), внутри показывались НАЗВАНИЯ ГРУПП («Установка оборудования», «Подключение оборудования») вместо ожидаемого пустого списка комплектов. Причина: `currentLevel()` имел фоллбэк `LEVELS[this.drillPath.length] || LEVELS[0]` — когда `drillPath.length` выходил за границы `LEVELS` (2 элемента: kit_group, kit_section — `kit` ещё не реализован), тихо откатывался на `LEVELS[0]` (группы) вместо явной защиты. А защиты от самого выхода за границы не было: стрелка `›` в строке и `drillOpen()` проверяли только `hierarchy.childKey` из конфига (у kit_section он заполнен — `"kit"`, т.к. дерево концептуально трёхуровневое), не проверяя, существует ли этот уровень РЕАЛЬНО в `LEVELS`.

1. **`currentLevel()`** — фоллбэк `|| LEVELS[0]` убран. Теперь при некорректном `drillPath` метод вернул бы `undefined` вместо того чтобы маскировать баг постановкой не относящихся к узлу данных.
2. **Новый геттер `hasNextLevel`** — единое место истины: `true` только если и `childKey` задан в конфиге текущего уровня, И `LEVELS[drillPath.length + 1]` реально существует. Используется и для стрелки `›` в строке, и в `drillOpen()` (заменил прежнюю неполную проверку) — раньше условие дублировалось в двух местах по-разному, теперь один источник.
3. **Иконка ✎** — размер увеличен (15px → 22px), зона нажатия расширена через padding+отрицательный margin (визуальный размер строки не меняется, но фактическая кликабельная область больше) — по прямому запросу с фото («слишком маленькая, нужно увеличить то поле на которое надо тыкать»).
4. Тело строки (`drill-row-body`) теперь получает `cursor: pointer` только когда `hasNextLevel` истинно — на последнем реально существующем уровне (сейчас это kit_section) курсор больше не обещает переход, которого не будет.

Протестировано (TestClient, SQLite): `config_json.levels` содержит 2 элемента; для симулированного `drillPath.length=1` (внутри группы, на разделах) `LEVELS[2]` — `undefined`, значит `hasNextLevel` вернёт `false` и стрелка/переход корректно не появятся. Рендер `/kit_group-v2` содержит новую JS-логику (`hasNextLevel`, `LEVELS[this.drillPath.length]` без `||`). В v28 поле убрали из модели `Material` (ставка стала общей, живёт в `constants`), но колонку в уже существующей таблице никто не дропнул — `SQLModel.metadata.create_all()` создаёт только отсутствующие таблицы целиком, лишние колонки в существующих не трогает. Из-за этого падал ЛЮБОЙ `INSERT` в `material`, не только копирование. Диагностировано по логам Railway (Deploy Logs): `psycopg2.errors.NotNullViolation: null value in column "vat_rate" of relation "material" violates not-null constraint`.
   - Добавлена `_drop_obsolete_columns()` в `app/database.py`, вызывается в `init_db()` рядом с `_ensure_is_deleted_columns()`. Дропает `material.vat_rate` через `ALTER TABLE ... DROP COLUMN IF EXISTS` — идемпотентно. Симметричный механизм к `_ensure_is_deleted_columns()` (тот добавляет недостающие колонки, этот убирает лишние) — при появлении будущих устаревших колонок достаточно добавить строку в список `obsolete`.
4. Фронт (JS) не округляет `price_vb_incl_vat` дополнительно — бэкенд гарантированно округляет всё при `save()`.
5. **Компактная вёрстка блока цен, по дополнительной правке в этой же сессии:**
   - **`vat_rate` убран из формы через `in_form=False`** (новый флаг у `FieldConfig`, поддерживался и раньше, но не использовался). Поле остаётся `virtual=True` с `source_constant_key="vat_rate"` — по-прежнему участвует в `ComputedPair.rate_constant_key`, по-прежнему видно как колонка списка материалов. Меняется только видимость в форме.
   - **Ставка НДС показывается прямо в лейбле «Цена с НДС»** — «Цена с НДС (20%)». Механизм в `page.py` универсальный: для поля, которое является `field_b` в `computed_pair` со `rate_constant_key`, лейбл рендерится с `x-text="constants[...]"` вместо статичного текста — сработает для любой будущей таблицы движка с аналогичной парой цена/ставка, без правок `page.py`.
   - **Все три денежных поля материала — один `FormRow`, ширина каждого — `100px`** (`price_excl_vat`, `price_incl_vat`, `price_vb_incl_vat`). Отдельный `FormRow` под `price_vb_incl_vat` убран.

**Важно для следующей сессии:** при первом деплое этого архива на Railway произойдёт настоящий `DROP COLUMN vat_rate` на боевой таблице `material` — ожидаемо и безопасно (колонка не используется кодом с v28), но стоит проверить деплой success и что создание/копирование материала в проде реально работает, прежде чем считать баг закрытым.

## Сделано в предыдущей сессии (v33 — копирование строки)

Контекст: нужна была возможность быстро создать похожую позицию (как в 1С — встал на строку, скопировал). Первая идея (маленькая пиктограмма «⎘» в каждой строке списка) была отклонена в процессе обсуждения — на телефоне легко промахнуться по маленькой кнопке в узкой строке. Вместо этого выбран механизм «выделение чекбоксом + панель действий над списком» — тот же паттерн, который в будущем даст groupdelete и другие массовые операции без переделки.

1. **Чекбоксы в начале каждой строки** (первая колонка, видна только когда `TableConfig.allow_create=True` — копировать в таблицу, где создание запрещено, бессмысленно; сейчас это исключает только `constant_table`). Клик по чекбоксу не открывает форму редактирования (`@click.stop` на ячейке).
2. **Панель выделения** (`.selection-bar`) — появляется над списком только когда есть хотя бы одна выделенная строка, показывает счётчик «N выделено», кнопку «Копировать» и «Снять выделение».
3. **«Копировать» активна только при РОВНО одном выделенном элементе** — при 0 или 2+ кнопка задизейблена (`:disabled`). Сознательное решение: групповое копирование нескольких строк сразу — не то поведение, которое нужно (человек, как правило, что-то меняет перед сохранением копии, а не штампует дубликаты пачкой).
4. **`copySelected()`**: находит выделенный item в уже загруженном списке, открывает обычную модалку редактирования, предзаполненную его данными, но без `id` и с `is_deleted=false`. Дальше — обычный путь: `save()` видит отсутствие `id` → шлёт `POST` (создание), а не `PUT`. Все поля копируются как есть, включая `sku_article` — человек правит вручную перед сохранением (осознанное решение, не очищать артикул автоматически).
5. **`selectedIds` сбрасывается при каждой перезагрузке списка** (`load()`) — смена страницы/поиска/фильтра/сортировки может увести выделенные id с экрана, панель не должна показывать "выделено N" для невидимых строк.
6. Никаких изменений API — копирование целиком на фронте поверх уже существующего `POST /api/{key}`.

Протестировано (TestClient, SQLite): разметка чекбоксов/панели присутствует на материалах и брендах, отсутствует на константах (`allow_create=False`); полный сценарий копирования материала — копия получает новый `id`, независима от оригинала, все поля (включая артикул) скопированы как есть, оригинал не затронут, обе записи существуют одновременно; регресс create/list/delete-toggle/пагинации/сортировки — не сломан.

## Сделано в этой сессии (v31 — пагинация списков)

1. **`GET /api/{key}` возвращает объект вместо голого массива.** Было: `[...]`. Стало: `{"items": [...], "total": N, "page": N, "page_size": N, "total_pages": N}`. Это ломающее изменение формата ответа — обновлены ВСЕ места фронта, которые дёргают `/api/{key}` (основной список, `relationOptions`, подгрузка `constants{}` в `init()`).
2. **Новые query-параметры:** `page` (1-based, по умолчанию 1, отрицательные/за пределами общего числа страниц — зажимается до валидного диапазона) и `page_size` (если не передан — берётся `default_page_size` из справочника constants; если передан явно — приоритетнее константы). Явный `page_size` используется для служебных запросов, которым нужен весь список целиком без пагинации (например `relationOptions` для фильтров/выпадающих списков — передают `page_size=1000`).
3. **`total` считается ДО применения LIMIT/OFFSET** — по тому же statement, с учётом активного поиска/фильтра, чтобы «Стр. X из Y» не врало при активном поиске.
4. **UI:** блок пагинации под таблицей — «‹ Назад / Стр. X из Y / Далее ›», кнопки дизейблятся на первой/последней странице, блок скрыт целиком, если страниц ≤ 1.
5. **Сброс на 1-ю страницу** при изменении поискового запроса, чекбоксов полей поиска, клике по фильтру-чипу, клике по сортируемому заголовку колонки — везде, где меняется набор данных, страница явно сбрасывается в `page=1` перед `load()`. Клик «Назад»/«Далее» не сбрасывает — только двигает `page`.

Протестировано (TestClient, SQLite): 25 материалов, `page_size=10` → 3 страницы (10/10/5), `page=99` зажимается до последней валидной страницы, `page_size=1000` возвращает всё на одной странице (сценарий `relationOptions`), запрос без `page_size` берёт `default_page_size=100` из constants, `/api/constant` тоже отдаёт новый формат `{items,...}`, поиск + пагинация вместе — `total` отражает именно отфильтрованное количество, а не общее.

⚠️ Побочно обнаружено (не связано с пагинацией, существовало и раньше): на SQLite (только тестовое окружение) `LOWER()` не обрабатывает кириллицу регистронезависимо — поиск/сортировка по русским полям в TestClient-тестах может давать 0 совпадений, хотя на Postgres (Railway, продакшен) `LOWER()` с кириллицей работает корректно. При написании будущих тестов с поиском по тексту — либо проверять на латинице/цифрах, либо не полагаться на регистронезависимость кириллицы в SQLite-тестах.

Для SQLite — не нужна, пропускается (там таблица создаётся сразу с полем). **Решено в сессии v32 (зафиксировано, не поднимать заново без причины):**

- Валюта поставщика (EUR/USD/др.) НЕ хранится отдельным полем — сознательно, для расчёта неважно какая именно валюта, только цифры (курс и цена в валюте).
- Курс бренда (`rate_vb`) правится вручную в форме, без интеграции с внешним источником курсов — как и было решено для первой итерации.
- Названия полей в БД/коде: `Brand.rate_vb`, `Material.price_vb_incl_vat`. Подписи в UI: «Курс ВБ», «Цена с НДС ВБ».

**Решено в сессии v33 (зафиксировано, не поднимать заново без причины):**
- Копирование строки реализовано через выделение чекбоксом (не через маленькую пиктограмму в строке — на телефоне легко промахнуться) + кнопка «Копировать» в панели над списком. Активна только при ровно одном выделенном элементе — групповое копирование нескольких строк сразу сознательно не делали.
- Инфраструктура выделения (`selectedIds`, `.selection-bar`, чекбоксы в строках) — рассчитана на будущие групповые операции (bulk soft-delete, массовое изменение поля типа бренда у нескольких материалов разом), но сейчас реализовано только копирование. Расширять панель новыми кнопками — когда появится конкретная следующая массовая операция, не заранее.
- Копия получает новый `id`, `is_deleted` копии всегда `false`, остальные поля (включая `sku_article`) копируются как есть без очистки — человек правит вручную перед сохранением.

**Обсуждались, но НЕ реализованы (обдумать порядок отдельно, не начинать без явного решения):**
- Inline-редактирование в списке без открытия модалки.
- Клавиатурная навигация по списку (стрелки вверх/вниз, Google Sheets-style) — отдельный по объёму кусок работы, в основном десктопная фича (разработка ведётся с телефона). Аддитивна, не создаёт технический долг независимо от того, когда её делать.
- Порядок относительно kits/spec_items — не выбран; фичи движка (копирование, будущие групповые операции) аддитивны и не требуют переделки существующих/будущих таблиц, поэтому можно чередовать или делать в любом порядке.
